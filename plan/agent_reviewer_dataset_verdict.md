## Вердикт

**REQUEST_CHANGES**

Критичные проблемы **найдены**. До устранения подтверждённой утечки и загрязнения схемы признаков **`APPROVE` недопустим** (блокирующее условие ТЗ ревьюера §8 п.1).

### Условия для APPROVE

1. Устранить утечку через признаки, производные от голов **целевого** матча (`diff_goals_target`, `sum_goals_target` и любые аналогичные колонки до исправления wide-слоя и загрузки target games).
2. Убрать технические колонки после `merge_asof` (`*_x`/`*_y`), чтобы манифест содержал только канонический набор признаков.
3. Расширить тесты так, чтобы подобная утечка ломала сборку (assert по запрещённым именам/инвариантам).
4. Прогнать полный набор тестов в среде с рабочим NumPy/pandas.

## 1. Findings (по убыванию severity)

### HIGH — Утечка целевого матча через голы из `game_team_stats`

| Поле | Содержание |
|------|------------|
| **Severity** | HIGH |
| **Риск для продукта** | Метрики обучения и отбор модели искажены; возможны тривиально высокие метрики за счёт признаков, кодирующих счёт и исход. |
| **Где** | `modeling/dataset_builder/assemble.py` — `_wide_feature_columns()`; источник голей — `modeling/dataset_builder/base.py` (`home_goals_target`, `away_goals_target` из JOIN по целевому `game_id`). |
| **Нарушение контракта** | План §2: статистика того же матча не должна входить в признаки. `_wide_feature_columns` строит `diff_*`/`sum_*` для всех пар `home_*`/`away_*`, включая `goals_target`. После `drop` остаются только сырые `home_goals_target`/`away_goals_target`, а **`diff_goals_target` и `sum_goals_target` сохраняются** и попадают в манифест (подтверждено в `artifacts/datasets/season_20252026/metadata_train.json`). |
| **Рекомендуемое исправление** | Не подтягивать голы целевого матча в слой фич **или** явно исключить из wide любые колонки текущего матча и производные (`diff_goals_target`, `sum_goals_target`). Метки оставить из отдельного канала без следов во фичах. |
| **Как проверить фикс** | Юнит-тест: искусственный матч с заданным счётом — во фичах не должно быть информации, однозначно восстанавливающей сумму голов или победителя; запрет имён `diff_goals_target`/`sum_goals_target` в списке фич train. |

### HIGH — Загрязнение признаков суффиксами `_x` / `_y` после `merge_asof`

| Поле | Содержание |
|------|------------|
| **Severity** | HIGH |
| **Риск** | Дрейф схемы, лишние признаки, расхождение с каноническим манифестом из плана (rolling + контекст). |
| **Где** | `modeling/dataset_builder/features.py` — `_snapshot_side()` (`pd.merge_asof`). |
| **Нарушение контракта** | Имена и порядок колонок должны соответствовать явному манифесту; появление `home_team_id_x` и т.п. — побочный эффект merge, не часть контракта. Пример: `artifacts/datasets/season_20252026/metadata_train.json`. |
| **Рекомендуемое исправление** | Перед `merge_asof` переименовать правую таблицу в однозначные `_hist_*` имена или полностью нормализовать после merge без `_x`/`_y` в финальных фичах. |
| **Как проверить фикс** | Сборка train на малом срезе + assert: ни одна feature-колонка не содержит `_x`/`_y`; сверка с белым списком имён. |

### MEDIUM — «Две строки на матч» проверяется через `nunique(team_id)`, не через число строк

| Поле | Содержание |
|------|------------|
| **Severity** | MEDIUM |
| **Риск** | Три строки на `game_id` при двух различных `team_id` не отфильтровываются → некорректные facts/join. |
| **Где** | `modeling/dataset_builder/team_game_facts.py`. |
| **Нарушение контракта** | План §4.2: ровно две строки в `game_team_stats` на игру. |
| **Рекомендуемое исправление** | Проверять `size() == 2` по группе или эквивалент после осмысленного dedup. |
| **Как проверить фикс** | Тест: три строки, два distinct `team_id` → матч в dropped + запись в отчёте. |

### MEDIUM — Две игры одной команды в один календарный `day`

| Поле | Содержание |
|------|------------|
| **Severity** | MEDIUM |
| **Риск** | Вторая игра того же дня может получить rolling со `shift(1)` от первой игры того же дня при сортировке `team_id, day, game_id` — это противоречит строгому «только `day < D`» без intra-day timestamp (план §2). |
| **Где** | `modeling/dataset_builder/features.py` — `compute_team_rolling_features`. |
| **Рекомендуемое исправление** | История только с `day < target_day` или явное допущение + фильтрация double-header. |
| **Как проверить фикс** | Синтетический double-header: rolling второй строки не использует первую в том же `day`. |

## 3. Пройденные проверки

- Единый контур фич для train/predict: `build_dataset` в `modeling/dataset_builder/base.py`.
- Календарный контур merge-asof: `allow_exact_matches=False`, `direction="backward"` в `features.py`.
- Rolling с `shift(1)` перед окном в `compute_team_rolling_features`.
- Schema parity: `assert_feature_parity`, сравнение `features_hash` при predict.
- Fail-fast: `validate_or_raise` в `validate.py` (ключи, уникальность `game_id`, NaN/inf, часть диапазонов, проверки hist vs target day и hist_game vs game_id, запрет меток в predict).
- Тест `hist_day < target_day` по смыслу: `test_strict_past_only_by_day` в `tests/test_modeling_dataset_build.py`.
- Наличие `features_hash`, `feature_set_version`, `code_version` в метаданных (`base.py`).

---

## 4. Непокрытые риски

- Отдельный golden/regression fixture на полную CLI-сборку (ТЗ ревьюера §9.4).
- Тесты не ловят утечку через `diff_goals_target` / `sum_goals_target` — критичный пробел относительно цели `test_no_same_game_leakage`.

## 5. Примечание о прогоне тестов

При ревью локальный запуск через системный `python3` не выполнен из‑за несовместимости архитектуры NumPy (x86_64 vs arm64). Выводы по leakage и схеме подтверждены статическим анализом кода и артефактами `metadata_train.json` в репозитории.
