# Задача 80. Dev-стенд: ветка `develop`, dev-бот и база `nhl_dev` на той же VM

**Блок:** релиз · **Надобность:** 🟠
**Область:** `.github/workflows/release.yml` (деплой `develop`), `.github/workflows/ci.yml`
(пуш в `develop`), `deploy/` (оверрайд compose для dev, `fetch-secrets.sh` и юнит — второй
секрет), Secret Manager (`nhl-bot-telegram-token-dev`), VM (`/opt/nhl_bot_dev`, база
`nhl_dev`), `DEVELOPMENT.md` §«Прод-деплой», `CLAUDE.md` («Ветки и выкатка»).
**Зависит от:** Задачи 79 (продовый бот на новом токене; старый токен освобождается).
**Источник:** просьба человека 2026-10-24; реестр — [`../open_tasks.md`](../closed_tasks.md).

## Кратко

Две ветки — два бота на одной VM: `develop` выкатывается на dev-бота (нынешний бот),
`master` — на продового (Задача 79). Код сначала мержится в `develop`, проверяется на
dev-боте, затем `develop` мержится в `master`. Postgres один, баз две: прод — `postgres`,
dev — `nhl_dev`.

## Зачем и на что влияет

- Сейчас живая проверка задачи (🟨 у 34, 63, 64, 76) идёт прямо на проде: мерж в `master`
  сразу выкатывает код настоящим подписчикам. Dev-бот даёт ту же проверку до прода.
- Миграция или новая SQL-функция сначала проходит на `nhl_dev`; продовая схема меняется
  только мержем в `master`.

## Степень важности

🟠: после выпуска (79) ошибки на проде видят пользователи, а не только автор.

## Подробно

**Состояние на 2026-10-24.**
- VM `e2-small` (2 ГБ RAM, диск 20 ГБ). Деплой — `release.yml` на пуш в `master`: тег,
  образ в GHCR, `docker compose up` в `/opt/nhl_bot`; `migrate` перед стартом применяет
  `db-functions db-migrate`.
- База прода — 207 МБ на диске (замер локальной копии 2026-10-24: `shot_attempts` 115 МБ,
  `game_player_stats` 57 МБ). Вторая база в том же контейнере уже бывает:
  `nhl_bot_predict_demo` (90 МБ) локально.
- Все сервисы берут `PG_DATABASE` из `docker-compose.yml` (сейчас `postgres` у каждого),
  `config.py` читает его из окружения — код базу не хардкодит.
- `docker-compose.yml` задаёт `name: nhl_bot`; второй проект на VM — через
  `COMPOSE_PROJECT_NAME` (он сильнее `name:`).

**Почему не общая база (обсуждено с человеком 2026-10-24).** `bot_subscriptions` хранит
только `chat_id`, без бота: dev-`sync` разослал бы всем продовым подписчикам от dev-бота,
а на `Forbidden` рассылка **деактивирует** подписку — dev гасил бы прод. И `migrate` при
деплое `develop` менял бы схему под продовым кодом. Отдельная база в том же Postgres
снимает обе проблемы почти без лишней памяти: `shared_buffers` и процесс сервера общие.

**Что сделать.**
1. **Ветка.** `develop` от `master`; в GitHub — защита обеих веток (мерж только через PR с
   зелёным CI), ветка по умолчанию для PR — `develop` (настройки — человек).
2. **База.** `CREATE DATABASE nhl_dev` в контейнере `db` прода; наполнить из свежего дампа
   сервиса `backup` (`pg_restore -d nhl_dev`). После восстановления очистить подписки и
   отметки рассылок в `nhl_dev` — подписчики dev-бота заводятся заново. `backup` dev-базу
   не снимает (её всегда можно пересобрать из продовой).
3. **Стек.** Чекаут `/opt/nhl_bot_dev`, свой `.env` (`COMPOSE_PROJECT_NAME=nhl_bot_dev`,
   `PG_DATABASE=nhl_dev`) и оверрайд `deploy/compose.dev.yml`: сервисы `migrate`, `bot`,
   `sync`, `predict` подключены к сети прод-проекта (`db` — внешний хост), своих `db` и
   `backup` у dev нет; `PG_DATABASE` — из `.env`, а не литералом.
4. **Токен.** Старый токен (после 79) — секрет `nhl-bot-telegram-token-dev`, файл
   `/run/nhl_bot_dev/telegram_bot_token`. `fetch-secrets.sh` сейчас знает один секрет —
   принимает имя секрета и каталог аргументами, второй экземпляр юнита (или шаблон
   `nhl-bot-secrets@.service`).
5. **Деплой.** `release.yml`: пуш в `develop` → CI → образ `ghcr.io/karych72/nhl_bot:dev-<sha>`
   (без git-тега) → деплой в `/opt/nhl_bot_dev`, environment `staging`, своя группа
   `concurrency`. Пуш в `master` — как сейчас, только прод. `ci.yml` — пуш в `develop` тоже.
6. **Память.** Замер `docker stats --no-stream` на VM до и после подъёма dev-стека — в отчёт.
   Если свободной памяти меньше ~300 МБ или `predict` двух стеков пересекается по времени
   (оба в 12:00 UTC) и VM уходит в swap — сдвинуть dev-`predict` или предложить человеку
   `e2-medium` (4 ГБ, ≈ +$12/мес; решение человека).
7. **Правило веток** — в `CLAUDE.md` уже записано (раздел «Ветки и выкатка») и вступает в
   силу с закрытием этой задачи: удалить там абзац «До закрытия Задачи 80…».

**Оценка места.** Диск: +~210 МБ на `nhl_dev` (растёт как продовая, ~40 МБ за сезон без
бросков) и образы `dev-<sha>` — их чистит `docker image prune -af` в деплое. Память: dev-`bot`
и `sync` — порядка 100–200 МБ каждый, `predict` — пик при прогоне; Postgres почти не растёт.
Сеть: dev-`sync` удваивает запросы к NHL API ночью (раз в 30 минут) — нагрузка ничтожная.

**Критерии приёмки.**
- Мерж в `develop` выкатывает только dev-стек: dev-бот отвечает на новом коде, у продового
  тег и контейнеры не изменились.
- Мерж `develop` → `master` выкатывает прод как сейчас (тег, образ, деплой).
- Пробная миграция на `develop` видна в `schema_migrations` базы `nhl_dev` и не видна в
  `postgres` (или: функции/миграции только `nhl_dev` — проверка без пробной миграции,
  исполнитель обосновывает).
- Подписки прода после подъёма dev-стека и ночи работы не деактивированы.
- Замер памяти — в отчёте; `DEVELOPMENT.md` описывает оба стека; `make ci-local` зелёный.

**Подводные камни.**
- Миграции идут одна за другой: `develop` применяет миграцию на `nhl_dev`, а на `postgres`
  она попадёт только мержем в `master`. Если `develop` откатывают без мержа — `make
  db-migrate-down` на `nhl_dev` или пересборка базы из дампа.
- Hotfix прямо в `master` нужно сразу влить обратно в `develop`, иначе следующий мерж
  `develop` → `master` его откатит.
- Нельзя запускать локальный `make bot` с dev-токеном, пока dev-бот на VM работает:
  второй polling-клиент получает `Conflict`. Для локальной отладки — личный третий бот.
