## Релизный блок

### Задача 33. Переход на сезон 2026/27 🟨 🔴
Идентификатор сезона сейчас задаётся в четырёх независимых местах, и три из них — зашитые
дефолты прошлого сезона: `.env` (`SEASON_ID`/`SEASON`/`CURRENT_SEASON`),
`telegram_bot/config.py:69-70` (`20252026`, `"25/26"`), `Makefile:50`
(`SEASON_START ?= 2025-10-01`). В БД пять сезонов, последний день — `2026-04-16`;
за 2026/27 нет ничего.

Область: `.env.example`, `telegram_bot/config.py`, `Makefile`.
Приёмка: сезон задаётся в одном месте, остальные читают оттуда; сезон 2026/27 загружен
в БД после первых игр; `make ci-local` зелёный. Старые дефолты удалить, а не оставить
рядом с новыми (Global Constraint 3).

Кодовая часть выполнена в ветке `sdd-task-33-season` (PR #36): сезон сведён к одному
источнику `SEASON_ID` — подпись сезона и дата старта полной перезагрузки выводятся из
него в `telegram_bot/config.py` (`derive_season()`), дефолтов в коде не осталось,
отсутствие `SEASON_ID` валит старт и бота, и лоадера явной проверкой. Задача остаётся
открытой до шага 6: после первых игр регулярки 2026/27 — `SEASON_ID=20262027` в `.env`,
`make season-load-full`, проверка `SELECT season_id, count(*) FROM games GROUP BY 1`.

### Задача 34. Автообновление данных 🟨 🔴
Все цели `season-sync-*` — ручные. В `.github/workflows/` только `ci.yml`, в
`docker-compose.yml` сервиса загрузчика нет.

Область: `docker-compose.yml` либо `.github/workflows/`, `Makefile`.
Приёмка: загрузчик идёт по расписанию без участия человека, минимум раз в сутки; окно дат
вычисляется переносимо — `make season-sync-week` сейчас использует macOS-синтаксис
`date -v-7d` (`Makefile:228`) и в Linux-cron не заработает; неуспешный прогон виден
(Global Constraint 4 — молчаливый отказ cron равен протухшим данным); повторный прогон
по уже загруженным дням идемпотентен.

Кодовая часть выполнена в ветке `sdd-task-34-auto-sync` (PR #38, 2026-09-28): сервис `sync` в
`docker-compose.yml` на образе бота, планировщик `pipeline/scheduled_sync.py` (stdlib) —
ежедневно в 08:00 UTC окно «сегодня − 2 дня … сегодня», затем дайджест; при старте
контейнера прогон без дайджеста. Отказ виден как `unhealthy` в `docker compose ps`
(healthcheck `scheduled_sync.py check`: последний прогон неуспешен или старше 26 ч) и
ERROR в `docker compose logs sync`. `season-sync-week` считает окно Python-ом
(`WEEK_AGO`). Идемпотентность проверена: окно 2025-10-07…08 загружено дважды, счётчики
`games`/`all_goals`/`game_player_stats` не изменились. Задача остаётся открытой до
проверки на живом стеке: `docker compose up -d --build sync`, через сутки
`SELECT max(day) FROM games WHERE season_id = <текущий>` сдвинулся без ручного запуска.
Смена сезона по-прежнему требует правки `SEASON_ID` в `.env` (дизайн Задачи 33).

### Задача 35. Площадка, живучесть, бэкап ✅ 🔴

Область: `docker-compose.yml`, `DEVELOPMENT.md`.
Приёмка: `restart: unless-stopped` у сервисов; `pg_dump` по расписанию, восстановление

Выполнена в ветке `sdd-task-35-backup` (PR #39, 2026-09-28), живая проверка: `docker ps` —

### Задача 36. Поведение на пустом и частичном сезоне ✅ 🔴
Сценарий «сезон начался, сыграно 0–3 тура» не проверялся ни разу: все пять загруженных
сезонов в БД полные.

Область: `telegram_bot/`, `tests/`.
Приёмка: тесты на сезон с 0 и с 1–3 игровыми днями для `/table`, `/leaders`, `/day_games`,
`/game`, `/advanced`; ни одного необработанного исключения; пустой ответ несёт текст
с причиной, а не пустую таблицу.

Выполнена в ветке `sdd-task-36-empty-season` (PR #44, 2026-09-28). Шаг 1
карточки (что пишет загрузчик в пустой сезон) прогнан по-настоящему: `season-load-full`
для `SEASON_ID=20262027` на скретч-БД (`nhl_task36_scratch`, тот же контейнер `nhl_bot-db-1`,
удалена после прогона) при 0 сыгранных играх лиги (2026-09-28, до старта регулярки) пишет
**0 строк во все таблицы без исключения** — не только `games`, но и `teams`/`teams_stats`/
`rosters`/`players_season_stats`: `build_teams_and_stats()` строит их из агрегата
`team/summary` по уже сыгранным играм, а `build_rosters()` идёт только по командам из этого
же списка (`pipeline/load_season_modern.py:263-338`). Фикстуры «0 игровых дней» в тестах —
пустой ответ на любой запрос, это и есть факт, а не гипотеза. «1–3 игровых дня» на живом
API получить нельзя (сезон 2026/27 на дату работы ещё не начался) — фикстура построена по
тому же факту: команда без единой игры отсутствует в `teams_stats`/`rosters` целиком, а не
приходит строкой с нулями. Найден и исправлен реальный дефект: `team_table()` (`/table`) на
пустом `teams_stats` рендерила таблицу-скелет (заголовки конференций/дивизионов без единой

нет статистики команд.». Тот же дефект на уровне одного дивизиона (частичный сезон: у
дивизиона нет ни одной сыгравшей команды) нашло финальное ревью — правка того же рода:

### Задача 39. Два пробела конфига моделирования ✅ 🟠

### Задача 40. Качество модели ✅ 🔴 (для трека B)
Ни одна из четырёх пар `(task, model)` не прошла baseline-гейт. Цифры с holdout
(994 игры, отчёты прогона Задачи 15): `home_win`/logreg — `log_loss_raw` 0.6977 против
тривиальной константы 0.6938, то есть **хуже**, чем всегда предсказывать базовую частоту;
`home_win`/lgbm — 0.7546, явное переобучение. Состав фич: 212 колонок на 6049 строк, и все
они — скользящие средние командного бокс-скора. Нет рейтинга силы команды (Elo/Glicko),
вратаря, составов, перелётов и часовых поясов. Задача 39 этого не чинит: она про то,
чтобы сравнение вообще было корректным, а не про то, чтобы модель начала работать.

Область: `modeling/dataset_builder/features.py`, конфиги.
Приёмка: хотя бы одна пара бьёт тривиальный baseline на holdout по log-loss **на
калиброванных вероятностях** и проходит acceptance-gate; `latest` проставляется
механизмом, а не рукой. Работа заведомо больше бюджета одной задачи (Global Constraint 6)
— разбивать при заведении.

Выполнена в ветке `sdd-task-40-model-quality` (PR #43, 2026-09-28), 4 подзадачи:
`calibration.method: platt` по умолчанию (Задача 1, спайк 40a показал isotonic на 300-игровом
калибровочном блоке даёт точные 0/1); финальный retrain lgbm на фиксированном
`num_boost_round` без утечки early stopping + сетка 2187→8 точек (Задача 2); as-of pre-game
Elo (`diff_elo`) в датасет-билдере, `feature_set_version: v2` (Задача 3); реальный прогон
обеих задач и моделей на 6049-строчном датасете и приёмка (Задача 4). Результат: `home_win`
бьёт тривиальный baseline обеими моделями (Δ trivial−model = +0.0018 logreg / +0.0029 lgbm),
`status: ok`, `latest` выставлен acceptance-механизмом для обеих пар; `over_5_5` гейт не
проходит ни одной моделью (нет сигнала в имеющихся фичах — подтверждено спайком 40a).
Запас у `home_win` **маленький и статистически не значим** — 95% ДИ block-by-day bootstrap
разности (model − trivial) касается или включает 0 для обеих моделей; подробная таблица —
[`docs/modeling_training.md`](../docs/modeling_training.md) §8, карточка —
[`tasks/task_40_model_quality.md`](tasks/task_40_model_quality.md). 40d (новые источники
данных — стартовый вратарь, перелёты/часовые пояса, составы) не начата, требует решения
человека о новых данных.
