# ТЗ для агента-исполнителя: реализация сборки датасета NHL (train + predict)

**Роль:** инженер-исполнитель (implementation agent).  
**Цель:** реализовать production-grade сборку датасета для обучения и предикта строго по контракту из `plan/deprecated_plan/nhl_dataset_build_plan.md`.

---

## 1. Контекст и главный приоритет

Критически важно реализовать сборку датасета **без утечки и без расхождения train/predict схемы**.  
Все решения, которые повышают удобство, но снижают корректность, запрещены.

Базовый документ-источник требований: `plan/deprecated_plan/nhl_dataset_build_plan.md`.  
Если в ходе реализации обнаружены неоднозначности, агент:
1) фиксирует вопрос в отдельном разделе отчёта;
2) выбирает **наиболее безопасный** вариант;
3) не «додумывает» логику, которая может нарушить anti-leakage.

---

## 2. Обязательные функциональные результаты

Нужно получить полностью рабочий контур:

1. Сборка `train` датасета:
   - один матч = одна строка;
   - есть признаки и метки;
   - выдержан контракт `hist_day < target_day`.
2. Сборка `predict` датасета:
   - тот же `feature_set_version`;
   - те же признаки (имена, порядок, типы), но без `y_*`;
   - поддержка cold-start policy для инференса.
3. Валидация качества:
   - fail-fast при нарушениях контракта.
4. Метаданные и версионирование:
   - `features_hash`, `feature_set_version`, `code_version`, `data_snapshot_id`.
5. Автотесты:
   - anti-leakage, schema parity, data consistency.

---

## 3. Ограничения (нельзя нарушать)

1. Нельзя использовать статистику целевого матча в его фичах.
2. Нельзя использовать матчи с `day == target_day` как историю.
3. Нельзя дублировать логику фич отдельно для train и predict.
4. Нельзя silently исправлять несоответствия схемы (добавлением/удалением колонок «на лету»).
5. Нельзя отключать fail-fast проверки ради прохождения пайплайна.
6. Нельзя менять существующую логику бота вне необходимой интеграции CLI.

---

## 4. Требуемая структура реализации

Создать/доработать модули (названия допустимо адаптировать под проект, но смысл обязателен):

- `modeling/dataset_builder/base.py`
  - выборка матчей-кандидатов для `train`/`predict`;
  - единые фильтры валидности матчей.

- `modeling/dataset_builder/team_game_facts.py`
  - long-слой команда-матч;
  - симметричные поля `*_for`, `*_against`;
  - валидация «ровно 2 команды на матч» или controlled drop + лог.

- `modeling/dataset_builder/features.py`
  - rolling фичи по прошлым матчам;
  - эквивалент `shift(1)` обязателен;
  - контекстные фичи (`rest_days`, `is_b2b`, `games_last_7d`).

- `modeling/dataset_builder/assemble.py`
  - wide-склейка home/away;
  - сборка `train` с метками;
  - сборка `predict` без меток;
  - гарантированный порядок колонок согласно манифесту.

- `modeling/dataset_builder/validate.py`
  - полный набор checks из плана;
  - формирование `data_quality_report.json`;
  - fail-fast механика.

- `modeling/dataset_builder/schema.py` (или эквивалент)
  - манифест признаков;
  - вычисление `features_hash`;
  - проверки schema parity train/predict.

- CLI команда:
  - `python -m modeling.cli build-dataset --mode train ...`
  - `python -m modeling.cli build-dataset --mode predict ...`
  - опционально `--validate-only`.

---

## 5. Детальный алгоритм (обязательный порядок)

1. Подготовить `base_games`:
   - корректные `game_id`, `day`, `home_team_id`, `away_team_id`;
   - фильтрация `winner_id IS NOT NULL` для train, `winner_id IS NULL` для predict.
2. Построить `team_game_facts`:
   - две строки на матч (home/away), opponent stats через self-join по `game_id`.
3. Рассчитать rolling:
   - строго по `team_id, day, game_id`;
   - только прошлые игры (`hist_day < target_day`).
4. Построить wide:
   - home/away абсолютные, diff, sum фичи.
5. Для train собрать метки:
   - `y_home_win`, `y_over_5_5`.
6. Применить cold-start policy:
   - train: `drop`;
   - predict: `allow_with_flag` (или по конфигу).
7. Прогнать валидацию и сохранить отчёты.
8. Записать датасет и metadata артефакты.

---

## 6. Контракт входов/выходов

## 6.1 Входы

- параметры режима: `mode=train|predict`;
- диапазон дат / сезонов;
- `feature_set_version`;
- список окон rolling;
- cold-start policy;
- путь сохранения артефактов.

## 6.2 Выходы

- parquet/csv датасет:
  - `dataset_train_*` или `dataset_predict_*`;
- `metadata.json`:
  - `feature_set_version`, `features_hash`, `code_version`, `data_snapshot_id`, размеры срезов;
- `data_quality_report.json`:
  - результаты проверок, dropped rows, причины.

---

## 7. Обязательные тесты

Создать/обновить `tests/test_modeling_dataset_build.py` с минимумом:

1. `test_no_same_game_leakage`
2. `test_strict_past_only_by_day`
3. `test_train_predict_feature_parity`
4. `test_two_team_rows_or_drop`
5. `test_cold_start_policy`

Тесты должны быть детерминированы и запускаться локально без внешней нестабильности.

---

## 8. Чеклист self-review агента-исполнителя (перед сдачей)

Перед завершением задачи агент обязан проверить и отразить в отчёте:

1. Где именно обеспечен `hist_day < target_day`.
2. Где исключается текущий матч из rolling.
3. Где и как зафиксирован манифест признаков.
4. Как реализован fail-fast.
5. Какие случаи дропа матчей возникают и как логируются.
6. Что train/predict действительно строятся одним feature builder.

---

## 9. Формат отчёта о выполнении

В финальном отчёте агент-исполнитель обязан дать:

1. Список изменённых файлов.
2. Что реализовано в каждом файле (кратко и по делу).
3. Результаты тестов/проверок.
4. Список известных ограничений (если есть).
5. Явное заявление: выполнен ли anti-leakage контракт.

Если что-то не выполнено, отчёт должен прямо помечать статус `PARTIAL` и причины.

---

## 10. Критерии приёмки (Definition of Done)

Работа считается принятой только если:

1. `train` и `predict` датасеты собираются командами CLI.
2. Проверки качества включены и реально блокируют невалидные кейсы.
3. Все обязательные тесты проходят.
4. Schema parity train/predict подтверждена автоматически.
5. Сохранены metadata + quality report.
6. Никаких признаков утечки не выявлено тестами.

Если любой пункт не выполнен — задача не завершена.
