# ТЗ для агента-ревьюера: аудит реализации сборки датасета NHL (train + predict)

**Роль:** независимый reviewer agent.  
**Цель:** провести строгий технический аудит реализации из `plan/deprecated_plan/nhl_dataset_build_plan.md` и подтвердить, что датасетный контур корректен, воспроизводим и без leakage.

---

## 1. Принцип ревью

Ревьюер работает в режиме «сначала риски».  
Главная задача: найти ошибки, которые могут испортить качество модели/прод-прогнозов, даже если код «формально работает».

Приоритеты:
1. leakage;
2. несовпадение train/predict признаков;
3. ложная валидация качества;
4. проблемы воспроизводимости;
5. вторичные вопросы стиля/рефакторинга.

---

## 2. Что именно проверять (обязательный scope)

1. Соответствие реализации требованиям из:
   - `plan/deprecated_plan/nhl_dataset_build_plan.md`;
   - `plan/dataset_agents/agent_executor_dataset_tz.md`.
2. Корректность data contract:
   - train содержит метки;
   - predict без меток;
   - одинаковый набор фич (кроме y).
3. Корректность anti-leakage:
   - `hist_day < target_day`;
   - отсутствует использование текущего `game_id` в фичах.
4. Полнота quality checks:
   - не декоративные, а реально блокирующие пайплайн.
5. Полнота тестов:
   - покрытие критичных сценариев и edge cases.

---

## 3. Критические анти-паттерны (считать багом)

1. Использование `<= target_day` без intra-day timestamp.
2. Rolling без `shift(1)`/эквивалента.
3. Разные код-пути фич для train и predict с риском drift.
4. Тихая автоподгонка схемы перед инференсом.
5. Отсутствие явного сравнения `features_hash`.
6. Игнорирование неконсистентных матчей без отчётности.
7. «Зелёные тесты», которые не проверяют реальный leakage.

---

## 4. Пошаговый сценарий ревью

1. Проверить архитектуру модулей dataset builder.
2. Пройтись по коду сборки train:
   - источники, фильтры, labels, drop policy.
3. Пройтись по коду сборки predict:
   - выбор upcoming матчей, cold-start, запрет target leakage.
4. Сверить feature manifest:
   - имена, порядок, типы, hash.
5. Проверить validate слой:
   - какие ошибки блокируют run;
   - какие только логируются.
6. Запустить/проверить тесты:
   - обязательные и дополнительные.
7. Проверить артефакты:
   - metadata и data_quality_report.

---

## 5. Минимальные обязательные проверки ревьюера

## 5.1 Контракт времени

- Для случайной выборки матчей убедиться, что источники rolling фич только из дат `< target_day`.
- Отдельно проверить случаи матчей в соседние даты и в один день.

## 5.2 Контракт текущего матча

- Доказать, что статистика `target_game_id` не попадает в признаки этой же строки.

## 5.3 Контракт схемы

- Проверить автоматическую блокировку, если:
  - в predict отсутствует фича из train;
  - в predict есть лишняя фича;
  - порядок колонок изменён.

## 5.4 Контракт качества

- Проверить, что нарушения:
  - duplicate `game_id`,
  - NaN в обязательных полях,
  - некорректные диапазоны,
  - неконсистентность парности команд,
  реально приводят к FAIL.

## 5.5 Контракт воспроизводимости

- Проверить наличие и заполненность:
  - `feature_set_version`,
  - `features_hash`,
  - `code_version`,
  - `data_snapshot_id`.

---

## 6. Требования к качеству замечаний

Каждое замечание должно содержать:
1. Severity: `HIGH | MEDIUM | LOW`.
2. Риск для продукта.
3. Где найдено (файл/модуль/символ).
4. Почему это нарушение контракта.
5. Рекомендованное исправление.
6. Как проверить, что фикс корректен.

Запрещены «общие рекомендации» без привязки к коду/контракту.

---

## 7. Формат финального ревью-отчёта

Ревьюер обязан выдать отчёт в структуре:

1. **Findings (по убыванию severity)**
2. **Open questions / assumptions**
3. **Пройденные проверки**
4. **Непокрытые риски**
5. **Вердикт**
   - `APPROVE` / `REQUEST_CHANGES`
   - с чёткими условиями для approve.

Если критичные дефекты отсутствуют, явно указать: «Критичных проблем не найдено».

---

## 8. Блокирующие условия для `APPROVE`

`APPROVE` запрещён, если обнаружено хотя бы одно:

1. Любой подтверждённый leakage.
2. Отсутствие автоматической проверки schema parity.
3. Отсутствие fail-fast на ключевых quality checks.
4. Нет теста, проверяющего `hist_day < target_day`.
5. Нет подтверждения, что train/predict используют один feature builder.

---

## 9. Дополнительные проверки (рекомендуемые)

1. Edge-case: команды с очень малой историей.
2. Edge-case: пропуски отдельных статистик в `game_team_stats`.
3. Edge-case: матчи с аномальной структурой (1 или 3 строки team stats).
4. Regression-check на фиксированном fixture:
   - стабильность схемы и числа строк после изменений.

---

## 10. Definition of Done для ревьюера

Ревью завершено только если:

1. Выполнены все обязательные проверки из раздела 5.
2. Отчёт содержит приоритизированные findings или явное подтверждение их отсутствия.
3. Вынесен недвусмысленный вердикт (`APPROVE`/`REQUEST_CHANGES`).
4. Для каждого блокирующего пункта даны конкретные условия исправления.
