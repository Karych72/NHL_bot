# Задача 144. ИИ: меньше токенов на вопрос по статистике (ресёрч с замером)

**Блок:** продукт · **Надобность:** 🟡
**Область:** `telegram_bot/ai_stats.py` (`_system`, `_schema`, `_review`, `_dialog`),
`telegram_bot/prompts/*.md`, `scripts/ai_stats_eval.py`, итог —
`plan/ai_questions/stats_prompt_diet.md`.
**Зависит от:** 142 (какая часть стоимости — префикс, какая — выход), 143 (на какой модели
мерить). Можно начать и без них на Sonnet 5.5.
**Источник:** обсуждение развития ИИ 2026-11-16; реестр — [`../open_tasks.md`](../open_tasks.md).

## Кратко

Три правки, которые не меняют круг вопросов, но снижают расход на каждый: ревьюер читает кэш
отвечающего, схема базы в промпте становится компактной, ответ по готовой выборке идёт без
ревью. Каждая проверяется замером на контрольном наборе.

## Зачем и на что влияет

- Системный блок вопроса по статистике — промпт роли, аннотации и DDL шестнадцати таблиц:
  3,4 + 4,5 + 14,6 тысячи символов, по оценке 8–9 тысяч токенов. Он уходит в каждый вызов.
- У ревьюера свой системный промпт и свои инструменты, значит и свой кэш: его префикс
  записывается в кэш заново на каждом вопросе, а читается только если следующий вопрос пришёл
  в течение 5 минут.
- Расход на вопрос ограничивает число бесплатных вопросов и стоимость премиума.

## Степень важности

🟡: экономия заметная, но после 143 может оказаться несущественной в деньгах — тогда из трёх
правок остаются те, что улучшают ещё и скорость ответа.

## Подробно

**Текущее состояние (снимок 2026-11-16; строки сверять).**
- `_system(prompt_file)` (`ai_stats.py:209`) собирает блок из промпта роли, аннотаций и схемы;
  вызывается с `stats_answer.md` и `stats_reviewer.md` — два разных префикса.
- Порядок кэша в API: инструменты → системный блок → сообщения. Инструменты у отвечающего
  (`_tools`) и ревьюера (`_verdict_tools`) разные, поэтому кэш расходится с первого байта.
- `_schema()` (`ai_stats.py:192`) отдаёт DDL как есть: типы, `NOT NULL`, ключи, `CHECK`.
- `_dialog` отправляет на ревью каждый `finish` с `kind = answer`, в том числе когда все цифры
  пришли из `player_overview`, где запросы написаны нами.
- Сообщения диалога не кэшируются: результат SQL (до 20 000 символов) оплачивается полной
  ценой входа в каждом следующем вызове цикла.

**Что проверить (каждое — отдельный замер, отдельный PR, если прошло).**
1. **Общий префикс.** Один список инструментов и один системный блок для обоих вызовов; что
   делать — «отвечай» или «проверь черновик» — говорит сообщение пользователя. Ревьюер остаётся
   отдельным вызовом с чистой историей. Ожидание: запись кэша ревьюера заменяется чтением.
2. **Компактная схема.** `таблица(колонка тип, …)` и первичный ключ одной строкой вместо DDL;
   типы оставить только там, где они не очевидны (`text` у времени гола). Ожидание: схема
   короче в 2–3 раза. Риск — рост ошибок SQL: смотреть раздел попыток и ошибок в прогоне.
3. **Ревью только там, где есть SQL модели.** Ответ, собранный только из `player_overview`, —
   без вызова ревьюера. Решать по данным 142: если ревьюер правит такие ответы — правку не брать.
4. **Кэш хвоста диалога** (точка кэша на последнем сообщении): выгодно при трёх и более вызовах
   на вопрос, при двух — убыток. Брать, только если по 142 типичный вопрос длиннее двух вызовов.

**Критерии приёмки.**
- По каждой из четырёх правок — числа до и после на `make ai-stats-eval`: доля верных, неверные
  цифры после ревью, стоимость и токены на вопрос (вход, выход, запись и чтение кэша), ошибки SQL.
- Правка принимается, если качество не ниже порога набора (90% и ноль неверных цифр после
  ревью) и стоимость вопроса ниже. Не прошла — записано почему, код не вливается.
- Замер стоимости — в двух режимах: вопросы подряд (кэш тёплый) и каждый вопрос холодный.
- `docs/telegram_bot.md` и `docs/ai_capabilities.md` обновлены под принятые правки.
- `make ci-local` зелёный.

**Подводные камни.**
- Общий префикс делает инструмент `verdict` видимым отвечающему, а `run_sql` — ревьюеру. Роль
  задаёт сообщение; вызов не того инструмента — `_ProtocolError`, как сейчас. Проверить, что
  ревьюер не начинает выполнять SQL сам.
- Любой байт разницы в инструментах или системном блоке ломает общий кэш: порядок инструментов
  и текст — одни и те же объекты для обоих вызовов.
- Изменение промпта сбрасывает кэш у всех — на стоимости первых вопросов после выкатки это видно.
- `test_db_nhl.py` сверяет `AI_TABLES` с правами роли; компактная схема должна строиться из тех
  же `data_tables/t.*.sql`, а не из второго списка колонок (Global Constraint 2).
- Не вводить второй путь «на случай»: принятая правка заменяет старое поведение (Global Constraint 3).
