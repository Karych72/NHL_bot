# Задача 140. Бэкапы вне VM и проверка восстановления

**Блок:** релиз · **Надобность:** 🟠
**Область:** новые `scripts/backup_bucket_setup.sh` и `scripts/backup_restore_check.sh`,
`deploy/systemd/` (таймер выгрузки), `docker-compose.yml` (сервис `backup`), `DEVELOPMENT.md`
(§«Бэкап», §«Восстановление»).
**Зависит от:** ничего. После Задачи 139 дамп снимается с паролем — учесть, если она уже в
коде. Кандидат 7 Задачи 82 (права дампов) закрывается здесь.

## Кратко

Ежедневный дамп базы копируется в бакет Google Cloud Storage, а восстановление из бакета
проверяется скриптом.

## Зачем и на что влияет

- Дампы лежат в `/srv/nhl_bot_backups` на той же VM, что и база. Потеря диска или VM —
  потеря и базы, и всех бэкапов.
- Невосстановимое в базе — не статистика NHL (её можно перезагрузить из API), а подписки,
  расписания, платежи премиума, журналы вопросов ИИ и действий.
- Роли (`nhl_ai_reader`, после Задачи 139 — роли приложений) в `pg_dump -Fc` не попадают:
  восстановленная база сейчас не заработает без ручных шагов.
- Сбой бэкапа виден только в `docker compose ps`; никто не узнает.

## Степень важности

🟠: подтверждённый риск безвозвратной потери платежей и подписок.

## Подробно

**Текущее состояние (снимок 2026-11-16, `origin/develop` = `5a97128`).**
- Сервис `backup` (`docker-compose.yml:187-219`): раз в сутки `pg_dump -Fc postgres` в
  `/backups`, атомарная запись, ротация 14 дампов, healthcheck «есть дамп моложе 26 часов».
- Права дампов — `644` (кандидат 7 Задачи 82).
- На VM есть `gcloud` и сервисный аккаунт: ими пользуется `deploy/fetch-secrets.sh`.
- База `nhl_dev` не бэкапится — и не должна: её наполняют из продового дампа.

**Что делать.**
1. **Бакет.** `sh scripts/backup_bucket_setup.sh` с ноутбука: создаёт бакет в проекте
   `nhl-bot-prod`, включает правило жизненного цикла (удалять старше N дней, вопрос 1), выдаёт
   сервисному аккаунту VM право только создавать объекты (`roles/storage.objectCreator`).
   Повторный запуск безопасен.
2. **Выгрузка.** systemd-таймер на VM рядом с юнитом секретов: раз в сутки копирует самый
   свежий `nhl_*.dump` в бакет (`gcloud storage cp`) и падает с ненулевым кодом, если дампа
   моложе 26 часов нет.
3. **Роли.** Рядом с дампом сохранять `pg_dumpall --roles-only --no-role-passwords`; пароли
   после восстановления задаёт `scripts/db_passwords.sh` (Задача 139).
4. **Права.** Дампы на VM — `600`.
5. **Проверка восстановления.** `sh scripts/backup_restore_check.sh` с ноутбука: скачивает
   последний дамп из бакета на VM, восстанавливает во временную базу, сверяет с продом число строк в
   таблицах подписок, расписаний и платежей, удаляет временную базу. Печатает
   итог одной строкой.
6. **Документация:** `DEVELOPMENT.md` — где лежат бэкапы, как восстановиться из бакета на
   новой VM.

**Критерии приёмки.**
- В бакете появляется дамп не старше 26 часов; через N дней старые удаляются сами.
- Сервисный аккаунт VM не может удалить или перезаписать объект в бакете
  (`gcloud storage rm` с VM — отказ).
- `backup_restore_check.sh` проходит на проде и печатает совпадение счётчиков.
- Восстановление по `DEVELOPMENT.md` на чистую базу даёт рабочего бота (проверить на dev-стенде).
- `make ci-local` зелёный.

**Подводные камни.**
- В проекте принят долгоживущий контейнер вместо host cron (`DEVELOPMENT.md:36`). Здесь таймер
  на хосте оправдан: `gcloud` и учётные данные уже на хосте, а в образе `postgres:alpine` их
  нет. Альтернатива — отдельный образ с `gcloud` в compose; выбрать одно и записать причину.
- Право только на создание объектов защищает бэкапы при взломе VM, но не даёт VM скачать дамп
  для проверки — скрипту проверки нужен доступ на чтение с ноутбука либо отдельное право
  `objectViewer`.
- В дампе — персональные данные (chat_id, вопросы пользователей): бакет без публичного
  доступа, с единым доступом на уровне бакета.
- Временная база при проверке восстановления занимает место и память на VM (Задача 109 —
  память VM): проверять в тихое время.
- Стоимость: дамп небольшой, хранение N копий — центы в месяц; проверить фактический размер.
