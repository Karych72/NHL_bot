# Задача 37. Плей-офф: загрузка или честная оговорка

**Статус:** не начата · **Блок:** релиз+ · **Надобность:** 🟠 подтверждённый долг
**Область:** минимум — `telegram_bot/help_text.py`; полностью — `pipeline/`, `data_tables/` (миграция), `telegram_bot/`, `modeling/`.
**Порядок:** после релиза, в любом порядке с 38, 41, 42.
**Реестр:** [`../open_tasks.md`](../open_tasks.md), раздел «Релизный блок».

## Кратко

Загрузчик запрашивает только регулярный чемпионат: во всех фильтрах запросов к API стоит
`gameTypeId=2` (`pipeline/load_season_modern.py:266-717`, `:781`). В каждом сезоне ровно
1312 игр = 32 × 82 / 2. Плей-офф не загружен ни за один сезон, и бот об этом не сообщает —
продукт молча обрывается на последнем дне регулярки (2026-04-16 для 25/26). Два уровня:
сказать об этом в `/help` или загружать плей-офф по-настоящему.

## Зачем и на что влияет

- **Зачем.** С середины апреля до июня — самый интересный хоккей, а бот показывает
  «последний игровой день» месячной давности без объяснения. Минимум — честность,
  полный вариант — новая функциональность.
- **На что влияет.** Минимум — одна строка справки. Полный вариант — схема `games`
  (колонки типа игры нет: `game_id, day, home_team_id, away_team_id, winner_id,
  is_overtime, is_shootouts, season, season_id`), загрузчик (второй тип игр, отсутствие
  буллитов в плей-офф), турнирная таблица и лидеры (регулярка отдельно от плей-офф),
  датасет моделирования (плей-офф нельзя молча подмешивать в train), DB-тесты.
- **Если не делать.** Пользователь в мае решает, что бот сломан.

## Степень важности

🟠 **Подтверждённый долг, не блокирует октябрьский релиз:** плей-офф начинается в апреле.
Минимальный вариант — час работы, его стоит сделать окном до релиза; полный — отдельная
задача после релиза, заведомо больше бюджета в 300 строк (Global Constraint 6).

## Подробно

### Текущее состояние (сверено 2026-09-22)

- Живая БД: 20212022–20252026 по 1312 игр, последние дни `2022-05-01`, `2023-04-14`,
  `2024-04-18`, `2025-04-17`, `2026-04-16` (2021/22 длиннее из-за переносов). Ни один
  тест не завязан на число 1312.
- `help_text.py`: `_COMMAND_LINES` описывает команды; про охват данных («регулярный
  чемпионат») нигде не сказано.
- Агрегатные эндпоинты (`teams_stats`, `players_season_stats`, `goalies_season_stats`)
  тоже берутся с `gameTypeId=2` — в NHL API это отдельные наборы для регулярки и плей-офф.

### Что нужно сделать — минимум

1. В `/help` (и, возможно, `/start`) одна фраза: данные охватывают регулярный чемпионат;
   матчи плей-офф в базе не отражены.
2. Тест на текст справки, если такие тесты есть (`tests/test_bot_*`), иначе — ручная проверка.

### Что нужно сделать — полностью: подзадачи 37A → 37B → 37C → 37D

Разбивка сделана 2026-09-29 по карте точек касания (`origin/master` = `7fdbd6b`; строки —
снимок, сверять). Порядок строгий: сначала схема и фильтры потребителей, потом данные,
потом показ. Так плей-офф-строки ни на один день не попадают в форму, серии, H2H и train.
Каждая подзадача — отдельная сессия и отдельный PR, каждая укладывается в бюджет 300 строк.

**Решение по агрегатам (принято при разбивке, пересматриваемо):** сезонные агрегаты
(`teams_stats`, `players_season_stats`, `goalies_season_stats`, `players_advanced_stats`,
`players_shot_types`, 11 URL с `gameTypeId=2` в `load_season_modern.py:266–717`) за
плей-офф **не загружаются**. Их PK — `(…, season_id)` без типа игры: строки плей-офф
перезаписали бы регулярку. `/table`, `/leaders`, `/advanced`, профиль команды остаются
регуляркой без правок. Статистика игроков за плей-офф — отдельная задача, если понадобится.

#### 37A. Схема: `games.game_type`

- Миграция `data_tables/migrations/0003_games_game_type.{up,down}.sql` по образцу 0002:
  `ALTER TABLE games ADD COLUMN IF NOT EXISTS game_type smallint`, бэкфилл `2` всем
  существующим строкам, затем `NOT NULL` и `CHECK (game_type IN (2, 3))`. Без BEGIN/COMMIT
  (миграции идут `--single-transaction`).
- Парный DDL `data_tables/t.games.sql` — то же определение колонки (правило синхрона,
  `DEVELOPMENT.md`); индекс не нужен, пока нет запроса, который им пользуется.
- Загрузчик пишет `game_type` из `gameType` мета-записи игры (`build_game_rows`,
  `load_season_modern.py:824+`); фильтр по-прежнему только `gameType=2`, так что данные
  не меняются.
- Тесты: схема в `tests/test_db_nhl.py` (колонка есть, NOT NULL, CHECK); в
  `test_pipeline_game_rows.py` — строка игры несёт `game_type = 2`.
- Приёмка: `make db-migrate` на живой БД; `SELECT game_type, count(*) FROM games GROUP BY 1`
  → одна группа `2`, 6560 строк; `make all-tests` зелёный.

#### 37B. Потребители `games` считают только регулярку

Фильтр `g.game_type = 2` туда, где плей-офф исказил бы смысл:
- `telegram_bot/bot_messages.py`: `_recent_team_outcomes` (:488, форма W–L–OTL и серия),
  `_h2h_season_wins` (:587), `_standings_as_of_day` (:1035, дата «по состоянию на» у таблицы
  из регулярки).
- `modeling/dataset_builder/base.py`: `load_target_games` (:87) и `load_history_team_stats`
  (:120) — train, predict и rolling-фичи только по регулярке; строку в
  `_compose_data_snapshot_id` обновить, чтобы снимок данных отражал фильтр.
- Не трогать: `day_digest`, `game_message`, `push_digest_job` — они про конкретные дни и
  матчи и должны показывать плей-офф (37D).
- Тесты: на каждый фильтр — сценарий с игрой `game_type = 3` в фикстуре, которая не должна
  попасть в результат (форма, H2H, дата таблицы, датасет).
- Приёмка: `make ci-local`; `build-dataset` на живой БД даёт те же 6049 строк, что до
  задачи (плей-офф в БД ещё нет — фильтр ничего не меняет).

#### 37C. Загрузчик: игры плей-офф

- `fetch_final_games` (`load_season_modern.py:779–785`): `gameType in (2,3)` вместо
  `gameType=2`; `game_type` берётся из записи. Пер-игровые эндпоинты (`/v1/gamecenter/…`)
  от типа не зависят, кэш `all_data/raw/` по `game_id` — тоже.
- Проверить на реальном пейлоаде: `is_overtime` (`:863`, `number > 3` ловит OT2+),
  `is_shootouts` (`:868`, в плей-офф всегда false), `winner` (`:856`).
- Фикстура плей-офф-игры (включая многоовертаймовую, если есть в сезоне 24/25 или 25/26):
  параметризовать `scripts/capture_nhl_fixtures.py` (сейчас `GAME_ID` и `gameTypeId=2`
  зашиты, `:35–80`), снять `boxscore`/`landing`/`play-by-play` и мета-запись; тест в
  `test_pipeline_game_rows.py`.
- `pipeline/scheduled_sync.py` правок не требует (окно по датам, тип не фильтрует) —
  подтвердить тестом или прогоном.
- Дозагрузка плей-офф за 5 сезонов в живую БД (`season-load-full` или `--date-from` по
  сезонам, `PG_USER=postgres`), перед этим — дамп БД.
- Приёмка (исходная приёмка Задачи 37 «полностью»): `SELECT game_type, count(*) FROM games
  WHERE season_id = … GROUP BY 1` → две группы по каждому сезону; счётчик сезона ≠ 1312;
  `make test-db-data` зелёный; `build-dataset` по-прежнему 6049 строк.

#### 37D. Бот показывает плей-офф и снимает оговорку

- Пометка плей-офф в дайджесте дня (`day_digest`, `bot_messages.py:1621`) и в карточке
  матча (`game_message`, `:178`): «Плей-офф, раунд R, игра G». Раунд, серия и номер игры
  читаются из `game_id` (`2025030123` → тип 03, раунд 1, серия 2, игра 3) — без нового
  API-запроса и без новой колонки. Счёт серии — вне задачи (нужен `seriesStatus`).
- `/tonight` уже читает live-скорборд без фильтра типа (`nhl_scoreboard.py`) — проверить
  на `score_now_sample` с плей-офф-игрой, правка только если пометки нет.
- Уведомления подписки на команду (`push_digest_job.py:50`) — плей-офф приходит как есть,
  с той же пометкой.
- Убрать оговорку из `START_MESSAGE` (`help_text.py:6`) и её тест
  (`test_skater_reports_bot.py:99`); в `/help` вместо неё — одна строка о том, что таблица и
  лидеры считают регулярный чемпионат, а матчи дня и карточки включают плей-офф.
- `docs/architecture.md` / `docs/data_loading.md:293` — отметить тип игры и решение по
  агрегатам.
- Приёмка: в живом боте карточка плей-офф-матча несёт пометку раунда; `/help` не
  утверждает, что плей-офф нет; `make ci-local`. Закрытие 37D закрывает Задачу 37 (✅).

### Критерии приёмки (из реестра)

- Минимум: в `/help` сказано, что данные охватывают регулярный чемпионат.
- Полностью: игры плей-офф загружаются и отличимы от регулярки в БД; счётчик игр сезона
  перестаёт быть ровно 1312; `make test-db-data` зелёный.

### Проверка

- Минимум: `/help` в живом боте содержит оговорку; `make ci-local`.
- Полностью: `SELECT <тип>, count(*) FROM games WHERE season_id = … GROUP BY 1` даёт
  две группы; `make all-tests`.

### Подводные камни

- Плей-офф-игры ссылаются на те же `teams (team_id, season_id)` — FK не ломаются, но
  ростеры к плей-офф меняются: для карточек не проблема, для агрегатов — да.
- Сначала минимум: оговорка в `/help` остаётся верной до конца полной задачи и уходит
  вместе с ней, а не живёт рядом с новой функцией.
