## Кратко

Задача 80 нашла утечку: `httpx` на уровне INFO пишет URL каждого запроса к Telegram, а в URL
Bot API — токен бота. Токены прода и dev-бота лежали в логах docker на диске VM (1351 строка
у прода на 2026-10-25), хотя сам токен специально держится только в RAM (`/run`, Задача 65).
Исправлено в `bot.py` и `push_digest_job.py` (логгер `httpx` → WARNING), но это один
случай одного класса. Задача — систематически пройти стек на подобные проблемы, проверить
кандидатов ниже и решить по каждому: исправить (отдельной задачей), принять риск или снять.

## Зачем и на что влияет

- Токен бота = полный контроль над ботом: рассылка от его имени всем подписчикам, чтение
  входящих. Ключ Anthropic (81) = деньги.
- Утечка нашлась случайно, при разборе упавшего деплоя. Другие такие же никто не ищет.
- С Задачи 80 на VM два стека, и dev-ветка проходит меньше проверок, чем прод.

## Найдено при заведении (кандидаты, проверить и решить)

Предварительный осмотр 2026-10-25, не исчерпывающий — исследование его дополняет.

**Секреты в логах и выводе**
1. ✅ исправлено (2026-10-25): URL с токеном от `httpx` INFO. Осталось: перезапуск контейнеров
   прода после релиза (старые логи уходят вместе с контейнером), решить о ротации продового токена.
2. PTB при неверном токене бросает `InvalidToken` с токеном в тексте (`The token `…` was
   rejected`) — попадает в лог трейсбэком. Видели вживую на dev-боте.
3. Сообщения сетевых ошибок `httpx`/PTB могут содержать URL запроса: `logger.warning(..., exc)`
   в `push_digest_job.py` (строки рассылок) печатает исключение целиком. Проверить, что в нём.
4. `scheduled_sync.py` логирует argv дочерних команд (`Running: ...`) — проверить, что в
   argv нет секретов ни сейчас, ни после 81.
5. Токены побывали в выводе команд агента (транскрипты Claude Code локально у человека,
   `~/.claude/projects/`). Токен dev-бота — ротировать (`/revoke` в BotFather).

**Хранение на VM**
6. Логи docker: драйвер `json-file` без ротации (`/etc/docker/daemon.json` нет) — что бы ни
   утекло в лог, хранится бессрочно и растёт без предела. Решить: `max-size`/`max-file`.
7. Бэкапы `/srv/nhl_bot_backups/*.dump` — права `644` (читает любой пользователь VM), без
   шифрования; в них `bot_subscriptions` с `chat_id` пользователей.
8. `/opt/nhl_bot_dev/.env` — копия продового `.env` (тот же ключ Anthropic и прочее, Задача 80).
   Проверить, что в нём нет того, что dev видеть не должен.

**Доступ к базе**
9. Postgres с `POSTGRES_HOST_AUTH_METHOD: trust`: порт опубликован только на `127.0.0.1`,
   но любой контейнер сети `nhl_bot_default` входит суперпользователем без пароля. С Задачи 80
   туда подключён dev-стек: код ветки `develop` имеет полный доступ к продовой базе `postgres`,
   а не только к `nhl_dev`. Вариант — отдельная роль dev с правами только на `nhl_dev`.
10. Пользователь `deploy` в группе `docker` = фактически root на VM; ключ деплоя — в секретах
    GitHub (`DEPLOY_SSH_KEY`). Оценить, чем грозит компрометация GitHub-аккаунта или Actions.

**CI/CD и цепочка поставки**
11. Actions подключены по тегам (`actions/checkout@v4`, `docker/build-push-action@v6`), не по
    SHA — подмена тега стороннего action исполняется с правом `packages: write` и ключом деплоя.
12. Деплой dev-стека — на каждый пуш в `develop`; ветка защищена (PR + зелёный CI), проверить,
    что из форков и чужих PR секреты окружения `production` недоступны.
13. Зависимости приложения — с хэшами (`requirements.txt`); нет автоматической проверки CVE
    (Dependabot / `pip-audit`).

**Сеть VM**
14. Правило `default-allow-rdp` (`tcp:3389` с `0.0.0.0/0`) — на Linux VM не нужно; SSH открыт
    миру (ключи, пароли и root запрещены — `sshd -T`). Порт `5355` (LLMNR) слушает `0.0.0.0`,
    снаружи закрыт файрволом.

**Бот и ИИ (с Задачи 81)**
15. Ввод пользователя: SQL — параметризован (f-строк в `execute` не найдено), повторно проверить
    с новыми запросами. Prompt injection в 81 ограничен инструментами со `strict`/`enum`,
    стоимость — лимитом вопросов; проверить, что текст пользователя не попадает в логи с ключом.
16. Персональные данные: `chat_id` в логах рассылок (`push_digest_job.py`) и в таблицах — что
    из этого нужно хранить и сколько.
