# Задача 33. Переход на сезон 2026/27

**Статус:** 🟨 кодовая часть выполнена (ветка `sdd-task-33-season`, PR #36); открыта до шага 6 — загрузки сезона 2026/27 после первых игр · **Блок:** релиз · **Надобность:** 🔴 блокирует релиз
**Область:** `.env.example`, `telegram_bot/config.py`, `Makefile`; попутно `README.md`, `docs/architecture.md`.
**Порядок:** первая в релизном блоке; от неё зависят 34 и 36.
**Реестр:** [`../open_tasks.md`](../open_tasks.md), раздел «Релизный блок».

## Кратко

Идентификатор сезона задан в нескольких независимых местах, и все дефолты — прошлого
сезона 2025/26. В БД пять полных сезонов (20212022–20252026), последний игровой день —
2026-04-16; за 2026/27 нет ни строки. Нужно свести сезон к одному источнику, убрать старые
дефолты и загрузить новый сезон после первых игр.

## Зачем и на что влияет

- **Зачем.** Сезон 2026/27 стартует в начале октября. Бот фильтрует все экраны по
  `config.SEASON_ID` (таблица, лидеры, дайджест, подписки, `/team`); загрузчик берёт
  `SEASON_ID`/`CURRENT_SEASON` из того же конфига (`pipeline/load_season_modern.py:195-196`);
  `make season-load-full` начинает с `SEASON_START`. Пока значения разъезжаются, любая
  точка может тихо остаться на 2025/26: бот покажет «текущим» прошлый сезон, а загрузчик
  перезальёт старый.
- **На что влияет.** Конфиг бота и пайплайна, Makefile, документация. Косвенно — Задача 34
  (расписанию нужна верная конфигурация сезона), Задача 36 (первые недели бот живёт на почти
  пустом сезоне), трек B (`build-dataset --season-ids` для predict-датасета).
- **Если не делать.** В октябре бот отвечает данными прошлого сезона; автообновление (34)
  настраивать не на что.

## Степень важности

🔴 **Блокирует релиз.** Без работающей конфигурации сезона релиз статистического бота
невозможен, а дата жёсткая — начало октября 2026. Первая задача релизного блока
(33 → 34 → 35 → 36).

## Подробно

### Текущее состояние (сверено 2026-09-22)

| Где | Что зашито |
|---|---|
| `.env.example:13-15` | `SEASON=20252026`, `SEASON_ID=20252026`, `CURRENT_SEASON=25/26`. Переменную `SEASON` не читает ни один модуль — мёртвая |
| `telegram_bot/config.py:67-70` | дефолты `DATE_FROM="2025-10-01"`, `SEASON_ID=20252026`, `CURRENT_SEASON="25/26"` |
| `Makefile:50` | `SEASON_START ?= 2025-10-01` — используется `season-load-full` |
| `README.md:52, 114-115` | примеры команд с `2025-10-01`, `20252026`, `"25/26"` |
| `docs/architecture.md` §Конфигурация | таблица дефолтов повторяет `config.py` |

Реестр насчитывает четыре места; при сверке нашлось пятое — дефолт `DATE_FROM` в
`config.py:67`, он тоже привязан к сезону. Живая БД: сезоны 20212022–20252026 по 1312 игр,
первые игровые дни 2021-10-12 / 2022-10-07 / 2023-10-10 / 2024-10-04 / 2025-10-07 — дата
старта каждый год своя.

`config.validate_env()` проверяет только токен и `PG_*`; у сезонных переменных есть
дефолты, поэтому их отсутствие в `.env` ничем не выдаётся.

### Что нужно сделать

1. **Один источник.** Рекомендация — в `.env` остаётся только `SEASON_ID`; `CURRENT_SEASON`
   («26/27») и стартовая дата окна для `season-load-full` выводятся из него в `config.py`
   (окно с 1 сентября шире реального старта, но безвредно: фильтр по сезону и типу игры стоит
   в самом запросе к API, `load_season_modern.py:781`; проверить, что лишние пустые дни не
   превращаются в лишние запросы). Если вывод кажется слишком хитрым — допустимо три явные
   переменные в `.env`, но тогда ни у одной нет дефолта в коде.
2. **Без дефолтов в коде.** Отсутствие `SEASON_ID` валит старт так же, как отсутствие токена:
   расширить `validate_env()` или проверять при чтении, с именем переменной в сообщении.
3. **Убрать старое, не оставляя рядом** (Global Constraint 3): дефолты в `config.py:67-70`,
   `SEASON_START ?= 2025-10-01` в Makefile (он и так делает `include .env` + `export`),
   мёртвую `SEASON` из `.env.example`.
4. **Документация тем же коммитом:** таблица переменных в `docs/architecture.md`, примеры
   в `README.md`, при необходимости `DEVELOPMENT.md`.
5. **Тесты:** старт без `SEASON_ID` падает с именем переменной (по образцу тестов
   `validate_env`); тесты, где сезон подразумевался через дефолт, задают его явно.
6. **Загрузка сезона 2026/27** — после первых сыгранных игр: `SEASON_ID=20262027` в `.env`,
   `make season-load-full`, проверка `SELECT count(*) FROM games WHERE season_id = 20262027`.

### Критерии приёмки (из реестра)

- Сезон задаётся в одном месте, остальные читают оттуда.
- Сезон 2026/27 загружен в БД после первых игр.
- Старые дефолты удалены, а не оставлены рядом с новыми.
- `make ci-local` зелёный.

### Проверка

- `make ci-local`.
- `grep -rn "20252026\|2025-10-01\|25/26" --include=*.py --include=Makefile --include=.env.example .`
  — совпадения только в тестах и истории планов.
- Живая БД: строка `20262027` в `SELECT season_id, count(*) FROM games GROUP BY 1`.

### Подводные камни

- **Пустой сезон до первых игр.** Переключать `.env` на 20262027 в день первых игр или
  после: иначе бот несколько дней показывает пустые экраны. Их поведение фиксирует
  Задача 36, но окно лучше не создавать самим.
- **Порядок загрузки нового сезона.** `teams` имеет PK `(team_id, season_id)`, на него
  ссылаются FK из `games` и `rosters`. Первый прогон для 20262027 должен создать команды
  сезона раньше игр — проверить реальным прогоном, а не по коду.
- **Кэш сырых ответов** (Задача 31) ключуется по `game_id` — новый сезон его не путает,
  но каталог кэша растёт.
- Задача 34 читает ту же конфигурацию — 33 делать первой.
