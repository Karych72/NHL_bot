# Задача 108. Расписания: ИИ разбирает текст → карточка-черновик с кнопками

**Блок:** продукт · **Надобность:** 🟡 (после 107)
**Область:** `telegram_bot/ai_router.py` (инструмент `schedule_screen`, `SYSTEM_PROMPT`),
`telegram_bot/bot.py` (карточка, callback `sch:…`, сохранение), `telegram_bot/schedule_repo.py`
(из 107), `scripts/ai_router_eval.jsonl`, тесты `tests/test_bot_ai_router.py`,
`tests/test_bot_schedules.py`, `docs/architecture.md`, `docs/telegram_bot.md`.
**Зависит от:** 107 (таблица, `next_run_at`, рендер по `chat_id`, лимит).
**Источник:** обсуждение с человеком 2026-11-01; реестр — [`../open_tasks.md`](../open_tasks.md).

## Кратко

Пользователь пишет обычным текстом: «присылай лидеров по голам каждую пятницу в 10», «профиль
BOS раз в месяц 1-го числа», «процент отражённых каждый день в 9 по Екатеринбургу». ИИ только
распознаёт, какой экран бота и какое расписание нужны, — бот показывает карточку-черновик,
где всё понятое уже выбрано, а недостающее и неверное правится 1–2 нажатиями. «✅ Сохранить» —
расписание из 107.

## Зачем и на что влияет

- **Быстро и недолго** — главное требование человека. Текстом задаётся всё сразу, кнопками —
  только правка; ввод времени и пояса руками не нужен.
- **ИИ не пишет отчёт и не выдумывает экраны.** Параметры инструмента — те же `enum`, что у
  инструментов-экранов 81: несуществующую команду или метрику модель выбрать не может.
- Разбор текста — обычный вопрос к ИИ и считается в лимит `ai_router.limit_refusal`.

## Степень важности

🟡: без 108 расписание создаётся только SQL-ом; вместе с 107 — законченная фича.

## Подробно

**Состояние на 2026-11-01** (`origin/develop` = `af7e561`): `ai_router.build_tools` — строгие
схемы экранов с `enum` (`bot.py:564` `AI_SCREENS`); `on_free_text` (`bot.py`) выбирает экран или
текст модели. Бот без FSM: всё состояние кнопки — в `callback_data` (≤ 64 байт), сообщение
правится `edit_text` (как `/subscriptions`, `sub:…`).

**Карточка (решение человека 2026-11-01):**

```
⏰ Новое расписание
Экран:   Лидеры · голы
Частота: [День] [•Неделя] [Месяц]
Когда:   [Пн][Вт][Ср][Чт][•Пт][Сб][Вс]
Время:   10:00  [−1ч] [+1ч] [:00/:30]
Пояс:    Москва (UTC+3)  [Сменить]
[✅ Сохранить]  [✖ Отмена]
```

- Ряд «Когда» зависит от частоты: день — нет ряда; неделя — дни недели; месяц — числа 1–28 и
  «последний» (две-три строки кнопок).
- Время — шаг 30 минут; «в 10:17» модель округляет до ближайшего слота, карточка показывает итог.
- Пояс по умолчанию — пояс последнего расписания чата, иначе МСК. «Сменить» — 9 поясов РФ
  (Калининград … Владивосток) кнопками; другой город — текстом, модель переводит в IANA-зону
  (`America/New_York`), бот проверяет её `zoneinfo` до показа карточки.
- Не распознанное модель оставляет пустым — поле подсвечено «выбрать», «Сохранить» скрыт, пока
  не заполнено всё. Экран модель не угадала — ответ «не понял, какой экран» с примерами, без карточки.
- Подсказка в подвале: ночь догружается до 11:00 МСК, раньше экран может прийти без последних матчей.

**Что делать.**

1. **Инструмент `schedule_screen`** в `build_tools`: `screen` + его параметры (повторно
   использовать схемы инструментов-экранов, без копии `enum`), `freq`, `weekday`, `month_day`,
   `time` (`HH:MM`), `timezone` (IANA) — необязательные, кроме `screen`. `SYSTEM_PROMPT`: «просьба
   присылать регулярно / по расписанию / каждый день … → `schedule_screen`». Набор экранов — словарь
   допустимых для расписания из 107.
2. **Состояние карточки в `callback_data`.** Черновик кодируется компактно: `sch:<draft>` где
   draft — экран и параметры, частота, день, слот времени (0–47), индекс пояса. Если экран с
   параметрами не помещается в 64 байта — черновик кладётся строкой в `bot_schedules` с
   `active = false` и кнопки несут его `id`; выбрать один способ при реализации, проверив
   самый длинный экран, и записать решение в docstring.
3. **Сохранение.** Повторная проверка лимита 107 (бесплатным — 1 активное) в момент нажатия:
   превышение — отказ со ссылкой на `/premium`, черновик остаётся. Успех — карточка меняется на
   «Готово: <экран> — по пятницам 10:00 (МСК), список — /subscriptions».
4. **Журнал (99):** `schedule_created`.
5. **Eval.** В `scripts/ai_router_eval.jsonl` — 8–10 фраз: каждая частота, пояс городом, время с
   минутами, не распознанный экран, просьба без расписания («покажи лидеров» → экран, не расписание).
6. **Документация:** `docs/architecture.md` (§ai_router — инструмент `schedule_screen`, карточка
   `sch:`), `docs/telegram_bot.md`.

**Не входит:** редактирование сохранённого; создание кнопкой под экранами; минуты вне сетки 30.

**Критерии приёмки.**
- `tests/test_bot_ai_router.py`: схема `schedule_screen` строгая, `enum` экранов совпадает с
  набором 107.
- `tests/test_bot_schedules.py` через `Dispatcher.feed_update`: смена частоты перерисовывает ряд
  «Когда»; ±1ч и :00/:30 по кругу суток; «Сохранить» скрыт при пустом поле; сохранение пишет
  строку с верным `next_run_at`; бесплатный чат со вторым расписанием получает отказ; самый
  длинный `callback_data` ≤ 64 байт.
- `make ai-eval` против API на новых фразах — прогнать и записать результат в отчёт.
- Живая проверка на dev-боте: три фразы из «Кратко» дают верные карточки, правка в 1–2 нажатия,
  расписание приходит в срок.
- `make ci-local` зелёный; pytest с `PG_PORT=1`, как в CI.

**Подводные камни.**
- Смена текста `SYSTEM_PROMPT` и инструментов один раз сбрасывает кэш префикса — ожидаемо.
- Окно продолжения диалога 83 (30 минут после ответа по статистике) перехватывает текст до
  маршрутизатора — просьба о расписании в это окно должна всё равно доходить до `schedule_screen`;
  проверить и закрыть тестом.
- Бюджет GC6: оценка ~250 строк с тестами.
