# Задача 139. Пароли в Postgres: dev-стенд без доступа к продовой базе

**Блок:** релиз · **Надобность:** 🟠
**Область:** новый `scripts/db_passwords.sh`, `deploy/compose.prod.yml`, `deploy/compose.dev.yml`,
`docker-compose.yml` (`db`, `backup`), `deploy/systemd/` (юнит секретов), `pg_hba.conf` в томе
`pgdata`, `data_tables/ai_reader_grants.sql`, `DEVELOPMENT.md`, `docs/security.md` (если уже
заведён Задачей 82).
**Зависит от:** ничего. Кандидат 9 Задачи 82 (`trust` в Postgres) закрывается этой задачей.
**Источник:** ревизия качества кода 2026-11-16, просьба человека завести задачу и продумать ввод
пароля; реестр — [`../open_tasks.md`](../open_tasks.md).

## Кратко

Сетевые подключения к Postgres начинают требовать пароль. Dev-стенд получает собственную роль
без прав суперпользователя, которой доступна только база `nhl_dev`. Пароли задаются одним
скриптом с ноутбука и ни разу не появляются на экране, в аргументах команд и в `.env`.

## Зачем и на что влияет

- Dev-стек подключён к сети прод-стека и ходит в тот же Postgres пользователем `postgres` без
  пароля. Разделение `nhl_dev` и `postgres` — только по имени базы в конфиге.
- Каждый пуш в `develop` сам выкатывает на VM код, которому физически доступна продовая база:
  ошибка в миграции или в строке подключения на dev-ветке меняет прод.
- Утверждение `DEVELOPMENT.md:84` «`trust` допустим, пока порт на loopback» не учитывает сеть
  docker.

## Степень важности

🟠: подтверждённый риск потери или порчи продовых данных; срабатывает от обычной ошибки, а не от
атаки.

## Подробно

**Текущее состояние (снимок 2026-11-16, `origin/develop` = `5a97128`).**
- `docker-compose.yml:19` — `POSTGRES_HOST_AUTH_METHOD: trust`; порт `127.0.0.1:5432`.
- `deploy/compose.dev.yml` — сервисы `migrate`, `bot`, `sync`, `predict` dev-стека в сети
  `nhl_bot_default`, `PG_DATABASE: nhl_dev`, пользователь — `postgres`.
- Роль `nhl_ai_reader` (только чтение, text-to-SQL) тоже без пароля (`DEVELOPMENT.md:282`).
- Секреты уже доставляются так: Secret Manager → `deploy/fetch-secrets.sh` при загрузке VM →
  файл в `/run/nhl_bot*/` → compose secret → обёртка entrypoint (`deploy/compose.prod.yml`).
  Пароли БД идут тем же путём.

**Как вводится пароль.** Один скрипт с ноутбука: `sh scripts/db_passwords.sh`.
1. Для каждой роли скрипт спрашивает пароль **без эха** (`stty -echo`; `read` из `/dev/tty`).
   Пустой ввод — скрипт сам генерирует пароль (`openssl rand -base64 32`), и человеку его знать
   не нужно. Для запуска без терминала — переменные окружения `PG_PASS_PROD`, `PG_PASS_DEV`,
   `PG_PASS_AI`.
2. Пароль уходит в Secret Manager через stdin: `gcloud secrets versions add <секрет>
   --data-file=-`. В аргументы команды он не попадает — значит, его нет в `ps` и в истории
   shell. На VM пароль с ноутбука не передаётся вовсе.
3. Дальше скрипт через `gcloud compute ssh … --command 'sh -s'` (как `scripts/set_channel.sh`)
   на VM: вызывает `fetch-secrets.sh` для новых секретов, читает пароль из файла и выполняет
   `ALTER ROLE … PASSWORD` через stdin `psql`, затем перезапускает стеки.
4. Скрипт ничего из паролей не печатает; в конце — только проверка: подключение с паролем
   проходит, без пароля — отклоняется.
5. Повторный запуск — это ротация: новая версия секрета, `ALTER ROLE`, перезапуск.

**Что делать.**
1. **Роли.** `nhl_dev_app` — владелец базы `nhl_dev`, без `SUPERUSER`, `CREATEDB`,
   `CREATEROLE`; `CONNECT` к базе `postgres` у неё отозван. Прод остаётся на `postgres` (или
   получает свою роль — вопрос 1). `nhl_ai_reader` получает пароль.
2. **`pg_hba.conf`:** для сетевых подключений (`host`) — `scram-sha-256`; локальный сокет
   внутри контейнера `db` остаётся `trust` для `docker compose exec db psql`. Переменная
   `POSTGRES_HOST_AUTH_METHOD` действует только при первом создании кластера, поэтому на
   существующем томе файл правит скрипт, затем `pg_reload_conf()`.
3. **Доставка в контейнеры.** Compose secret с файлом в формате `.pgpass` и переменная
   `PGPASSFILE` у сервисов. Её понимают `psycopg2`, `psql` (миграции) и `pg_dump` (бэкап), так
   что код приложения не меняется. Пароль роли ИИ — отдельный секрет только у `bot`.
4. **`compose.dev.yml`:** `PG_USER: nhl_dev_app`; `compose.prod.yml` и `backup` — свой secret.
5. **Юнит секретов** на VM — добавить новые секреты в загрузку при старте.
6. **Документация:** `DEVELOPMENT.md` (§«Dev-стенд», §«Прод-деплой», абзац про `trust`),
   решение по кандидату 9 — в `docs/security.md`.

**Критерии приёмки.**
- Из контейнера dev-стека `psql -h db -U nhl_dev_app -d postgres` отклоняется; `-d nhl_dev` —
  проходит.
- Из любого контейнера `psql -h db -U postgres` без пароля отклоняется.
- Оба бота, `sync`, миграции, бэкап и ответы ИИ работают после перезапуска VM (секреты
  подтягиваются сами).
- `grep -rn "trust" docker-compose.yml deploy/` — только строка локального сокета или CI.
- Пароля нет в выводе скрипта, в `.env`, в `docker inspect`, в логах Postgres.
- `make ci-local` зелёный; CI-джоб `db-tests` продолжает работать (у него свой `trust`).

**Подводные камни.**
- **Порядок на живой базе:** сначала пароли ролям и секреты в контейнеры, потом переключение
  `pg_hba.conf`. Наоборот — оба бота теряют базу до конца скрипта. Скрипт должен уметь
  откатить `pg_hba.conf` одной командой.
- `.pgpass` игнорируется, если права шире `0600` или владелец не совпадает с пользователем
  процесса; compose secret монтируется с правами файла на хосте — проверить под non-root
  пользователем образа.
- `ALTER ROLE … PASSWORD` попадает в лог Postgres при `log_statement = ddl` или `all` —
  убедиться, что на проде стоит `none` (значение по умолчанию).
- Объекты в `nhl_dev` сейчас принадлежат `postgres`: нужен `REASSIGN OWNED` или
  `ALTER … OWNER` на базу, схему и таблицы, иначе миграции dev упадут.
- Локальная разработка (`docker compose up` на ноутбуке) остаётся на `trust` — базовый
  `docker-compose.yml` не усложнять, пароли живут в `deploy/compose.*.yml`.
- Восстановление `nhl_dev` из продового дампа (`DEVELOPMENT.md:189-191`) делается от
  `postgres` с `--no-owner` — после задачи добавить `--role=nhl_dev_app`.

## Открытые вопросы человеку

1. **Продовая роль.** Оставить приложение прода на суперпользователе `postgres` с паролем
   (по умолчанию, меньше правок) или завести `nhl_app` без прав суперпользователя?
2. **Ввод пароля.** По умолчанию — запрос без эха с автогенерацией на пустой ввод. Если
   удобнее всегда вводить свой или всегда генерировать — скажите, скрипт упростится.
