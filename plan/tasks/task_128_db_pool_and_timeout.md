# Задача 128. Пул БД бота: потокобезопасный пул и `statement_timeout`

**Блок:** инженерия · **Надобность:** 🟠
**Область:** `telegram_bot/database.py`, `tests/test_bot_database.py`, `docs/architecture.md`
(раздел «Connection Pool»).
**Зависит от:** ничего.
**Источник:** ревизия качества кода 2026-11-16, просьба человека завести задачи; реестр —
[`../open_tasks.md`](../open_tasks.md).

## Кратко

Пул соединений бота становится потокобезопасным, а у каждого его запроса появляется серверный
таймаут.

## Зачем и на что влияет

- Пул создаётся как `SimpleConnectionPool`, а соединения берут и поток event loop, и потоки
  `asyncio.to_thread`. `SimpleConnectionPool` для этого не предназначен: возможны гонки
  `getconn`/`putconn` и `PoolError`.
- Большая часть экранов выполняет запросы прямо в event loop. Таймаута у запросов нет, поэтому
  один медленный запрос или блокировка от загрузчика останавливает бота для всех чатов.

## Степень важности

🟠: подтверждённый риск зависания и гонок. Правка на несколько строк.

## Подробно

**Текущее состояние (снимок 2026-11-16, `origin/develop` = `5a97128`).**
- `telegram_bot/database.py:117` — `psycopg2.pool.SimpleConnectionPool`.
- Из потоков пул используют `bot.py` (около строк 963–981 — тикер расписаний, около 1124 —
  журнал действий на каждую команду и нажатие).
- У соединений пула не задан `statement_timeout`. Отдельное соединение `ai_stats.run_readonly`
  таймаут уже имеет — его не трогать.

**Что делать.**
1. Заменить `SimpleConnectionPool` на `ThreadedConnectionPool`; поправить аннотации и docstring
   модуля.
2. Передать в соединения пула `options="-c statement_timeout=<мс>"`. Значение — константа в
   `database.py` (вопрос 1 ниже).
3. Тест: соединение из пула возвращает заданный `statement_timeout` (DB-тест в
   `tests/test_db_nhl.py` либо проверка аргументов `connect` в `tests/test_bot_database.py`).
4. Обновить раздел «Connection Pool» в `docs/architecture.md`.

**Критерии приёмки.**
- `grep -n "SimpleConnectionPool" telegram_bot/` пуст.
- `SHOW statement_timeout` на соединении из пула возвращает заданное значение.
- Живая проверка на dev-боте: экраны, рассылка и расписания работают как раньше.
- `make ci-local` зелёный.

**Подводные камни.**
- Таймаут не должен попасть на соединения загрузчика (`pipeline/`) и миграций: у них запросы
  длинные по делу. Параметр задаётся только в пуле бота.
- Запрос, упавший по таймауту, поднимет исключение в хендлере. Общего обработчика ошибок
  диспетчера сейчас нет, пользователь получит тишину — это отдельная находка ревизии, в задачу
  не входит.
- Размер пула (сейчас до 5) при переходе не менять без причины.

## Открытые вопросы человеку

1. **Значение таймаута.** По умолчанию — 5 секунд: экраны бота отвечают за десятки
   миллисекунд, запас большой.
