# Задача 26. Сезонный retrain через cron

**Статус:** не начата (заблокирована Задачей 22) · **Блок:** трек B · **Надобность:** ⚪ (после 22)
**Область:** планировщик из Задачи 34, `Makefile` (`modeling-train`, `modeling-dev`), `modeling/` (при необходимости — predict-джоб для Задачи 22).
**Порядок:** последняя в треке B: 39 → 40 → (21) → 22 → **26**.
**Критерии приёмки и закрытие:** карточка Задачи 26 в [`../engineering/work_plan_2026-08-08.md`](../engineering/work_plan_2026-08-08.md) (три места) и строка в реестре.

## Кратко

Цепочка build-dataset → train → gate → сдвиг `latest` по **редкому** расписанию (старт
сезона + не чаще раза в неделю) — отдельным триггером, **не** частью суточной загрузки.
Сдвиг `latest` только если новая модель не хуже текущей (champion/challenger), а не просто
лучше константы. До неё весь цикл моделирования ручной. Механизм расписания даёт
Задача 34 — переиспользовать его.

## Зачем и на что влияет

- **Зачем.** Нестационарность: правила, уровень голов, составы меняются от сезона к сезону
  (§14 плана классификатора) — модель без retrain устаревает, а прогноз в боте (22)
  начинает врать молча. Последнее звено, замыкающее трек B в автономный цикл.
- **На что влияет.** Планировщик (новая цепочка рядом с загрузкой), окружение
  моделирования на площадке (`requirements-modeling.txt` не в образе бота), время
  и ресурсы хоста (полная сетка lgbm — часы), артефакты (`artifacts/models`, отчёты,
  дисковое место).
- **Если не делать.** Retrain остаётся ручной операцией раз в сезон — терпимо, поэтому ⚪.

## Степень важности

⚪ **Можно не делать в этом цикле.** Имеет смысл только после 22 (нечего переобучать, пока
модель не используется) и после 34 (нечего переиспользовать). До того — ручной
`make modeling-train`.

## Подробно

### Текущее состояние (сверено 2026-09-22)

- В `.github/workflows/` только `ci.yml`; расписаний нет ни там, ни в `Makefile`.
- `Makefile:71-74`: `modeling-dev` (ставит modeling-стек в `.venv`), `modeling-train`
  (обучение под конфигом).
- Гейт уже встроен в `train`: `latest` переставляется только при `status: ok`
  (`docs/modeling_training.md` §6 п. 5–6); тесты на `latest` есть
  (`tests/test_modeling_artifacts.py`, `test_modeling_acceptance.py`,
  `test_modeling_predict_runner.py`).
- Датасет пересобирается из БД (`build-dataset --mode train`); фичи меняют
  `features_hash` — retrain обязан пересобирать датасет, а не брать старый CSV.
- **Гейт слабый для автомата** (сверено 2026-09-29): `status: ok` означает лишь, что лучшая
  семья строго бьёт `trivial_base_rate` по калиброванному log loss на holdout
  (`docs/modeling_training.md` §6 п. 6). С текущей моделью в `latest` новая не сравнивается —
  автоматический прогон может заменить хорошую модель худшей, лишь бы она была лучше
  константы. При ручном запуске это прикрывает человек, читающий отчёт; при автоматическом — нет.
- **`over_5_5` не проходит гейт ни разу** (`docs/modeling_training.md` §8): `latest` для неё
  нет, и каждый прогон по расписанию будет красным целиком (run status `ok` только если все
  задачи `ok`).
- Суточная загрузка уже по расписанию (Задача 34, PR #38): сервис `sync`,
  `pipeline/scheduled_sync.py`.

### Что нужно сделать

0. **До автоматизации — решить судьбу `over_5_5`:** довести до прохождения гейта либо
   выключить задачу в конфиге retrain. Иначе каждый прогон по расписанию красный, к этому
   привыкают и перестают смотреть — отказ становится молчаливым.
1. **Один сценарий** (скрипт или цель Makefile) с жёстким порядком и остановкой на первой
   ошибке: проверка предусловия → `build-dataset --mode train` →
   `train --config configs/modeling_default.yaml` → сравнение с текущей моделью →
   сдвиг `latest` → (predict для ближайших игр и запись в таблицу для 22). Ничего не
   глотать (Global Constraint 4): шаг с ненулевым кодом — цепочка остановлена, `latest`
   не тронут.
   - **Предусловие:** retrain сам **не запускает** загрузку данных, а проверяет, что
     последний суточный sync (34) завершился успешно; иначе — отказ с ненулевым кодом.
     Обучение на недогруженных или битых данных хуже, чем отсутствие обучения.
2. **Champion/challenger.** Новая модель сдвигает `latest`, только если на общем свежем
   holdout её калиброванный log loss не хуже, чем у модели в текущем `latest` (допуск —
   решение при заведении). Проверка против `trivial_base_rate` остаётся как санитарная,
   но критерием замены не является. Первый прогон, когда `latest` нет, — только базовый гейт.
   **Допустимая альтернатива** (выбрать при заведении и записать в отчёт): расписание
   обучает и публикует отчёт, а `latest` двигается ручной командой — для одного пользователя
   это снимает риск молча выкатить плохую модель.
3. **Расписание** — отдельный триггер в механизме Задачи 34, **не** звено суточной
   загрузки. **Не чаще раза в неделю** (решение человека, 2026-09-29): по умолчанию —
   еженедельно в фиксированный день и час, плюс прогон на старте сезона; реже — можно,
   чаще — нет. Ежедневный retrain не нужен и вреден: за сутки прибавляется ~10 игр
   к ~6000 строк, модель не меняется по существу, а `latest` дёргается из-за шума в выборе
   гиперпараметров, прогноз в боте прыгает без причины; плюс часы хоста и каталог
   артефактов на каждый день. Если полный прогон дольше недели — расписание реже, а не
   урезание сетки молча (замерить длительность). Retrain не пересекается
   с суточной загрузкой по времени (lock или разнесённое окно).
4. **Откат.** Предыдущие успешные `run_id` не удаляются; откат = перестановка `latest` на
   прежний `final/`. Описать команду в документации. Если появится ротация прогонов — она
   обязана сохранять текущий и предыдущий успешный.
5. **Видимость результата.** Итог каждого прогона (`status`, `run_id`, время, решение
   champion/challenger) — в лог и туда же, куда Задача 34 выводит неуспешный sync.
   Непрошедший прогон должен быть заметен, а не только записан в файл.
6. **Окружение:** modeling-venv на площадке (`make modeling-dev`) или отдельный образ;
   бот-образ не трогать.
7. **Тесты:** проваленный гейт → `latest` прежний; успешный → сдвинут (если существующие
   тесты покрывают — не дублировать, сослаться). Новые: challenger хуже champion →
   `latest` прежний; упавший последний sync → retrain не стартует.
8. **Документация:** `docs/modeling_training.md` — раздел «Retrain по расписанию» (частота,
   правило замены, откат); `DEVELOPMENT.md` — где смотреть логи и последний статус.

### Критерии приёмки (карточка в плане 08-08)

- pipeline → train → gate → сдвиг симлинка `latest`.
- При непройденном гейте симлинк не двигается.
- Расписание переиспользует механизм Задачи 34.
- Дополнено 2026-09-29: retrain — отдельный триггер не чаще раза в неделю, не часть
  суточной загрузки;
  стартует только после успешного последнего sync; `latest` сдвигается, только если новая
  модель не хуже текущей (или продвижение ручное — выбор фиксируется); итог прогона виден;
  откат на предыдущий `run_id` документирован.

### Проверка

- Прогон цепочки руками от начала до конца с логом; затем один автоматический запуск
  по расписанию с видимым результатом (`status`, `run_id`, время).

### Подводные камни

- Полная сетка `modeling_default.yaml` — 2187 обучений lgbm на окно × 5 окон × 2 задачи;
  если это часы, retrain не должен пересекаться с суточной загрузкой (lock или разнесённое
  окно). Встраивать retrain в суточную цепочку sync — нельзя, см. п. 3.
- Дисковое место: каждый `run_id` — отдельный каталог артефактов и отчётов; ротация
  старых прогонов — отдельное решение, когда упрётся, а не «на всякий случай» (но с
  сохранением цели отката, п. 4).
- Champion/challenger на разных holdout нечестен: при сдвиге окна сравнивать обе модели
  на одном и том же отрезке свежих игр, а не старую метрику из отчёта champion с новой.
- Старт сезона: первые недели датасет нового сезона пуст, retrain фактически учится
  на прошлых сезонах — нормально, но holdout по времени сдвинется.
