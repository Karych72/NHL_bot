# Задача 83. ИИ отвечает на статистические вопросы по нашей БД

**Блок:** продукт · **Надобность:** 🟡
**Область:** новый модуль ответа на вопрос (рядом с модулем Задачи 81 — имя решает
исполнитель), хендлер свободного текста из 81 (ветка «нет подходящего экрана»), промпты
(генерация, ревью, разбор контекста), миграция: read-only роль БД и таблица лога,
`telegram_bot/config.py`, `docs/telegram_bot.md`, `docs/architecture.md`.
**Зависит от:** 81 — каркас (ключ, клиент `anthropic`, хендлер свободного текста, лимит, лог,
обработка сбоев) берётся оттуда, не пишется заново. Пересекается с черновиком премиум-ИИ
(`plan/premium_ai/README.md`, локальный, в репозиторий не внесён): 83 — его часть «ответ из
БД» без поиска в интернете.
**Источник:** просьба человека 2026-10-25; реестр — [`../open_tasks.md`](../open_tasks.md).

## Кратко

Пользователь пишет вопрос, на который нет готового экрана: «сколько Капризов набрал в
этом сезоне», «сколько Колорадо выиграл в гостях», «кто из русских больше всех бросает».
Модель пишет SELECT по схеме нашей БД, бот выполняет его read-only, модель формулирует
ответ по результату, вторая модель проверяет ответ. Проверка прошла — ответ уходит
пользователю; нет — бот просит уточнить вопрос. Уточнение и вопрос вдогонку («а в прошлом
сезоне?») бот понимает как продолжение прошлого вопроса.

## Зачем и на что влияет

- 81 открывает только существующие экраны. Вопросы вне экранов попадают в отказ, и по логу
  81 будет видно, сколько их. 83 закрывает эту часть без ручного каталога запросов.
- Цифры в ответе — только из результата нашего SQL: модель-ревьюер сверяет ответ с
  результатом, а не с «общими знаниями».
- Каркас SQL-цикла и ревью переиспользует премиум-ИИ: туда добавится поиск в интернете.

## Степень важности

🟡: расширяет 81, ничего не блокирует.

## Подробно

**Решения человека (2026-10-25).**
1. Модель пишет SQL сама по схеме БД (вариант «Б»), а не выбирает из каталога готовых
   запросов.
2. Отдельная задача, не часть 81.
3. Доступ к функции ограничен. **Как именно — человек решит позже** (см. «Открытые
   вопросы», п. 1).

**Что делать.**
1. **Быстрая проверка «есть ли у нас эти данные».** Первый вызов модели решает одно из трёх:
   *по данным* (с перечнем нужных таблиц), *нет таких данных* (вопрос о том, чего в БД нет:
   контракты, травмы, история до первого загруженного сезона, КХЛ) или *не по теме*. Опора —
   схема БД (`data_tables/*.sql`) плюс аннотация «какая таблица для каких вопросов и за какие
   сезоны в ней данные»; аннотация лежит в репозитории рядом с промптом и кэшируется вместе
   с ним. Нет данных — ответ «в наших данных этого нет», без SQL и без второй модели.
   Проверка и SQL могут идти одним вызовом, если это дешевле на замере (решает исполнитель
   с цифрами).
2. **Генерация.** Модель пишет один SELECT; бот выполняет его ролью только на чтение,
   с `statement_timeout` и лимитом строк. Ошибка SQL или пустой результат — модель видит
   ошибку и даёт исправленный запрос. Потолок попыток — в «Открытых вопросах», п. 3.
   По результату модель пишет короткий ответ на русском.
3. **Ревью.** Отдельный вызов, свой системный промпт, на входе: вопрос (с контекстом
   диалога), SQL, результат, черновик ответа. Ревьюер отвечает строго по схеме
   (`ok` / `уточнить` + текст уточняющего вопроса + причина): отвечает ли SQL на заданный
   вопрос (сезон, тип матчей, игрок или однофамилец), совпадает ли каждая цифра ответа с
   результатом, нет ли в ответе фактов не из результата. `ok` — ответ пользователю;
   `уточнить` — пользователю уточняющий вопрос ревьюера («Вы про регулярку или вместе с
   плей-офф?»), а не сырой отказ. Черновик, не прошедший ревью, пользователю не показывается.
4. **Продолжение или новый вопрос.** Бот хранит последние пары «вопрос–ответ» пользователя
   (вопрос, SQL, ответ, время). Новое сообщение — продолжение, если пришло в окне времени
   после прошлого ответа **и** модель на первом шаге отметила его как продолжение
   («а в прошлом сезоне?», «а у Макара?», ответ на уточнение ревьюера). Вне окна — всегда
   новый вопрос, история в запрос не идёт. Ответ на уточнение ревьюера — всегда продолжение
   того вопроса, к которому оно задано. Окно и глубина истории — «Открытые вопросы», п. 4.
5. **Read-only доступ к БД.** Отдельная роль Postgres: `SELECT` на таблицы данных, без
   доступа к таблицам бота (`bot_subscriptions`, лог вопросов и т.п.), `statement_timeout`,
   лимит строк на стороне бота. Миграция — сначала на `nhl_dev`. Учесть находку Задачи 82
   про `trust` в Postgres: роль должна реально ограничивать, а не держаться на доверии сети.
6. **Ограничение доступа** — по решению человека (п. 1 открытых вопросов). Лимит в сутки из
   81 действует и здесь; считать ли вопрос 83 дороже вопроса 81 — тот же пункт.
7. **Лог.** На каждый вопрос: пользователь, текст, признак «продолжение», решение проверки
   данных, SQL каждой попытки и число строк, черновик, вердикт ревьюера и причина, итоговый
   ответ, токены и стоимость по каждому вызову, задержка, ошибка. Хранение — таблица с
   миграцией (по ней ищутся повторяющиеся вопросы и непокрытые данные).
8. **Сбой API или БД** — как в 81: пользователю «не удалось ответить, попробуйте командой:
   /help», ошибка в лог (GC4).
9. **Документация:** `docs/telegram_bot.md` — раздел о вопросах по статистике и
   ограничении доступа; `docs/architecture.md` — новый модуль; промпты — в репозитории.

**Подводные камни.**
- Текст пользователя — данные, не инструкции; SQL пишет модель, поэтому граница
  безопасности — роль БД, а не промпт. «DROP» в тексте вопроса должен упереться в права роли.
- Однофамильцы, кириллица против латиницы в именах («Капризов» / Kaprizov), регулярка
  против плей-офф, текущий неполный сезон (на 2026-10-25 в БД 8 игр 2026/27, без бросков) —
  частые источники неверного SQL; ревьюер и контрольный набор должны их ловить.
- Ревьюер, который всегда говорит `ok`, бесполезен: в контрольном наборе нужны вопросы,
  где ожидается `уточнить`.
- Бюджет 300 строк (GC6): каркас — из 81; промпты и аннотация схемы — данные, а не код.
  Если не влезает — делить (например, 83A: проверка данных + генерация + ревью,
  83B: продолжение диалога).

## Открытые вопросы (решает человек)

1. **Кому доступно.** Варианты: только платные подписчики (связь с `plan/premium_payments/`),
   белый список `chat_id`, только текущие пользователи (как «текущий» в 81), отдельная
   квота. **Решение отложено человеком 2026-10-25** — без него задача не начинается.
2. **Модель ревьюера.** Предложение: та же `claude-sonnet-5-5` с отдельным промптом (одна
   модель — общий кэш, дешевле); `claude-opus-5-5` строже, но примерно вдвое дороже на
   вызове ревью.
3. **Потолки.** Предложение (из черновика премиум-ИИ): 3 SQL-попытки, не больше 4–5 вызовов
   модели на вопрос; жёсткий потолок ≈ $0.10 за вопрос.
4. **Окно продолжения.** Предложение: 30 минут после последнего ответа, в запрос — последние
   3 пары «вопрос–ответ».

**Стоимость** (оценка до замера, цены сверить перед работой): ≈ $0.03–0.07 за вопрос — схема
БД ≈ 7K токенов в кэше, 1–3 SQL-попытки, вызов ревью. Это в 3–7 раз дороже вопроса 81, отсюда
ограничение доступа. Замер на контрольном наборе — часть приёмки.

**Ещё нужно до начала.**
1. Закрыта 81 (каркас).
2. Решение по п. 1 «Открытых вопросов»; пп. 2–4 — подтвердить или поправить.

**Критерии приёмки.**
- Контрольный набор в репозитории: 30–50 вопросов с правильными ответами, посчитанными
  вручную по БД; плюс вопросы «нет таких данных», «не по теме», неоднозначные (ожидается
  `уточнить`) и цепочки продолжений. Прогон — отдельной командой против настоящего API
  (не в `make ci-local`). Порог: ≥ 90% верных ответов, **ни одной неверной цифры в ответе,
  прошедшем ревью**, итог и средняя/максимальная стоимость — в отчёте.
- Юнит-тесты без сети: роль БД не может писать и не видит таблиц бота (на настоящей БД);
  вердикт `уточнить` → пользователю уточнение, черновик не уходит; ответ вне окна времени
  не получает истории; ответ на уточнение — продолжение; превышение потолка попыток →
  сообщение пользователю; ограничение доступа соблюдается. Модель в юнит-тестах подменяется
  заданными ответами — это проверка нашего цикла, а не модели.
- Живая проверка на dev-боте: 5–6 вопросов разного вида, одно продолжение, один вопрос
  без данных.
- `make ci-local` зелёный.
