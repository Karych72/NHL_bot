# Задача 121. История 2009/10–2020/21 в БД

**Блок:** трек B · **Надобность:** 🟡 · **Зависит от:** — (сырой слой уже собран, см. «Текущее состояние»)
**Область:** `pipeline/load_season_modern.py` (справочник команд), `modeling/dataset_builder/`
и `configs/modeling_*.yaml` (нижняя граница сезонов), `telegram_bot/prompts/stats_*.md`
(рамка данных ИИ), `docs/data_loading.md`, `docs/modeling_training.md`.
**Источник:** разговор с человеком 2026-11-02 — 2026-11-16 «какую историю с аналогичными данными
можно загрузить», исследование API и сбор сырого слоя в той же сессии. Реестр —
[`../../open_tasks.md`](../../open_tasks.md).

## Кратко

Загрузить в `nhl_dev`, затем в продовую базу двенадцать сезонов 2009/10–2020/21
(14 917 завершённых матчей, регулярка и плей-офф) из уже скачанного сырого слоя. Перед загрузкой
поправить справочник команд, иначе прошлые сезоны получат нынешние дивизионы; закрыть датасет
модели нижней границей, чтобы загрузка его молча не изменила; перевести рамку данных ИИ
с «с 2021/22» на «с 2009/10».

## Зачем и на что влияет

- **Модель (трек B).** Сейчас датасет — 6270 строк на пяти сезонах. История даёт примерно
  втрое больше матчей и ~1,7 млн попыток бросков к нынешним 770 тыс. — для xG (69, 93) и для
  проверки по сезонам (66) с большим числом тестовых сезонов. Помогут ли дальние сезоны модели
  победы и тоталу, решает отдельная проверка после загрузки (см. «Вне задачи»): результативность
  начала 2010-х ниже нынешней, а овертайм 3 на 3 действует только с 2015/16.
- **ИИ-ответы (83, 94).** Главный риск каталога 94 — карьерные итоги «с 2021/22 в наших данных».
  С историей рамка сдвигается на 2009/10, карьерные вопросы по большинству активных игроков
  закрываются целиком.
- **Экраны бота** привязаны к `SEASON_ID` и историю не показывают — меняется только то, что
  читает базу без фильтра сезона (ИИ, датасет).

## Степень важности

🟡: качество модели и ответов ИИ; бот, рассылки и канал не меняются, релиз от задачи не зависит.

## Подробно

### Текущее состояние (снимок 2026-11-16, перед работой сверять)

- **Сырой слой собран целиком в `NHL_bot/all_data/raw/`** (только ноутбук человека, в git и бэкап
  не входит): 18 сезонов 2009/10–2026/27, 66 705 файлов `{season}/{game_id}.{pbp|box|landing}.json.gz`,
  441 МБ; каждый сезон сверен со списком завершённых матчей API (`gameStateId=7`, типы 2 и 3),
  пропусков нет, все архивы проходят `gzip -t`. История 2009/10–2020/21 — 415 МБ. Формат и пути
  те же, что пишет `fetch_game_json`, — загрузчик возьмёт матчи из кэша и в сеть за ними не пойдёт.
  На VM в томе `nhl_bot_syncdata` из прошлых сезонов лежит только плей-офф 2021/22–2025/26.
- **Почему с 2009/10.** Проверка API 2026-11-02 (по 8 матчей на сезон): с 2009/10 у 100% бросков
  есть координаты и `situationCode`, в play-by-play ~300 событий на матч (хиты, вбрасывания),
  заполнены `puckPossessions` и «три звезды» — ровно наш набор. В 2005/06–2008/09 play-by-play
  урезан до 50–90 событий без единой координаты и `situationCode` (для `shot_attempts` негоден),
  до 2004/05 хиты, блоки и промахи в отчётах — нули. Сезонные отчёты stats/rest и составы
  `/v1/roster/{tri}/{season}` (в том числе ATL 2009/10, PHX 2013/14) отвечают для всех сезонов.
- **Матчей по сезонам** (регулярка + плей-офф): 2009/10 — 1319, 2010/11 — 1319, 2011/12 — 1316,
  2012/13 — 806 (локаут, 48 игр), 2013/14 — 1323, 2014/15 — 1319, 2015/16 — 1321, 2016/17 — 1317,
  2017/18 — 1355, 2018/19 — 1358, 2019/20 — 1212 (прерван COVID), 2020/21 — 952 (56 игр,
  изолированные дивизионы).
- **Справочник команд берёт дивизион и конференцию из `/v1/standings/now`**
  (`load_season_modern.py:315`). Для прошлого сезона это нынешняя раскладка, а у исчезнувших
  клубов (ATL, PHX) — NULL. Исторический `/v1/standings/{YYYY-MM-DD}` работает: на 2010-04-11 —
  30 команд со своими дивизионами (WSH — Southeast).
- **Датасет берёт все сезоны из `games`** (`modeling/dataset_builder/base.py:124`, фильтр только
  `game_type = 2`): загруженная история сразу попадёт в обучение, xG (обучается на прошлых
  сезонах) и Elo. Сезоны проверки заданы в `configs/modeling_default.yaml:20`
  (`test_seasons: [20232024, 20242025, 20252026]`), нижней границы обучения нет.
- **Промпты ИИ прямо называют рамку 2021/22:** `stats_schema_notes.md:7–8` (список сезонов,
  «данных до 2021/22 нет»), `:45` (броски у 20212022–20252026), `:61` («с сезона 2021/22 в наших
  данных»), `stats_answer.md:19, 30`, `stats_reviewer.md:17`.

### Что сделать

1. **Справочник команд по дате сезона.** Брать standings на последний день регулярки
   загружаемого сезона (`/v1/standings/{дата}`), а не `now`; для текущего сезона поведение не
   меняется. Пройти загрузчик на прочие «сейчас»: `current_team_id` и `currentage` уже пишутся
   NULL осознанно (строки 525, 575, 599) — проверить, что других нет.
2. **Нижняя граница датасета.** Поле в конфиге сборки (`configs/modeling_*.yaml`) с нынешним
   первым сезоном 20212022 — датасет, xG и Elo после загрузки истории те же, что до неё.
   Сдвинуть границу — решение отдельной проверки, не этой задачи.
3. **Загрузка на `nhl_dev`.** Сезоны по одному, от старого к новому (`--season-id`, окно —
   весь сезон), регулярка и плей-офф. Кэш — тот же `all_data/raw` (на VM — скопировать
   историю в том `nhl_bot_dev_syncdata`, ~415 МБ). Каждый сезон сверить: матчей в `games` по
   типам = числа выше, у сезонов 2009/10+ у бросков есть координаты.
4. **Рамка данных ИИ.** Промпты из «Текущего состояния» — на «с 2009/10»; отметить неполные
   сезоны (2012/13, 2019/20, 2020/21), чтобы ИИ не сравнивал их итоги с полными без оговорки.
   Прогнать `make ai-stats-eval`: вопросы с рамкой 2021/22 в `scripts/ai_stats_eval.jsonl`
   поправить на новые ожидаемые числа.
5. **Прод.** Код — обычным путём `develop` → `master`; данные на продовую базу — после релиза,
   тем же способом, что на `nhl_dev` (кэш в `nhl_bot_syncdata`).
6. **Документация.** `docs/data_loading.md` — загрузка истории и откуда кэш;
   `docs/modeling_training.md` — нижняя граница датасета; `CLAUDE.md`, ограничение 8 — новые
   объёмы (снимок, а не источник истины).

### Критерии приёмки

- В `teams` прошлых сезонов — свои дивизионы и конференции, ATL и PHX без NULL; в текущем сезоне
  справочник тот же, что до правки.
- `build-dataset` до и после загрузки истории даёт те же 6270 / 6787 / 16024 строк
  `dataset_train` / `games_train` / `shots_train` (сверить с актуальными перед стартом) — как
  в приёмке 102.
- В `nhl_dev` — 14 917 матчей 2009/10–2020/21 по таблице выше; `shot_attempts` есть у каждого
  матча этих сезонов.
- `make ai-stats-eval` зелёный; на вопрос о карьере игрока ИИ называет рамку «с 2009/10».
- `make ci-local` зелёный, `test_db_nhl` прогнан на базе с историей.

### Подводные камни

- **Место на диске VM.** Оценка (2026-11-02, не замер): +0,5–0,9 ГБ на каждую базу, `nhl_dev`
  и `postgres` — вдвое; плюс ~0,4 ГБ кэша на каждый том. Бэкап хранит 14 дампов `postgres` —
  каждый вырастет в 3–4 раза. Перед загрузкой — `df -h` на VM и размер последнего дампа.
- **Переезды клубов** меняют `team_id`: ATL → WPG (2011), PHX → ARI (2014), ARI → UTA (2024);
  новые VGK (2017) и SEA (2021). Запросы ИИ «за историю клуба» должны это учитывать —
  оговорка в `stats_schema_notes.md`.
- **Плей-офф 2019/20** — пузырь с квалификационным раундом и турниром за посев. Проверить,
  как эти матчи приходят (`gameType`, серии) и не ломают ли представление `playoff_series` (105).
- **Координаты 2009–2012** по известным данным сообщества искажены по аренам (scorer bias) —
  для xG на ранних сезонах это шум; учесть в проверке, а не здесь.
- **Загрузка с API, а не из кэша**, заняла бы сутки и больше: при сборе сырого слоя API
  притормаживал до 3–4 матчей в минуту. Кэш на VM копировать, а не качать заново.
