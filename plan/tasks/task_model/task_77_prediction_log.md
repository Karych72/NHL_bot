# Задача 77. Журнал прогнозов: история публикаций и проверка на живых играх

**Блок:** трек B · **Надобность:** 🟠
**Область:** таблица журнала (новая миграция — следующий свободный номер после 0009),
`modeling/publish_predictions.py` (`_replace_task_rows`), новая команда проверки в
`modeling/cli.py`, тесты, `docs/modeling_training.md`, `docs/architecture.md`.
**Зависит от:** Задача 73 (PR #92): сервис `predict` и таблица `game_predictions`.
**Источник:** просьба человека 2026-10-23 «давай логировать прогнозы наши»; реестр —
[`../../open_tasks.md`](../../open_tasks.md).

## Кратко

Каждую публикацию прогноза сохранять в журнал, который ничего не удаляет. Сравнить журнал
с результатами сыгранных матчей и считать качество нашей модели на живых играх: log-loss и
Brier победы и тотала против константы.

## Зачем и на что влияет

- `game_predictions` — витрина для бота: каждая публикация удаляет строки задачи и пишет новые,
  а сыгранная игра пропадает из неё на следующий день. Поэтому история того, что бот показал,
  нигде не хранится. С выкатки 73 (2026-10-14) она теряется каждый день.
- Решение по тоталу человек принял на условии: «ошибку принимаем — не оправдается, уберём»
  (2026-10-14). Проверить «оправдался или нет» без журнала нечем. Walk-forward по прошлым
  сезонам — не то же самое, что живой прогноз на признаках дня публикации.
- Журнал — основа для будущих сравнений с рынком (70) и ретроспектив по корзинам (74).

## Степень важности

🟠: без журнала решение по тоталу принять нечем, а история прогнозов теряется каждый день.

## Подробно

**Состояние на 2026-10-23.** Сервис `predict` раз в сутки в 12:00 UTC вызывает
`publish-predictions` (`home_win`) и `publish-goals` (`over_5_5`). Обе публикации идут через
`_replace_task_rows`: DELETE строк задачи + INSERT одной транзакцией. На проде 2026-10-23 в
таблице по 14 строк на задачу. Игра бывает в predict-датасете дважды — накануне («завтра»)
и в день матча («сегодня»), — и прогнозы на эти два дня различаются: признаки разные.

**Что делать.**

1. **Таблица журнала** (например, `prediction_log`): `game_id`, `task`, `model`, `run_id`,
   `probability`, `published_at`. Записи только добавляются. Повторный прогон в тот же день
   не должен дублировать строки: уникальность по (`game_id`, `task`, `run_id`, дата
   публикации). FK на `games` нет — игра ещё не сыграна.
2. **Запись** — в той же транзакции, что и замена `game_predictions`, в `_replace_task_rows`.
   Журнал не должен разойтись с тем, что видел бот.
3. **Проверка на живых играх** — команда CLI (например, `evaluate-live`). Для каждой сыгранной
   игры берётся последняя запись журнала, опубликованная до дня матча включительно (все
   игры NHL начинаются после 12:00 UTC публикации). Считаются:
   - log-loss, Brier и ECE модели против константы — доли побед хозяев и доли «больше 5.5»
     по прошлым сезонам, как в §2a/§2c `docs/modeling_training.md`;
   - разность «модель − константа» с ДИ — парный bootstrap по игровым дням (`modeling/bootstrap.py`);
   - n игр, таблица калибровки.

   Вывод — `summary.md` и `metrics.json`, как у `evaluate-goals`. Без записи в БД.
4. **Восстановление пропущенной истории (по решению человека).** С 2026-10-14 до выкатки 77
   журнала нет. Прогнозы за эти дни можно пересчитать замороженными моделями из
   `deploy/models/` на признаках «как на день публикации» и записать с пометкой источника
   `backfill`. Совпадение с показанным неточное: b2b у отброшенных правилом 5 игр игр и доля
   ничьих зависят от дня сборки. Если не восстанавливать — проверка начинается с выкатки 77.

**Решения человека, нужные до старта.**
- Восстанавливать ли пропущенные дни (п. 4), и если да — отдельной пометкой.
- Критерий «тотал не оправдался». Предложение: при n ≥ 300 живых игр ДИ разности
  «модель − константа» по log-loss целиком выше 0 → строку тотала убираем. ДИ включает 0
  → модель не хуже константы, оставляем. Победа — тот же отчёт, решения не требует.

**Критерии приёмки.**
- Публикация пишет журнал. Повторный прогон в тот же день журнал не раздувает. Строки
  прошлых дней переживают следующую публикацию.
- `evaluate-live` на синтетическом журнале и результатах считает метрики, совпадающие с
  ручным расчётом.
- Тесты SQL журнала — на БД (`make all-tests`, миграция).
- `docs/modeling_training.md` — раздел о живой проверке; `docs/architecture.md` — таблица
  и миграция.
- `make ci-local` зелёный.

**Подводные камни.**
- Ключ сопоставления — `game_id`: у `scheduled_games` и `games` он общий. Перенесённую
  игру (новая дата, тот же `game_id`) сопоставлять с последней публикацией до её
  фактического дня.
- Константа и формулы метрик — те же, что в walk-forward (`modeling/metrics.py`), чтобы
  живые цифры сравнивались с §2a–§2c напрямую.
- Отчёт запускается в контейнере `predict` на проде:
  `docker compose run --rm predict python -m modeling.cli evaluate-live`.
