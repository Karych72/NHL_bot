# Задача 145. ИИ: карьера и биография игрока из NHL API (ресёрч)

**Блок:** продукт · **Надобность:** 🟡
**Область:** NHL API (эндпоинты игрока), `pipeline/`, `data_tables/`, итог —
`plan/ai_questions/career_bio_research.md` и задачи на загрузку.
**Зависит от:** ничего; приоритет уточняет 142 (доля отказов «нет данных о карьере»). Связана с
121 (история с 2009/10 в БД): она сдвигает рамку «в наших данных», но карьерных итогов не даёт.
**Источник:** обсуждение развития ИИ 2026-11-16; реестр — [`../open_tasks.md`](../open_tasks.md).

## Кратко

Выясняем, можно ли взять из официального NHL API итоги карьеры и биографию игрока (рост, вес,
драфт, награды) и положить в базу, чтобы ИИ отвечал на такие вопросы одной короткой выборкой.

## Зачем и на что влияет

- В каталоге Задачи 94 «карьера и рубежи» («сколько всего голов у Овечкина», «сколько Малкину до
  1300 очков») — тип с высокой частотой, и на него бот отвечает оговоркой: в базе данные с
  2021/22 (после 121 — с 2009/10), а Овечкин играет с 2005/06.
- Био: возраст в базе есть (`rosters.currentage`), роста, веса, драфта, наград — нет.
- Это расширение почти без токенов: ответ — одна строка из таблицы, без SQL по игровым логам
  и без поиска в интернете.

## Степень важности

🟡: закрывает самый частый известный отказ, но сначала нужно убедиться, что данные в API есть
и в каком виде.

## Подробно

**Что проверено пробой 2026-11-17** (один игрок, Овечкин, `/v1/player/8471214/landing`).
- Био: `heightInCentimeters`, `weightInKilograms`, `birthDate`, `birthCity`, `birthCountry`,
  `shootsCatches`, `sweaterNumber`; драфт `draftDetails` — год, клуб, раунд, номер в раунде, общий номер.
- Итоги карьеры `careerTotals`: регулярка и плей-офф отдельно — игры, голы, передачи, очки, ±,
  броски, голы и очки в большинстве и меньшинстве, победные голы, среднее время.
- `seasonTotals` — 73 строки: все сезоны и лиги с юниоров (первый — 2000/01, сборная U17), у
  каждой клуб и тип игр; смена клуба внутри сезона видна отдельной строкой.
- `awards` — награды с сезонами; признаки `inHHOF`, `inTop100AllTime`.
- Не проверено: вратарь, завершивший карьеру игрок, новичок без матчей.

**Что выяснить.**
1. Какие поля реально отдаёт API: итоги карьеры (регулярка и плей-офф отдельно), посезонные
   строки (включая сезоны до 2009/10 и другие лиги), рост и вес, дата и место рождения, драфт
   (год, раунд, номер, клуб), награды, номер, хват. Для вратарей — свой набор.
2. Покрытие: действующие игроки, завершившие карьеру (Гретцки, Ягр) — нужны ли они и отдаёт ли
   API их по `player_id`; откуда брать `player_id` игроков, которых нет в наших `rosters`.
3. Объём и расписание: сколько запросов на первичную загрузку (игроков в `rosters` — порядка
   тысячи на сезон), как часто обновлять (итоги карьеры меняются после каждого матча — можно ли
   считать «итог до сезона из API + текущий сезон из нашей базы»).
4. Согласованность: сходятся ли итоги карьеры из API с суммой наших посезонных строк за
   сезоны, которые есть в базе (сверить на 20 игроках).
5. Форма хранения: одна таблица на игрока (итоги и био) или посезонные строки карьеры; как это
   видит ИИ — новая таблица в `AI_TABLES` или поля в `player_overview`.
6. Рубежи («сколько до 900 голов», «какое место в истории») — что из этого считается по
   данным API, а что требует списка лидеров всех времён (есть ли такой эндпоинт).

**Критерии приёмки.**
- `plan/ai_questions/career_bio_research.md`: таблица «поле → есть / нет / с оговоркой» по
  проверенным игрокам (полевой, вратарь, ветеран, новичок, завершивший карьеру), с примерами ответов.
- Оценка объёма: запросов на первичную загрузку и на ежедневное обновление, размер таблицы.
- Результат сверки итогов карьеры с нашей базой на 20 игроках.
- Рекомендация по форме хранения и по тому, какие типы вопросов каталога 94 это закрывает.
- Заведены задачи на загрузку и на подключение к ИИ — или записано, почему делать не стоит.

**Подводные камни.**
- API неофициальный и без договора об уровне обслуживания: поля меняются без объявления. Загрузчик
  должен падать громко на изменившейся форме ответа (Global Constraint 4), а не писать пустые поля.
- Рост и вес в API могут быть в двух системах единиц — брать метрическую.
- Проект читает API только из `pipeline/`, бот читает только базу. Вызов API из бота на вопрос
  пользователя — другое архитектурное решение (так сделан live-счёт в Задаче 57); если ресёрч
  придёт к нему, вынести на решение человека, а не делать молча.
- Не тянуть данные «на будущее»: в базу идут только поля, под которые есть тип вопроса из
  каталога 94 или из журнала (Global Constraint 1).
