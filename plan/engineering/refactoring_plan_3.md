# Refactoring Plan 3: дорожная карта и приоритеты

**Статус:** актуальный мастер-план незавершённой инженерной и продуктовой работы.  
**База:** наследует контекст [`refactoring_plan_2.md`](./refactoring_plan_2.md) и историю [`refactoring_plan.md`](./refactoring_plan.md).  
**Дата среза:** 2026-05-15.

---

## 1. Шкала важности

Каждая задача ниже помечена уровнем **P0–P3**. Это не «сроки», а относительную ценность исправления/доработки для продукта и поддержки.

| Уровень | Значение |
|--------|----------|
| **P0 — Критичная** | Пользователь сталкивается с тупиком в интерфейсе, некорректным сценарием или явной поломкой основного потока; без закрытия плана доверие к боту падает. |
| **P1 — Высокая** | Нагрузка на БД, риск регрессий при изменениях, неполнота тестов/CI, навигационные дыры в популярных ветках — влияет на стабильность релизов и эксплуатацию. |
| **P2 — Средняя** | Качество кода, документация API модуля, консистентность форматирования, новые экраны из уже имеющихся данных — улучшает продукт, но не блокирует «пройти сценарий». |
| **P3 — Низкая** | Полировка контента (три звезды NHL, серии W/L), удаление малозначимого dead code без угрозы безопасности — можно планировать после P0–P2. |

## 3. Детализация по направлениям

### 3.1. Навигация и отсутствие тупиков (P0–P1)

| Пункт | Важность | Критерий готовности |
|-------|----------|---------------------|
| **7.1** | **P0** | После любого типового действия в `/stats` (лидерборд, пагинация, дайджест, команды, игроки, вратари) пользователь видит клавиатуру с выходом назад или в главное меню; нет экрана «только текст». |
| **7.2c** | **P1** | Пройден чеклист всех callback-веток из [`docs/user_journey_stats.md`](../../docs/user_journey_stats.md) (или эквивалент); расхождения заведены как отдельные баги. |

### 3.2. Производительность и архитектура (P1)

| Пункт | Важность | Критерий готовности |
|-------|----------|---------------------|
| **5.4** | **P1** | Для согласованного списка запросов (зафиксировать в коде комментарием или ADR): ограничение размера кэша, инвалидация/TTL, отсутствие устаревших данных дольше приемлемого окна для NHL daily stats. |

### 3.3. Тесты и CI (P1)

| Пункт | Важность | Критерий готовности |
|-------|----------|---------------------|
| **6.1b** | **P1** | `conftest.py` с общими фикстурами (конфиг, мок БД или URL); новые тесты на регрессии навигации/форматов по мере внедрения. |
| **6.1c** | **P1** | Минимум один интеграционный сценарий «запрос → ответ» для слоя сообщений или хендлеров без запуска реального Telegram при необходимости. |
| **DB-C** | **P1** | В [`db_tests_remediation_plan.md`](./db_tests_remediation_plan.md) чеклист этапа C закрыт: воспроизводимые команды для данных + зелёный прогон. |
| **DB-D** | **P1** | Либо job в CI с Postgres и схемой, либо явное решение «только локально» задокументировано в корневом README с обоснованием. |

### 3.4. Документация модулей (P2)

| Пункт | Важность | Критерий готовности |
|-------|----------|---------------------|
| **6.2b** | **P2** | Публичные entrypoints (`bot.py` регистрация, основные функции `bot_messages.py`, фасады в `stats_handlers.py`) имеют однострочные/краткие docstrings; сложные функции — параметры и исключения. |

### 3.5. UX и контент (P2–P3)

| Пункт | Важность | Критерий готовности |
|-------|----------|---------------------|
| **7.7b** | **P2** | Нет смешения `parse_mode` без необходимости; имена с `-` и спецсимволы не ломают разметку; чеклист экранов вынесен в комментарий к PR или в `docs/`. |
| **7.4** | **P2** | Есть хотя бы один новый пользовательский поток «карточка команды» или «расширенная стата», использующий уже загружаемые поля БД. |
| **7.3b** | **P3** | Три звезды отображаются с источником данных (API/таблица), согласованы с официальной терминологией.; fallback при отсутствии данных. |
| **7.5b** | **P3** | Серии/сравнения не дублируют текст `/help` без добавленной ценности; производительность приемлема (см. **5.4**). |

### 3.6. Чистка кода (P3)

| Пункт | Важность | Критерий готовности |
|-------|----------|---------------------|
| **DC-2**, **DC-3** | **P3** | Принято явное решение «удалить / встроить / оставить с пометкой»; код и документация согласованы; тесты зелёные. |
| **DC-meta** | **P3** | Индекс планов в [`plan/README.md`](../README.md) не ссылается на выполненные чеклисты как на активные. |

## 4. Рекомендуемая последовательность работ

1. **P0:** закрыть **7.1** (тупики) — максимальный эффект на восприятие бота.
2. **P1:** **7.2c** (полный проход навигации) + **5.4** (кэш под нагрузку) параллельно по ресурсам, либо кэш сразу после навигации.
3. **P1:** **6.1b** / **6.1c** + **DB-C** / **DB-D** — укрепить линию регрессий перед большими UX-изменениями (**7.4**, **7.7b**).
4. **P2:** **6.2b**, **7.7b**, **7.4** — в удобном порядке для релиза.
5. **P3:** **7.3b**, **7.5b**, **DC-*** — по мере наличия времени.
