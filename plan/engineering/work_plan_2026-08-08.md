**Зачем.** Задача 28 починила код загрузчика (`is_shootouts`, `shifts`,
`goalies_season_stats.time_on_ice[_per_game]`, `current_team_id` из лендинга), но правка
кода не пересчитывает уже лежащие строки. В текущей БД (5 сезонов, ~6559 игр,
`SEASON_ID` 20212022–20252026) `games.is_shootouts = true` у всех игр,

**I4 — точная процедура, один прогон на сезон.** `make season-load-full` /
`make season-reload-current` грузят только текущий сезон: `Makefile:43` —
`SEASON_START ?= 2025-10-01`, `Makefile:167-168` — `season-load-full` это `season-sync`
от `SEASON_START` до сегодня, а `SEASON_ID`/`CURRENT_SEASON` `season-sync` явно не
пробрасывает — берёт их из `.env`/окружения (по умолчанию `20252026`/`25/26`,
`telegram_bot/config.py:70-71`). Одним прогоном чинится только сезон 2025/26
(~1300 игр из 6559); остальные четыре сезона грузятся отдельными прогонами
`season-sync` со своими `SEASON_ID`/`CURRENT_SEASON`/`DATE_FROM`, например:

```
make season-sync DATE_FROM=2021-10-01 DATE_TO=$(date +%Y-%m-%d) SEASON_ID=20212022 CURRENT_SEASON="21/22"
make season-sync DATE_FROM=2022-10-01 DATE_TO=$(date +%Y-%m-%d) SEASON_ID=20222023 CURRENT_SEASON="22/23"
make season-sync DATE_FROM=2023-10-01 DATE_TO=$(date +%Y-%m-%d) SEASON_ID=20232024 CURRENT_SEASON="23/24"
make season-sync DATE_FROM=2024-10-01 DATE_TO=$(date +%Y-%m-%d) SEASON_ID=20242025 CURRENT_SEASON="24/25"
make season-load-full   # текущий сезон 2025/26, SEASON_ID/CURRENT_SEASON уже в .env
```

`DATE_TO=$(date +%Y-%m-%d)` безопасен даже для прошлых сезонов: `fetch_final_games`
(`load_season_modern.py:724-730`) фильтрует по `season=<SEASON_ID>` в cayenne-запросе,
так что окно дат нужно только не *уже* реальных дат сезона, не точнее — `DATE_FROM`
1 октября того года консервативно предшествует первой игре сезона (тот же паттерн, что
`SEASON_START` по умолчанию для текущего сезона). Проверить перед прогоном на живом
NHL-эндпоинте фактическую нумерацию `SEASON_ID` для всех пяти сезонов (могла разойтись
с предположением выше) и актуальный набор `SEASON_ID` в самой БД (`SELECT DISTINCT
season_id FROM games ORDER BY 1`), а не полагаться на цифры из этого текста.

Перезагрузка идемпотентна (`docs/architecture.md:765` — сезонные таблицы через UPSERT,
матчевые через `DELETE … WHERE game_id = ANY(window) → INSERT`), прогон можно повторять.

**M10(a) — предупреждение, проверить на первом же историческом прогоне.** `is_shootout`
при отсутствующем в PBP `gameOutcome` тихо даёт `False` (`str(None) == "SO"`) — «данных об
исходе нет» неотличимо от «не буллиты» (это в контракте §3 доков, код трогать не нужно).
Если в архивных PBP старых сезонов (2021–2024) поля `gameOutcome` не окажется (структура
ответа могла отличаться в более старых играх), все их игры молча получат
`is_shootouts = false` — то же самое зашитое-неверное поведение, что чинила Задача 28,
только в другую сторону и без комментария-предупреждения в коде. Проверить на выборке
после первого прогона по историческому сезону: сверить количество игр с `is_shootouts =
true` с реальным количеством буллитных игр за тот сезон (публичная статистика NHL) —
не просто «не упало».

**Критерии приёмки:**
- Все 5 сезонов перезагружены процедурой выше (или уточнённой на живых данных версией).
- `games.is_shootouts` совпадает с фактическим исходом игр во всех сезонах (выборочная
  проверка по публичной статистике буллитных игр — не только «код не упал»).
