# План: прематч-классификаторы NHL (победитель, тотал O/U 5.5)

**Статус:** проектирование (не реализовано в коде).

**Цель документа:** зафиксировать контракт данных, каталог признаков, протокол обучения/валидации, выбор моделей, калибровку, метрики, структуру кода и критерии приёмки на уровне, достаточном для реализации без «додумывания» на месте.

**Ограничения (принятые):** без симуляций счёта; только вероятностные классификаторы и их `predict_proba`; источник исходов и статистики — существующая PostgreSQL-схема проекта ([data_tables/](data_tables/)); исторические коэффициенты букмекеров в плане не предполагаются (отдельный этап).

## 1. Постановка задач и метки

### 1.1 Бинарная «победа дома» (moneyline с ОТ)

**Метка `y_home_win`:**

- `1`, если `games.winner_id = games.home_team_id`;
- `0`, если победила гостевая (`winner_id = away_team_id`);
- Игры без исхода (если встречаются в БД до финала) — **исключить** из обучения и скоринга.

**Нюанс NHL:** типичный рынок moneyline включает овертайм и буллиты. Метка выше ему соответствует. Рынок «регуляция» (три исхода или пуш на ничью) — **отдельная задача**, другая разметка.

**Класс-баланс (policy v1):** домашнее преимущество даёт `P(home)` заметно выше 0.5 и это **естественный base rate**. По умолчанию использовать `class_weight=None`; оптимизировать log loss / Brier.
`class_weight='balanced'`/инверсии частот включать только как отдельный эксперимент (при явной причине, например искусственном пересэмплировании train) и обязательно сравнивать калибровку до/после.

### 1.2 Бинарный тотал «больше / меньше 5.5»

**Метка `y_over_5_5`:**

- Счёт: для каждого `game_id` взять сумму `goals` по двум строкам `game_team_stats` (home и away). Надёжный способ: агрегировать `SUM(goals) GROUP BY game_id` и убедиться, что ровно две команды (или фильтровать по паре из `games`).
- `y_over_5_5 = 1` если сумма > 5.5, иначе `0` (5 или меньше голов).

**Нюансы:**

- Для линии **ровно 5.5** пуша нет — бинарная метка однозначна.
- Если позже понадобятся целые линии (например 6.0) — отдельная схема с пушем (исключение из loss или трёхклассовая постановка).

### 1.3 Мультизадачность vs две отдельные модели

| Подход | Плюсы | Минусы |
|--------|--------|--------|
| **Две независимые модели** | Проще отладка, разный набор фич на задачу (например, больше «атака/оборона» для тотала) | Дублирование пайплайна |
| **Одна модель, две головы (multitask)** | Общие представления; один forward | Сложнее тюнинг; обе задачи должны иметь данные на одном множестве игр |

**Рекомендация для v1:** две модели (home win и over 5.5), общий модуль построения матрицы признаков X и общий сплит по времени. Multitask — опционально в v2 после стабилизации фич.

## 2. Анти-утечка и контракт времени

### 2.1 Инвариант (обязательный)

Для строки матча с `game_id`, `day = D` любой признак может использовать только информацию из игр с **`games.day < D`** (и при необходимости ту же границу по `game_id` порядку, но дата — основной контракт).

**Запрещено:**

- Любые поля из `game_team_stats` / `game_player_stats` для **того же** `game_id`, кроме того, что нужно **после** матча для метки (на этапе обучения метки считаются отдельно и не попадают в X).
- «Текущий сезонные» агрегаты без отсечения по дате (например, среднее по всему сезону, включая будущие игры).

### 2.2 Практическая реализация rolling

Два эквивалентных паттерна (выбрать один и не смешивать в одном проекте без причины):

**A) SQL-first:** оконные функции `ROWS BETWEEN ... PRECEDING` по **глобальной хронологии** игр команды. Критично: окно должно быть **по прошлым играм команды**, отсортированным по `day`, `game_id`, и для матча в D брать только строки с датой < D. Удобно делать через предрасчёт таблицы «игра команды → агрегат после предыдущих N игр».

**B) Python-first:** выгрузить long table `(game_id, day, team_id, is_home, goals_for, goals_against, ...)` отсортировать по `team_id, day, game_id`, для каждой строки считать `rolling().shift(1)` (обязательный **shift(1)** после rolling, чтобы не включить текущий матч).

**Проверка утечки (автотест):** для случайной выборки матчей вручную или скриптом пересчитать одну фичу «в лоб» только из прошлых игр; сравнить с пайплайном (допуск — float epsilon).

### 2.3 Старт сезона и холодный старт

- Для первых K игр команды в выборке признаки из rolling N игр будут NaN или неполными.
**Политика (зафиксировать в конфиге):**

- `min_games_for_features = K` (например 3 или 5): если за последние N игр доступно меньше K прошлых матчей — строка матча **дропается** из обучения/скоринга **или** заполняется медианой лиги (хуже для интерпретации, лучше для покрытия). Рекомендация: **дроп** для обучения; для скоринга в проде — явный флаг «мало данных» и консервативный прогноз (например, не отдавать вероятность или отдавать с широким disclaimer).

## 3. Каталог признаков v1 (реализуемые из текущей схемы)

Источники: [t.games.sql](data_tables/t.games.sql), [t.game_team_stats.sql](data_tables/t.game_team_stats.sql). Опционально позже: [t.teams_stats.sql](data_tables/t.teams_stats.sql), вратари.

Обозначения: для команды C на дату матча считаем rolling по **предыдущим** играм C.

### 3.1 Исходы и голы (самые сильные простые сигналы)

| Имя фичи (пример) | Описание | Параметры |
|-------------------|----------|-----------|
| `gf_roll_mean_N` | Среднее голов забитых за последние N игр | N ∈ {5, 10, 20} |
| `ga_roll_mean_N` | Среднее пропущенных | то же |
| `gf_roll_std_N` | Волатильность забитых (опционально) | малый N осторожно |
| `goal_diff_roll_mean_N` | Средняя разница gf − ga | |

Для **матча** формируются пары: `home_gf_roll_mean_N`, `away_gf_roll_mean_N`, плюс **разности** `diff_* = home − away` (часто сильнее для moneyline).

### 3.2 Штрафы и силовые (из game_team_stats)

| Имя | Описание |
|-----|----------|
| `pp_pct_roll_mean_N` | rolling среднее `power_play_percentage` |
| `pp_opps_roll_mean_N` | rolling `power_play_opportunities` |
| `pim_roll_mean_N` | rolling `pim` |

Нюанс: проценты могут быть шумными при малых выборках; можно клиппинг [0,1] и ограничить N.

### 3.3 Броски и активность

| Имя | Описание |
|-----|----------|
| `shots_for_roll_mean_N`, `shots_against_roll_mean_N` | через головы соперника в прошлых матчах или join по game_id для «against» |

Реализация «shots against»: для каждой прошлой игры команды A взять `shots` соперника из той же игры (join `games` + вторая строка `game_team_stats`).

### 3.4 Контекст расписания (из дат games)

Для команды перед матчем на день D:

| Имя | Описание |
|-----|----------|
| `rest_days` | D − day предыдущей игры команды (клип 0..14) |
| `is_b2b` | 1 если вчера была игра |
| `games_last_7d` | число игр за 7 дней |

Считается только по прошлым играм; для первой игры сезона — политика по умолчанию (NaN → дроп или заполнение).

### 3.5 Специфика для `y_over_5_5`

Дополнительно к разностям для moneyline полезны **симметричные** сигналы темпа:

- `expected_pace = home_gf_roll + away_gf_roll` (или + `ga` соперников как proxy открытости).
- `defense_sum = home_ga_roll + away_ga_roll`.
- Взаимодействия можно оставить модели бустинга; для логрега — явные произведения 2–3 пар (осторожно с мультиколлинеарностью).

### 3.6 Нормализация

- **LightGBM/CatBoost:** часто не нужен строгий scaler; важны типы (categorical vs float).
- **LogisticRegression:** `StandardScaler` на **train** фолде только, тот же transform на val/test.

### 3.7 Категориальные признаки

- `home_team_id`, `away_team_id` как категории: сильно увеличивают число параметров; для логрега — one-hot с регуляризацией или таргет-энкодинг с **внутрифолдовым** сглаживанием (иначе утечка). Для CatBoost — нативные категориальные.
- Рекомендация v1: **без** team_id в логреге; только числовые rolling + rest/b2b. Добавить team эффекты в v1.5 после стабильного baseline.

## 5. Сплиты, CV и тюнинг

### 5.1 Запрещённые методы

- `KFold(shuffle=True)`, `StratifiedShuffleSplit` по матчам — **нельзя** (утечка будущего в прошлое внутри сезона).

### 5.2 Рекомендуемый протокол

**Walk-forward по времени:**

- Сортировка по `day`, затем `game_id`.
- Разбиение блоками: например по **месяцам календаря** или по фиксированному числу игр (10k матчей в train, 500 в test — подобрать под объём данных).

**Схема тюнинга гиперпараметров:**

- Внутри каждого train-окна: последний **внутренний** хвост как `val` для early stopping (бустинг) и выбора гиперпараметров.
- Итоговая оценка: **роллинг** по нескольким тестовым окнам; усреднение log loss / Brier / ECE.

**Embargo (опционально):** если когда-нибудь появятся признаки с «липким» эффектом на границе, между train и test оставить зазор в 1 день; для текущих rolling-фич обычно не обязателен.

### 5.3 Финальный holdout

- Один **полностью удержанный** интервал (например последние 15–20% календарного времени последнего сезона в данных) — **ни разу** не участвует ни в тюнинге, ни в обучении калибратора. На нём только финальный отчёт: inference цепочки `raw → calibrator`, обученной на более ранних срезах.

## 6. Семейства моделей: детали реализации

### 6.1 Logistic Regression (baseline)

- `sklearn.linear_model.LogisticRegression` с `solver='lbfgs'` или `'saga'`, **`penalty='l2'`**, подбор `C` по сетке на временном val (например `C ∈ {0.01, 0.1, 1, 10}`).
- `max_iter` достаточно большой (5000+).
- **Калибровка:** часто не обязательна как отдельный шаг; можно всё равно применить изотонику на holdout для честного сравнения с бустингом.

**Когда «лучше»:** малый N, нужна интерпретируемость, мало категориальных признаков.

### 6.2 LightGBM (primary candidate)

- `objective='binary'`, `metric='binary_logloss'`.
- Ключевые гиперпараметры для тюнинга: `num_leaves`, `min_data_in_leaf`, `feature_fraction`, `bagging_fraction`, `lambda_l1/l2`, `learning_rate`, `n_estimators` с **early stopping** по val logloss.
- **`class_weight` или `is_unbalance`:** по эксперименту на home-win (лёгкий дисбаланс).

**Когда «лучше»:** нелинейности, взаимодействия, средний/большой объём строк.

### 6.3 CatBoost (альтернатива, особенно с team_id)

- Нативные категориальные; ordered boosting снижает смещение.
- Тюнинг: `depth`, `learning_rate`, `l2_leaf_reg`, `iterations` + early stopping.

**Когда «лучше»:** много категорий, шумные фичи, меньше ручной настройки препроцессинга.

### 6.4 XGBoost

- Сопоставим с LightGBM; чуть тяжелее настройка на малых данных. Иметь как опцию, не как обязательный первый шаг.

### 6.5 Random Forest

- `predict_proba` → обязательна калибровка (§7). Использовать как третью модель в **stacking** или не использовать в v1.

### 6.6 Naive Bayes, SVM, MLP

- **Не включать** в основной трек; при желании один раз замерить как «нижняя граница» для отчёта.

### 6.7 Stacking (v2)

- Уровень 0: OOF-предсказания логрега и LGBM/Cat по **временным** фолдам (те же сплиты, что и для оценки).
- Уровень 1: логрег на двух вероятностях + (опционально) исходные 3–5 сильных фич.
- **Опасность:** если OOF сделаны на том же окне, что и мета-обучение, нужен **ещё один** внешний тест. Проще: stacking обучать только на последнем большом train и проверять на holdout.

## 7. Калибровка вероятностей

### 7.1 Зачем

Деревья и бустинг часто дают **ранжирование** лучше, чем **калибровку**: бины с предсказанным p=0.7 могут иметь эмпирическую частоту 0.55. Для перевода в «коэффициенты» и сравнения с рынком нужна калибровка.

### 7.2 Методы

| Метод | Когда использовать |
|--------|---------------------|
| **Platt scaling** | Мало данных на калибровке; нужна гладкая кривая |
| **Isotonic regression** | Больше данных; гибкая монотонная карта |
| **Temperature scaling** | Чаще для нейросетей; для таблички опционально |

### 7.3 Протокол без утечки

- Сырой классификатор обучается на `train`.
- **Калибратор** обучается на **отдельном** наборе: `calibration` slice (например следующий временной блок после train), используя **предсказания** сырой модели на этом слайсе и истинные y.
- **Финальная оценка** — на `test` / holdout: цепочка `raw → calibrator`.

**В sklearn:** использовать совместимый с текущей версией API калибровки и явно разделять наборы (`train` для сырой модели, отдельный `calibration` для калибратора, `test/holdout` только для оценки). Реализацию обернуть в явные функции, чтобы не перепутать срезы.

### 7.4 Сохранение артефакта

Сохранять **оба**: `model_raw` + `calibrator` (или один pipeline). В конфиге фиксировать тип калибратора и дату обучения.

## 8. Метрики и отчёты

### 8.1 Основные

- **Log loss:** `-mean(y log(p) + (1-y)log(1-p))` с клиппингом p в [ε, 1−ε], ε ~ 1e-15.
- **Brier:** `mean((p - y)^2)`.

### 8.2 Калибровка

- **Reliability diagram:** разбить предсказания по квантилям или фиксированным бинам (10 бинов), для каждого бина средний p vs доля y=1.
- **ECE (expected calibration error):** среднее по бинам `|acc_bin - conf_bin| * w_bin` где `w_bin` — доля точек в бине.

### 8.3 Дополнительно

- **ROC-AUC** — для полноты; не оптимизировать как главную.
- **Покомандные ошибки (диагностика):** средний log loss по командам с малым числом игр — выявить переобучение на редкие команды.

### 8.4 Bootstrap

- 1000 resample по матчам **внутри тестового окна** для 95% ДИ log loss / Brier; отчёт в markdown/json рядом с артефактами.

---

## 9. От вероятности к коэффициенту

**Fair decimal odds** для исхода с вероятностью p: `odds = 1/p`.

Для двух исходов без ничьей: нормализация `p_home + p_away = 1` (вторая вероятность `1 - p` при бинарной постановке).

**С маржей букмекера** модель не обязана совпадать; для сравнения с линией позже: devigging (например пропорциональное удаление маржи из подразумеваемых вероятностей).

## 12. Критерии приёмки (Definition of Done) для фазы моделирования

1. Воспроизводимый скрипт: от пустого артефакта до обученной модели одной командой (`make` target или `python -m modeling.cli train`).
2. Автотест: для синтетического или урезанного датасета проверка **shift(1)** / эквивалента в SQL.
3. Отчёт по holdout: log loss, Brier, ECE до и после калибровки; reliability PNG в `artifacts/reports/`.
4. Файл метаданных: версия фич, диапазон дат, число строк train/cal/test, git commit hash.
5. Для обеих задач (home win и over 5.5) — отдельные артефакты или явная multitask-реализация с теми же критериями.

## 14. Риски

- **Non-stationarity:** правила лиги, уровень голов, ОТ — меняются; retrain по сезонам обязателен.
- **Отсутствие рынка в данных:** низкий log loss на исходах ≠ деньги; при появлении коэффициентов — отдельный слайс метрик (market log loss, CLV).
- **Неучтённые факторы:** стартовый вратарь, травмы звёзд, мотивация плей-офф — без данных останутся в шуме.

## 15. Чеклист этапов работ (порядок выполнения)

1. Реализовать `labels.py` + unit-тест на нескольких известных `game_id` из БД.
2. Реализовать `features.py` с одним окном N=10 и политикой `min_prior_games`.
3. Walk-forward split + baseline logreg + отчёт метрик.
4. LightGBM или CatBoost + early stopping + сравнение с logreg.
5. Калибровка + финальный holdout + bootstrap ДИ.
6. (Опционально) stacking и/или team_id в CatBoost.
7. Упаковка артефактов и `make modeling-train` / документация в README фрагменте.
