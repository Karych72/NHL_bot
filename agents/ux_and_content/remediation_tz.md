## Задача A — Push-уведомления (7.6), блокер

**Цель:** не только документ в `telegram_bot/push_subscriptions.py`, а рабочий минимум.

**Сделать:**

1. Схема хранения (PostgreSQL рядом с БД бота) по полям и уникальности из docstring `push_subscriptions.py`; миграция или SQL-скрипт в репозитории.
2. Команды или кнопки **opt-in** («Подписаться») и **отписка** («Отписаться» / `/unsubscribe` — на усмотрение, но явно в `/help`).
3. Отправка утреннего дайджеста и/или уведомлений по команде — вынести в вызываемый из cron/worker скрипт или job; использовать ту же логику контента, что и дайджест в боте (`day_digest` / `dispatch_day_digest_messages`), с флагами **`attach_conv_nav_on_last=False`** для рассылки (как описано в `push_subscriptions.py`).
4. Ограничение нагрузки: батчи, backoff при `429`, не слать при блокировке бота (обрабатывать ошибки API).
5. Кратко описать в `docs/telegram_bot.md` (или существующем doc): модель данных, что хранится (`chat_id`, `kind`, `team_id`), откуда берётся согласие и как отписаться.

**Приёмка:**

- Пользователь может подписаться и отписаться; в БД нет «висячих» строк без понятного жизненного цикла.
- Рассылка не нарушает лимиты в наивной реализации (ничего бесконечного в одном цикле без пауз).
- `/help` упоминает подписки и отписку.

## Задача C — Промпт даты дайджеста: «Назад»

**Файлы:** `telegram_bot/stats_handlers.py` (`bot_digest_pick_date_prompt`), `telegram_bot/bot.py` (`ConversationHandler`, состояние `THIRD`).

**Сделать:** после запроса даты показывать inline-кнопку **«Назад»** (callback на состояние меню выбора даты `bot_digest_date_menu` или на `CHOOSE_STATS` — согласовать с UX: логичнее вернуть на экран «Сегодня / Вчера / Выбрать дату»). Зарегистрировать обработчик в `THIRD` (и при необходимости не ломать `MessageHandler` для произвольного текста).

**Приёмка:** пользователь не обязан помнить `/cancel`, чтобы выйти с шага ввода даты.

## Задача D — Экранирование / единый формат разметки

**Файлы:** `telegram_bot/bot_messages.py`, `telegram_bot/messages/*.txt`, хендлеры с `parse_mode`.

**Вариант 1 (предпочтительно для согласованности с 7.7):** перевести лидерборды и карточку матча на **HTML** (`html.escape` для всех пользовательских строк из БД), обновить шаблоны под безопасные теги (`<b>`, `<pre>` где нужны колонки).

**Вариант 2:** оставить Markdown и ввести функцию экранирования для Telegram MarkdownV2 или legacy Markdown (зависит от того, что сейчас используется в `parse_mode`).

**Приёмка:**

- ФИО с дефисами, апострофами и т.п. не ломают сообщение.
- Нет сырого HTML от пользователя без escape в режиме HTML.
