## 1. Принцип ревью

Приоритет:

1. **Корректность статистической процедуры** — особенно block bootstrap по `day` для holdout (резмер выборки дней = `D`, целые дни как блоки, без ресемплинга внутри дня).
2. **Воспроизводимость** — единый `random_seed` из YAML, **независимые seeds запрещены** (это явное требование UPDATE-плана), отсутствие глобального `np.random.seed(...)`.
3. **Изоляция от рантайма / БД** — bootstrap-код не тянет PostgreSQL и не делает скрытую параллелизацию.
4. **Минимальный скоуп MR** — этап 6 не должен расширять `modeling/metrics.py` за пределы того, что описано в этапе 5, и не должен трогать этапы 7–10.

Если хоть один из пунктов §3–§5 ниже нарушен — **request changes** с указанием конкретного места в коде/тесте.

## 2. Размещение и публичный API

- [ ] Реализация лежит **в одном** из двух мест: `modeling/metrics.py` (расширение) **или** `modeling/bootstrap.py` (новый файл, импортирующий метрики). Дублирования формул `log_loss` / `brier` между файлами нет.
- [ ] Публичная функция bootstrap принимает: `y_true`, `y_pred`, `day` (опционально), `n_resamples: int`, `block_by_day: bool`, `seed: int`, `metric_fns: Mapping[str, Callable]`, `num_threads: int = 1`. Имена допустимо уточнять, но семантика — фикс.
- [ ] Возвращаемая структура (`BootstrapResult` / `dict`) сериализуема в JSON и содержит ровно: `metric_name`, `point`, `ci_low`, `ci_high`, `n_resamples`, `block_by_day`, `seed`. Лишних полей нет (особенно — никаких рантайм-полей вроде `wall_time`, `cpu_id`).
- [ ] Дефолты совпадают с UPDATE-планом: `n_resamples=1000`, `num_threads=1`. В docstring явно сказано: для `holdout` — `block_by_day=True`, для `test_k` — `block_by_day=False`.

## 3. Корректность алгоритма

### 3.1 i.i.d. resampling (`test_k`)

- [ ] Используется **один** `np.random.Generator`, инициализированный через `np.random.default_rng(seed)`. Никаких `np.random.seed(...)`, `np.random.RandomState(...)`, `random.seed(...)` нигде в bootstrap-коде.
- [ ] На каждом ресемпле: `idx = rng.integers(0, n, size=n)` (с возвратом, размер = исходному `n`). **Не** `rng.choice(n, n, replace=False)` (это перестановка, а не bootstrap).
- [ ] Метрики считаются как `metric_fns[name](y_true[idx], y_pred[idx])` — для каждой метрики на **тех же** ресемплированных индексах одного шага (а не по разным `idx` для разных метрик).
- [ ] Точечная оценка `point` — прямой вызов `metric_fns[name](y_true, y_pred)` на исходных массивах (без ресемпла). Тестом подтверждено совпадение с прямым вызовом метрики.

### 3.2 Block bootstrap по `day` (`holdout`)

- [ ] Группировка по `day` детерминирована: ключи отсортированы по возрастанию. Конвертация `day` → `datetime` локальная, без побочных эффектов на входной DataFrame.
- [ ] На каждом ресемпле выбирается `D` индексов дней с возвратом (`D` = число уникальных дней в исходных данных). **Не** меньшее число, **не** «random subset» без замены.
- [ ] Для каждого выбранного дня **все строки этого дня целиком** включаются в ресемпл (block-структура). Никакого ресемплинга **внутри** дня.
- [ ] Итоговый ресемпл — `np.concatenate([day_to_idx[sorted_days[i]] for i in day_choice])`. Метрика считается на полученных `(y_true[idx_b], y_pred[idx_b])`.
- [ ] **Edge case D = 1** → `BootstrapError` с понятным сообщением. **Тихая деградация до i.i.d. — блокер.**
- [ ] **Edge case `day` содержит NaT/None** → `BootstrapError`. Не игнорируется молча.

### 3.3 ДИ

- [ ] Используется **перцентильный метод**: `np.quantile(m_resamples, 0.025)` и `0.975`. BCa, t-bootstrap, нормальные ДИ — в v1 нет (если есть — блокер: вне скоупа UPDATE-плана).
- [ ] `n_resamples` равен фактическому числу ресемплов в результирующем массиве (нет молчаливого отбрасывания «битых» ресемплов; если ресемпл вызвал NaN — это сигнал ошибки в метрике, а не повод тихо пропустить).

### 3.4 Контракт ошибок

- [ ] `n_resamples ≤ 0` → понятная ошибка.
- [ ] `len(y_true) != len(y_pred)` → ошибка.
- [ ] `y_true` содержит значения вне `{0, 1}` → ошибка (UPDATE-план оперирует только бинарными метками).
- [ ] `block_by_day=True` без `day` → ошибка.
- [ ] Все исключения — с понятным сообщением (`BootstrapError` или явный `ValueError`, не голый `assert`).

## 4. Воспроизводимость (сквозное требование)

- [ ] В коде bootstrap **нигде** не создаётся отдельный seed (типа `seed + fold_index`, `seed * 31 + metric_id` и т.п.). Если есть фолд-специфичный seed — **блокер**. UPDATE-план: «`bootstrap_seed = random_seed`; независимые seeds запрещены».
- [ ] Запуск bootstrap **не меняет** глобальный `np.random.get_state()` (есть тест).
- [ ] Версии библиотек (`numpy`, `pandas`) фактически логируются в `metadata.json` (это делает CLI этапа 10, но bootstrap-функция отдаёт наверх все нужные поля результата — `bootstrap.N`, `bootstrap.block_by_day`, `bootstrap.seed`).

## 5. Изоляция и потоки

- [ ] Файл с bootstrap-кодом **не** импортирует `psycopg2`, `modeling.dataset_builder.*`. Это легко проверить grep'ом и/или AST-тестом из этапа 11 (минимум — нет таких импортов).
- [ ] Никаких `os.cpu_count()`, `multiprocessing.cpu_count()`, `joblib.parallel_backend(..., n_jobs=-1)` под капотом. Если используется параллелизация — `n_jobs` / `num_threads` явно берётся из параметра функции (= `compute.num_threads` из YAML).
- [ ] Никаких прямых обращений к `os.environ["OMP_NUM_THREADS"]` и т.п. внутри bootstrap-модуля.
- [ ] По умолчанию — последовательный однопоточный цикл. Параллелизация — опциональна и явна.

## 6. Тесты

В `tests/test_modeling_bootstrap.py` (или соответствующее расширение `tests/test_modeling_metrics.py`):

- [ ] **Детерминизм при фиксированном seed:** два независимых вызова с одинаковым `seed` дают попарно идентичные `point`, `ci_low`, `ci_high` (`np.testing.assert_allclose` с `atol=0`).
- [ ] **Чувствительность к seed:** разные `seed` → разные ДИ (защита от случайно зашитого внутри функции seed).
- [ ] **`point` ≡ прямой метрике:** на исходных `(y_true, y_pred)` `point` совпадает с прямым вызовом `metric_fns[name](y_true, y_pred)` — `np.testing.assert_allclose(atol=1e-12)`.
- [ ] **Покрытие i.i.d. ДИ:** на синтетике истинное значение попадает в 95% ДИ в **≥ 90%** прогонов из 20–50 seed'ов (мягкая граница против flakiness; точный порог задокументирован в комментарии теста).
- [ ] **Block vs i.i.d.:** на синтетике с сильной внутри-дневной зависимостью block bootstrap даёт **шире** ДИ, чем i.i.d. на тех же данных. Это качественная проверка (`ci_high − ci_low` block > i.i.d.).
- [ ] **Edge cases:** `D=1`, `NaT in day`, `n_resamples=0`, `len(y_true) != len(y_pred)`, `y_true ∉ {0,1}` — каждый кейс падает с понятной ошибкой.
- [ ] **Отсутствие глобального state:** `np.random.get_state()` совпадает до и после вызова bootstrap (нет `np.random.seed(...)` под капотом).
- [ ] **Сериализация результата:** `dataclasses.asdict(result)` (или эквивалент) даёт dict, который проходит через `json.dumps` без ошибки.

Если хоть один из пунктов выше отсутствует — **request changes**.

- [ ] Если исполнитель выбрал §3.6.1 ТЗ (минимальная реализация `log_loss`/`brier` в `modeling/metrics.py` ради зависимости) — там действительно **только** `log_loss` и `brier`. **Никаких** ECE, reliability, breakdown по командам, тривиального baseline в этом MR быть не должно — это этап 5.
- [ ] `log_loss` (если добавлен в этом MR) использует клип `p ∈ [ε, 1−ε]`, `ε` по умолчанию `1e-15`, имя параметра — `epsilon_clip` (как в YAML).

## 10. Сквозные требования UPDATE-плана (чеклист)

- [ ] **Источник истины фич**: bootstrap не работает с манифестом напрямую; проверка не дублируется (см. §2 ТЗ исполнителя).
- [ ] **Воспроизводимость**: `bootstrap_seed = random_seed`, независимые seeds запрещены (см. §4).
- [ ] **Лимит потоков**: `num_threads` — параметр, по умолчанию 1 (см. §5).
- [ ] **Логи**: bootstrap отдаёт `bootstrap.N`, `bootstrap.block_by_day`, `bootstrap.seed` наверх (см. §2).
- [ ] **`<run_id>`**: bootstrap не зависит от времени и не генерирует id.
- [ ] **Никакого доступа к PostgreSQL**: проверено grep'ом / AST-тестом (см. §5).

## 11. Вердикт

**approve / approve with nits / request changes.**

**Блокеры:**

- независимые seeds (любой seed, не равный `random_seed` напрямую) внутри bootstrap-кода;
- глобальный `np.random.seed(...)` или мутация `np.random.get_state()`;
- тихая деградация block bootstrap до i.i.d. при `D=1`;
- ресемплинг внутри дня в режиме `block_by_day=True` (нарушает блочную структуру);
- размер выборки дней в block bootstrap ≠ `D` (искажает ширину ДИ);
- дублирование формул `log_loss` / `brier` между bootstrap-модулем и `modeling/metrics.py`;
- BCa / t-bootstrap / нормальные ДИ вместо перцентильного метода;
- использование `os.cpu_count()` / `joblib(-1)` / `OMP_NUM_THREADS` без явного `num_threads`;
- импорт `psycopg2` или `modeling.dataset_builder.*` в файле с bootstrap;
- в MR есть посторонняя работа из этапов 5 (сверх минимума `log_loss`/`brier`), 7–10.

**Ниты:**

- стиль docstring и расположение раздела документации (`docs/modeling_training.md` vs docstring);
- имена внутренних переменных (`rng`, `idx`, `day_to_idx` и т.п.);
- выбор между `dataclass` и `TypedDict` для результата — оба варианта допустимы, важно лишь, что результат сериализуем в JSON;
- формат сообщений `BootstrapError` (без потери информации о причине).
