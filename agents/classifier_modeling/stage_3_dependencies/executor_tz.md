## 1. Цель этапа

Завести **отдельный файл зависимостей для обучения классификаторов** и **отдельную цель в `Makefile`** так, чтобы:

- весь ML-стек (LightGBM, scikit-learn, matplotlib и т.п.) ставился **только** при работе над моделированием;
- зависимости моделирования **не попадали** в `requirements.txt`, в Docker-образ бота и в обычный `make setup` / `make run-bot`;
- состав версий библиотек был зафиксирован и пригоден для логирования в `metadata.json` артефактов (см. «Сквозные требования», п. о воспроизводимости).

Никакого кода обучения, конфигов YAML, сплитов, метрик и CLI `train` в этом этапе не добавляется — только файл зависимостей, цель `Makefile`, минимальная синхронизация документации и smoke-проверка установки.

---

## 2. Объём работ

### 2.1 Файл `requirements-modeling.txt`

Создать в корне репозитория файл `requirements-modeling.txt` со следующим составом (порядок — для читаемости, имена пакетов — канонические из PyPI):

- `numpy`
- `pandas`
- `scikit-learn`
- `lightgbm`
- `matplotlib`
- `pyyaml`
- `joblib`

Требования к файлу:

- **CatBoost не добавлять.** Согласно UPDATE-плану, CatBoost в v1 не используется и переезжает в этап 15 (опциональный отдельный файл зависимостей вроде `requirements-modeling-catboost.txt` — **вне скоупа** этого этапа).
- Версии **зафиксировать** (pin) — минимум для `scikit-learn`, `lightgbm`, `numpy`, `pandas`, `matplotlib`, `pyyaml`, `joblib`. Это нужно для воспроизводимости и для согласованного логирования версий в `metadata.json` артефактов (см. сквозное требование о воспроизводимости в UPDATE-плане).
- Формат пинов — как в существующих `requirements-dev.txt` / `requirements.txt` (точное `==` или допустимый диапазон, согласованный с уже выбранным стилем проекта; если в `requirements.txt` пины не жёсткие, всё равно зафиксировать конкретные совместимые версии в `requirements-modeling.txt`, чтобы прогон обучения воспроизводился).
- В начало файла — короткий комментарий (1–3 строки): назначение файла, ссылка на `make modeling-dev`, явное напоминание, что это **не runtime-зависимости бота** и они **не попадают в Docker**.
- Файл должен корректно ставиться на ту же версию Python, что используется в проекте (`python3` через `.venv`, см. текущий `Makefile`).

### 2.2 Цель в `Makefile`

В существующий [`Makefile`](../../../Makefile) добавить цель `modeling-dev`:

- цель должна гарантировать, что виртуальное окружение `.venv` собрано (как минимум зависеть от `setup`, как это сделано у других целей);
- основное действие: `$(PIP) install -r requirements-modeling.txt`;
- цель добавить в `.PHONY` рядом с существующими;
- название должно быть ровно `modeling-dev` (как в UPDATE-плане), чтобы не разъезжаться с документацией.

Категорически:

- **Не** включать `-r requirements-modeling.txt` в цели `setup`, `setup-dev`, `run-bot`, `ci-local` или в любые другие цели, относящиеся к рантайму бота / CI бота.
- **Не** менять состав `requirements.txt` и `requirements-dev.txt` в рамках этого этапа.

### 2.3 Изоляция от Docker-образа бота

- Убедиться, что `requirements-modeling.txt` **не** упоминается ни в `Dockerfile`, ни в `docker-compose.yml`.
- Если требуется, добавить запись в `.dockerignore`, чтобы файл `requirements-modeling.txt` (или любые случайно собранные локально артефакты обучения) не утекали в контекст сборки бота. Минимальная цель: образ бота, построенный по текущему `Dockerfile`, **не** содержит `lightgbm`, `scikit-learn`, `matplotlib`.

### 2.4 Документация

- В [`DEVELOPMENT.md`](../../../DEVELOPMENT.md) (или в `docs/modeling_dataset_builder.md` / новом `docs/modeling_training.md` — на усмотрение, главное, чтобы было discoverable из документации моделирования) добавить **короткий** раздел: «Зависимости моделирования», где явно указано:
  - что для обучения используется отдельный файл `requirements-modeling.txt`;
  - как его поставить: `make modeling-dev`;
  - что эти зависимости **не** входят в `requirements.txt` и **не** попадают в Docker-образ бота;
  - что CatBoost в v1 не используется (вынесен в этап 15 UPDATE-плана).
- В `README.md` менять ничего обязательного не требуется; если уже есть раздел про модели — поставить ссылку на новый абзац.

### 2.5 Smoke-проверка

Локально один раз выполнить (для подтверждения работоспособности, не оставлять как отдельный артефакт):

- `make modeling-dev` отрабатывает без ошибок;
- после установки `python -c "import numpy, pandas, sklearn, lightgbm, matplotlib, yaml, joblib; print('ok')"` печатает `ok`;
- `make setup` (свежий) в чистом окружении **не** ставит `lightgbm`, `scikit-learn`, `matplotlib`.

Результаты smoke-проверки кратко описать в описании MR (одной таблицей или списком).

## 3. Сквозные требования (обязательно учесть)

Из раздела «Сквозные требования» UPDATE-плана на этом этапе релевантно:

- **Воспроизводимость и логирование версий**: версии `sklearn`, `lightgbm`, `pandas`, `numpy` должны быть пинованы — иначе будущий этап (обучение) не сможет честно логировать их в `metadata.json` артефакта. Не оставлять незакреплённые верхние границы для основных ML-библиотек.
- **Лимит потоков** (`compute.num_threads`, прокидывается в `n_jobs` sklearn и `num_threads` LightGBM): на уровне зависимостей достаточно того, что `scikit-learn` и `lightgbm` реально установлены и работают; никаких глобальных env-переменных (`OMP_NUM_THREADS` и т.п.) в `Makefile` цели `modeling-dev` **не** хардкодить.
- **Никакого доступа к PostgreSQL в train-коде**: на уровне зависимостей это означает, что в `requirements-modeling.txt` **не должно быть** `psycopg2*` и других БД-драйверов. Train-зависимости — только то, что нужно для офлайн-обучения по уже собранным CSV/JSON артефактам датасета.

## 4. Критерии приёмки

1. Файл `requirements-modeling.txt` создан в корне репозитория, содержит `numpy`, `pandas`, `scikit-learn`, `lightgbm`, `matplotlib`, `pyyaml`, `joblib` с зафиксированными версиями; **не** содержит `catboost`, `psycopg2*`, бот-специфичных пакетов.
2. В `Makefile` есть цель `modeling-dev`, которая ставит зависимости из `requirements-modeling.txt`; цель добавлена в `.PHONY`. `setup`, `setup-dev`, `run-bot`, `ci-local` остались без изменений по составу зависимостей.
3. Docker-образ бота, собранный по текущему `Dockerfile`, **не** содержит ML-зависимостей моделирования; `requirements-modeling.txt` не упомянут в `Dockerfile` / `docker-compose.yml`.
4. В документации (`DEVELOPMENT.md` или соответствующий док-файл моделирования) есть короткий абзац о `requirements-modeling.txt` и `make modeling-dev`, явно сказано о неучастии в runtime бота и о том, что CatBoost — в этапе 15.
5. Smoke-проверка из §2.5 выполнена, результаты приложены к MR.

## 5. Ограничения и вне скоупа

- **Только** зависимости и `Makefile`. Никаких новых модулей в `modeling/`, никакого кода для конфигов, сплитов, метрик, обучения, калибровки и CLI `train` (это этапы 2 и 4–10 UPDATE-плана).
- **Никаких** изменений `requirements.txt` и `requirements-dev.txt`, кроме обоснованных мелочей (например, опечатка/дубль). Любая такая правка — отдельным абзацем в описании MR.
- **Не** добавлять `requirements-modeling-catboost.txt`, Optuna и любые опциональные зависимости из §15 UPDATE-плана.
- **Не** добавлять глобальные env-переменные (`OMP_NUM_THREADS`, `MKL_NUM_THREADS` и т.п.) и не настраивать BLAS — потоки задаются на уровне YAML конфига моделирования в последующих этапах.
- Версии Python и системные библиотеки не трогаются.
