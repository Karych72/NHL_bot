# ТЗ для ревьюера: этап 1 — контракт входа для обучения

**Роль:** независимый reviewer.  
**Источник:** [`plan/classifier/nhl_classifier_modeling_plan_UPDATE.md`](../../../plan/classifier/nhl_classifier_modeling_plan_UPDATE.md), раздел «### 1. Использование уже готового контракта входа», с учётом «## Сквозные требования (читать перед каждым этапом)».  
**Пара ТЗ для исполнителя:** [`executor_tz.md`](executor_tz.md).

Пути — от корня репозитория.

---

## 1. Принцип ревью

Приоритет: **однозначность контракта**, **отсутствие скрытых эвристик** для состава \(X\), **согласованность с `modeling/dataset_builder/schema.py`**, предсказуемые ошибки при битых входах, тестируемость.

---

## 2. Контракт и документация

- [ ] В документации (`docs/modeling_dataset_builder.md` или отдельный короткий файл со ссылкой из него) явно указаны: файл таблицы train, обязательный `metadata_train.json`, обязательные поля **`feature_manifest`**, **`features_hash`**, **`feature_set_version`** в контексте обучения.
- [ ] Поддерживаемый формат таблицы на v1 зафиксирован (CSV; parquet — только если реально добавлен и описан).

---

## 3. Загрузчик

- [ ] Публичный API загрузки понятен из названий и docstring (что на входе, что на выходе).
- [ ] Матрица признаков \(X\) строится **по манифесту** (имена и порядок колонок), а не как «все колонки минус известные ключи» без опоры на манифест.
- [ ] Ключи, метки и служебные колонки согласованы с `schema.KEY_COLUMNS`, `schema.LABEL_COLUMNS`, `schema.SERVICE_COLUMNS` (или явный импорт/обёртка без расхождения констант).
- [ ] При неконсистентности таблицы и манифеста (лишние/пропавшие признаки, неверный порядок для обучения — по политике ТЗ) поведение документировано и покрыто тестом.
- [ ] Переиспользуются существующие хелперы из `schema.py` там, где это уместно (parity, dtype), без дублирования расходящихся списков колонок.

---

## 4. Тесты

- [ ] Есть тест успешной загрузки на синтетических данных (минимальный CSV + JSON).
- [ ] Есть тест негативного сценария (несовместимость с манифестом или отсутствие обязательных полей метаданных).

---

## 5. Скоуп

- [ ] В MR нет несвязанных этапов UPDATE-плана (конфиг modeling, сплиты, метрики, train CLI и т.д.), кроме минимальных импортов/заготовок, если они явно нужны для загрузчика.

---

## 6. Вердикт

**approve / approve with nits / request changes**.

**Блокеры:** состав \(X\) определяется эвристиками по именам колонок вместо манифеста; расхождение констант ключей/меток с `schema.py`; отсутствие fail-fast при битом JSON; отсутствие тестов на позитив и негатив.

**Ниты:** формулировки документации, именование модуля/API, стиль логирования при игноре колонок (если исполнитель выбрал не fail-fast для части случаев — проверить обоснованность).
