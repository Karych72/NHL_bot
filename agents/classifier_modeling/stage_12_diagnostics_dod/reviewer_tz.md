## 1. Принцип ревью

Приоритет:

1. **Корректность гейта baseline-check** — строгое (`<`, не `<=`) улучшение log loss лучшего семейства над `trivial_base_rate` на holdout; верный выбор семейства-победителя; верный статус прогона.
2. **Честность диагностики** — отсутствующие артефакты/поля `metadata.json`/секции отчёта **никогда** не дают `status: ok`. Молчаливая деградация — блокер.
3. **Слой приёмки не дублирует и не переписывает этапы 4–10** — он только читает их результат. Пересчёт метрик/ДИ/reliability внутри этапа 12 — блокер.
4. **Изоляция от рантайма/БД** — никакого PostgreSQL, `dataset_builder`, скрытых пулов потоков.

Если хоть один из пунктов §3–§6 ниже нарушен — **request changes** с указанием конкретного места в коде/тесте.

---

## 2. Размещение и API

- [ ] Логика приёмки лежит **в одном** месте: `modeling/acceptance.py` (рекомендуется) **или** выделенные функции в `modeling/cli.py`. Не размазана по обработчику команды неразрывно с обучением.
- [ ] Функции слоя приёмки чистые и тестируемые: гейт принимает уже посчитанные holdout-метрики, диагностика принимает `run_id`/пути и читает диск. Нет «походов» за сырыми данными или повторного обучения.
- [ ] Слой приёмки **не** пересчитывает log loss / Brier / ECE / ДИ / reliability — берёт значения из `metrics.json` / структур этапов 5/6/10. Любой собственный расчёт метрики — блокер (дублирование с этапом 5/6).

---

## 3. Гейт baseline-check (пункт 6 DoD)

- [ ] Критерий — **строгое** улучшение: `logloss(model_final лучшего семейства) < logloss(trivial_base_rate)`. Наличие `<=` вместо `<` — **блокер** (план требует «строго улучшать»).
- [ ] Сравнение — на **holdout**, для калиброванной цепочки `model_final → calibrator_final`, с тем же `epsilon_clip`, что и у метрик этапа 5. Сравнение с сырой (некалиброванной) моделью или на test_k вместо holdout — блокер.
- [ ] **Лучшее семейство** выбирается по меньшему holdout log loss; тай-брейк при равенстве детерминирован и задокументирован.
- [ ] **Статус:** все включённые задачи прошли → `ok`; хотя бы одна не прошла → `failed_baseline_check`.
- [ ] В гейте участвуют **только** задачи с `tasks.<task>.enabled=true`. Отключённая задача не влияет на статус.
- [ ] Результат гейта (per-task: победитель, его log loss, log loss baseline, дельта, вердикт) виден в `summary.md` и `run.log`; машиночитаемый блок есть в `metrics.json`.

---

## 4. Статус прогона, `summary.md` и код возврата

- [ ] `summary.md` содержит **грепаемую** строку `status: ok` либо `status: failed_baseline_check` в детерминированном месте.
- [ ] Случай «провалена диагностика артефактов» **не** маскируется под `status: ok`: используется либо отдельный статус (например, `failed_artifact_check`), либо жёсткое падение CLI до записи успешного отчёта. Решение задокументировано.
- [ ] При неуспешном статусе команда `train` возвращает **ненулевой** код возврата, но `summary.md`/`metrics.json` записаны (видна причина).
- [ ] При `status: ok` — код возврата `0`.
- [ ] Гейт baseline-check включён **по умолчанию**. Если есть отладочный флаг (`--no-fail-on-baseline` или аналог) — он меняет только exit-code, **не** записываемый `status`, и по умолчанию выключен.

---

## 5. Диагностика артефактов (пункты 1–5 DoD)

- [ ] **(DoD 1)** Проверяется наличие финальных моделей обеих включённых задач, walk-forward отчётов по фолдам, holdout-отчёта, reliability PNG. Пустой результат невозможен.
- [ ] **(DoD 3)** Для каждой включённой задачи проверяется наличие в holdout-отчёте: `log loss`, `Brier`, `ECE` **до и после** калибровки, ДИ из block bootstrap по дню, строки `trivial_base_rate`, reliability PNG, breakdown по командам. Проверяется **наличие**, а не пересчёт.
- [ ] **(DoD 4)** В `metadata.json` каждого артефакта проверяются **все** поля: `features_hash`, диапазоны дат `train/val/cal/test/holdout`, размеры выборок, версии `sklearn`/`lightgbm`/`pandas`/`numpy`, `git_commit` (или `null` без `.git`), `random_seed`, `<run_id>`. Отсутствие любого поля → понятный провал с указанием поля и файла.
- [ ] `features_hash` в `metadata.json` сверяется с `features_hash` прогона из `metadata_train.json`; расхождение → провал (сквозное требование «источник истины фич»).
- [ ] **(DoD 5)** Существуют отдельные `final/` для **обеих** задач и **обоих** семейств; `latest` — реальный симлинк, указывающий на актуальный `<run_id>/final/`. Проверяется, что это именно симлинк и что цель корректна.
- [ ] Любая нехватка артефакта/поля даёт **честный провал** (а не `status: ok`). Это ключевой блокер этапа.

---

## 6. Сквозные требования и изоляция

- [ ] Файл слоя приёмки **не** импортирует `psycopg2`, `modeling.dataset_builder.*`. Проверяется grep'ом / AST-тестом этапа 11.
- [ ] Слой приёмки **не** генерирует `<run_id>` и не зависит от текущего времени в логике гейта (детерминирован по входным метрикам).
- [ ] Никаких `os.cpu_count()`, скрытых пулов потоков, тяжёлых параллельных вычислений в слое приёмки — он читает готовое.
- [ ] Диагностика/гейт пишут в **тот же** `artifacts/reports/<run_id>/run.log`, а не заводят свой лог.
- [ ] Гейт детерминирован: на одних и тех же входных метриках всегда один и тот же `status`.

## 7. Тесты

В `tests/test_modeling_acceptance.py`:

- [ ] **Гейт — проход** (лучшее семейство строго лучше baseline по всем включённым задачам → `ok`).
- [ ] **Гейт — провал** (хотя бы одна задача не строго лучше → `failed_baseline_check`).
- [ ] **Граница строгости** (`logloss == baseline` → провал, не проход).
- [ ] **Выбор победителя** (меньший holdout log loss; детерминированный тай-брейк при равенстве).
- [ ] **Отключённая задача** не участвует в гейте.
- [ ] **Диагностика — успех** на корректной раскладке.
- [ ] **Диагностика — провалы по одному** (нет `final/`; нет поля `metadata.json`; нет reliability PNG; нет ДИ / `trivial_base_rate` / breakdown в отчёте; `latest` не симлинк или указывает не туда) — каждый кейс падает с понятной причиной.
- [ ] **`git_commit=null` без `.git`** — принимается, не считается провалом.
- [ ] **End-to-end smoke** на синтетическом мини-датасете: реальный прогон создаёт все артефакты DoD, пишет `status`, возвращает ожидаемый код возврата.
- [ ] **Код возврата** при `failed_baseline_check` — ненулевой, отчёты записаны.

Если хоть один пункт отсутствует — **request changes**.

## 11. Вердикт

**approve / approve with nits / request changes.**

**Блокеры:**

- `<=` вместо строгого `<` в критерии baseline (план требует строгого улучшения);
- сравнение с baseline на test_k вместо holdout или по некалиброванной модели;
- неверный выбор лучшего семейства / недетерминированный тай-брейк;
- отсутствующие артефакты или поля `metadata.json` дают `status: ok` (молчаливая деградация);
- неуспешный прогон возвращает код `0`;
- пересчёт метрик/ДИ/reliability внутри слоя приёмки (дублирование этапов 5/6);
- переписывание/перетягивание этапов 4–10 в этот MR;
- импорт `psycopg2` / `modeling.dataset_builder.*` в файле слоя приёмки;
- гейт baseline-check выключен по умолчанию.

**Ниты:**

- расположение раздела документации (`docs/modeling_training.md` vs docstring);
- имена статусов сверх `ok`/`failed_baseline_check` (например, `failed_artifact_check`) — допустимы, если задокументированы;
- стиль строки `status:` в `summary.md` (важно лишь, что она детерминированно грепается);
- имена внутренних функций/переменных слоя приёмки.
