# ТЗ для исполнителя: Фаза 2 — инфраструктура проекта

**Роль:** инженер-исполнитель.  
**Источник требований:** `plan/engineering/refactoring_plan_2.md`, раздел «Фаза 2».

---

## 1. Цель фазы

Добавить воспроизводимый контейнерный запуск и автоматическую проверку качества в CI.

---

## 2. Обязательные задачи

### 2.1 **2.3** — Docker

- Добавить **`Dockerfile`**, пригодный для сборки и запуска проекта (бот и/или связанные сервисы — по фактической структуре репозитория).
- Добавить **`docker-compose.yml`**, описывающий минимально полезный локальный стек (например, бот + зависимости; БД — если бот без неё не стартует).

Учесть переменные окружения из `.env.example`; секреты не коммитить.

### 2.2 **2.4** — GitHub Actions

- Добавить workflow(ы) в **`.github/workflows/`**: линтинг, проверка типов, тесты.
- Команды должны совпадать с принятыми в проекте (`Makefile`, `requirements.txt`, конфиги pytest/mypy/ruff и т.д. — использовать существующие, не изобретать параллельный стандарт).
- CI должен быть **детерминированным**: pinning версий runner-инструментов по возможности, воспроизводимая установка зависимостей.

Если CI уже частично есть — **расширить/выровнять** под план, не дублировать бессмысленно.

---

## 3. Критерии приёмки

1. `docker build` и `docker compose up` (или документированный эквивалент) работают на чистой машине при наличии `.env`.
2. Pipeline в GitHub Actions проходит на чистой ветке: линт, typecheck, тесты.
3. В `DEVELOPMENT.md` или `README.md` есть краткие шаги «как собрать / как прогнать CI локально» — **только если** исполнителю поручено обновлять документацию; иначе достаточно Makefile/README, уже существующих в репо.

---

## 4. Ограничения

- Не ломать существующие локальные workflow без причины.
- Не добавлять тяжёлые сервисы в compose без необходимости для запуска бота.
