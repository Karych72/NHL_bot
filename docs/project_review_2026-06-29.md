# Ревью проекта NHL_bot — плюсы, минусы, валидация плана

**Дата:** 2026-06-29
**Метод:** полное изучение проекта (~18k строк Python + SQL + планы/ТЗ), параллельный анализ трёх подсистем + ручная проверка ключевых фактов.

---

## Что это за проект

Три слабосвязанных контура вокруг одной PostgreSQL-схемы:

1. **`pipeline/`** — загрузчик NHL API → PostgreSQL (`load_season_modern.py`, монолит ~1543 строки).
2. **`telegram_bot/`** — бот на `python-telegram-bot` с меню `/stats`, лидербордами, карточками игр.
3. **`modeling/`** — ML-контур: прематч-классификаторы (победа дома, тотал O/U 5.5) на LightGBM + LogReg с walk-forward валидацией и калибровкой.

Плюс развитый «процессный» слой: `plan/`, `agents/` (ТЗ executor/reviewer на каждый этап), `docs/`.

---

## Плюсы

**Инженерная культура — заметно выше среднего для пет-проекта:**
- **Безопасность БД сделана правильно**: параметризованные запросы + whitelisting идентификаторов (`ALLOWED_COLUMNS`/`ALLOWED_TABLES` в `database.py`, `validate_table/column` перед каждым динамическим SQL), `html.escape()` для пользовательских данных. Есть тест на XSS (`<script>` → entities).
- **Секреты в порядке**: `.env` в `.gitignore`, в репо только `.env.example`. Токенов в истории нет.
- **CI совпадает с локальным `make ci-local`**: ruff + mypy + compileall + pytest, кэш зависимостей, Python 3.11 как в проде.
- **Разделение зависимостей**: `requirements.txt` (бот) / `-dev.txt` / `-modeling.txt` — ML-пакеты не текут в Docker-образ бота.
- **Пайплайн загрузки**: идемпотентные upsert'ы (`ON CONFLICT DO UPDATE`), явная семантика null vs 0 (семья `optional_*` хелперов, задокументирована), экспоненциальный backoff с уважением `Retry-After`.

**Модельный контур — отдельно сильная часть:**
- Чистое разделение: сборка датасета ходит в PostgreSQL, обучение — **только** из CSV+JSON. Это **проверяется AST-тестом** (запрет импорта `psycopg2`/`dataset_builder` в train-модулях).
- Грамотная защита от **утечки времени**: walk-forward, `shift(1)` в rolling-фичах, отдельный `calibration_k`-блок, явный запрет `KFold(shuffle=True)` (AST-тест), запрет `CalibratedClassifierCV` (его внутренний CV ломает временной порядок).
- **Воспроизводимость**: единый `random_seed` разводится по всем подсистемам, в метадату пишутся версии библиотек, git-commit, `features_hash`.
- **Acceptance-gate**: модель обязана бить тривиальный base-rate, иначе прогон `failed_baseline_check` и симлинк `latest` не двигается.
- **Pydantic v2 конфиг** с fail-fast при расхождении YAML и `metadata_train.json` (источник истины — метадата).
- Реализация **обгоняет план**: целевая карта файлов из плана реализована полностью + сверх (`bootstrap.py`, `acceptance.py`, `report.py`). 17 тест-файлов, ~3500 строк модельных тестов.

**Документация и планирование** — необычно зрелые: `DEVELOPMENT.md`, `docs/architecture.md`, пошаговые ТЗ в `agents/`, приоритизированный `refactoring_plan_3.md` (P0–P3).

## Минусы

**Критичные / высокие:**

| Проблема | Где | Риск |

**Средние:**
- Монолит `load_season_modern.py` смешивает fetch/transform/load — тяжело тестировать и переиспользовать.
- Нет версионируемых миграций (есть `data_tables/migrations/`, но это не история с rollback); нет индексов и FK-ограничений в DDL.
- Нет валидации обязательных env-переменных на старте бота (упадёт при первом обращении к БД).
- Docker: образ от root, без healthcheck; в compose нет volume для БД (данные теряются на `down`).
- Нет lock-файла зависимостей; `mypy ignore_missing_imports=True` слишком мягкий.
- Датасеты CSV закоммичены в `artifacts/`, хотя `DEVELOPMENT.md` просит выгрузки не коммитить (пока мелочь — 1211 строк).

## Валидация плана на будущее

План разделяется на два трека.

### 1. Инженерный трек (`refactoring_plan_3.md`) — план валиден ✅

Приоритизация P0–P3 трезвая и совпадает с тем, что видно в коде: P0 «тупики в `/stats`» и P1 «кэш read-only запросов + конфтест + DB-job в CI» — это и есть реальные слабые места. Замечания:
- **DB-D (Postgres-job в CI) стоит поднять с P1 в фактический приоритет** — закрывает сразу две дыры (DB-тесты не в CI + ломкость DDL). Сейчас недооценён.
- В план стоит **явно добавить два пункта, которых там нет**: (а) апгрейд `python-telegram-bot` (безопасность + блокер для будущего); (б) транзакционная атомарность DELETE→INSERT в пайплайне. Оба важнее многих P2/P3.
- Dead-code чистка (DC-2/DC-3) как P3 — корректно, не трогать раньше.

### 2. Модельный трек (`nhl_classifier_modeling_plan` + UPDATE) — методология отличная, но **блокирующий разрыв с данными** ⚠️

Сам план методологически очень силён (анти-утечка, калибровка без утечки, bootstrap-ДИ, monotone-constraints, acceptance-gate). **Но ключевая проблема — объём данных:**

```
Обучающий датасет: 1211 игр, ОДИН сезон (2025-2026), 7 месяцев, 242 колонки.
predict-датасет: пустой (только заголовок).
```

Конфиг `modeling_default.yaml` требует: `n_test_windows: 5`, `inner_val_games: 300`, `calibration_games: 300`, `holdout.fraction: 0.15`.

**Арифметика не сходится:** каждое из 5 walk-forward окон требует 300 (inner_val) + 300 (calibration) игр, плюс train, плюс test, плюс ~180 на holdout. На 1211 игр это физически не помещается — на ранние окна не остаётся train, а bootstrap-ДИ на тестовых окнах ~100–200 игр будут настолько широкими, что «улучшение log loss над base-rate» окажется статистически неотличимым. То есть **acceptance-gate либо не пройдёт, либо пройдёт неинформативно.**

Дополнительно: февраль 2026 — всего 74 игры (олимпийская пауза), что нарушает однородность месячных окон при `split.method: month`.

**Что это значит для плана:**
- Этапы 1–4, 7–11 (инфраструктура, сплиты, обучение, тесты) — **реализованы и валидны как код**. Не выброшенная работа.
- **Этап 12 (Definition of Done) и Фаза 14 (интеграция в бота) преждевременны на текущих данных.** Выпускать модель в бота сейчас — показывать прогноз, неотличимый от «дом побеждает с base-rate».

**Рекомендации по плану (в порядке приоритета):**
1. **Сначала набрать данные**: загрузить 3–5 прошлых сезонов через тот же пайплайн (`season-sync` с историческими датами) — ~4–6k игр, walk-forward становится осмысленным. Это **предусловие** ко всему остальному в треке.
2. **Параметры сплита привязать к объёму данных**: либо снизить `inner_val_games`/`calibration_games` под текущий сезон для дымовых прогонов, либо явно зафиксировать, что полная конфигурация требует N≥4000 игр.
3. Только после п.1–2 — Фаза 14 (инференс в боте), где ещё не написан код загрузки модели и сверки `features_hash` на инференсе (план описывает, реализации нет).
4. Сезонный retrain через cron (этап 15) — правильное направление, но после стабилизации на мультисезонных данных.

## Итог

Проект **инженерно зрелый и аккуратный** — особенно модельный контур и дисциплина безопасности/воспроизводимости. ## Перепроверка фактов ревью (валидация по коду, 2026-06-29)

Конкретные утверждения сверены с кодом. Большинство подтвердилось; два пункта исправлены.

### Подтверждено
- `load_season_modern.py` = 1543 строки; `python-telegram-bot==13.15`; DB-тесты выключены в CI (`pytest --ignore=tests/test_db_nhl.py`); `dataset_train.csv` = 1211 игр (1212 строк с заголовком); `dataset_predict.csv` пуст (1 строка-заголовок); `configs/modeling_default.yaml` — `n_test_windows: 5`, `inner_val_games: 300`, `calibration_games: 300`, `holdout.fraction: 0.15`, `method: month`; усечения `TELEGRAM_MAX_MESSAGE_LENGTH=4096` и `_TELEGRAM_INLINE_BUTTON_CAP=100`; перекос тестов (~4400 строк modeling-тестов против ~325 бот + 283 пайплайн).

### Исправление №1 — пункт «атомарность загрузки» неверен (уверенность ~95%)
Ревью относило DELETE→INSERT к критичным («падение между DELETE и INSERT → дыра в данных»). Фактически `load_season_modern.py:1149–1490` оборачивает **DELETE из 5 таблиц и все UPSERT в одну транзакцию**: `conn.autocommit = False` (1150) → DELETE (1161-1166) → upsert'ы → единственный `conn.commit()` (1485), `conn.rollback()` в `except` (1487), `conn.close()` в `finally` (1490). Падение посередине откатывает и DELETE — **дыры в данных не возникает**. Пункт снят с «критичных». Остаточный (низкий) риск: одна большая транзакция на прогон дольше держит блокировки.

### Исправление №2 — арифметика модельного трека описывает верный вывод неверным механизмом (уверенность ~80%)
Расчёт «5 окон × (300+300) = 3000 игр не помещаются» некорректен для `method: month`: по `splits.py:188–194` блоки `inner_val_k`/`calibration_k` **перекрываются между соседними окнами** (каждое окно берёт хвост игр перед своим test-месяцем), то есть они не суммируются. **Вывод о нехватке данных остаётся в силе** по иной причине: ранним окнам не хватает истории для расширяющегося train, а bootstrap-ДИ на тест-месяцах ~100–170 игр будут слишком широкими, чтобы acceptance-gate был информативен.

### Не охвачено ревью
- Олимпийская пауза (фев-2026, 74 игры) — не только неоднородность окон, но и сдвиг распределения: `shift(1)`-rolling через 2-недельный перерыв смешивает «форму до» и «после».
- Кода загрузки модели и сверки `features_hash` на инференсе в репозитории не найдено — инференс-контур не прогонялся даже технически (predict-датасет пуст).

## План дальнейших работ

Каждый пункт: **Зачем** (мотивация/риск) и **Как** (конкретные шаги). Приоритеты: P0 — блокирует/опасно сейчас; P1 — высокий; P2 — средний; P3 — потом.

### Трек A — Инженерный (бот / пайплайн / CI)

#### A1 · Postgres-job в CI + включить `test_db_nhl.py` — **P0**
- **Зачем.** Сейчас DDL и SQL-функции проверяются только вручную (`ci.yml`: `--ignore=tests/test_db_nhl.py`). Ломающее изменение схемы попадёт в master незамеченным. Закрывает сразу две дыры из ревью (DB-тесты не в CI + ломкость DDL).
- **Как.** Добавить в `ci.yml` сервис-контейнер `postgres:16` (`services:` с healthcheck `pg_isready`), прокинуть `PG_HOST/PORT/USER/DATABASE` в env шага тестов, применить DDL из `data_tables/` перед прогоном, убрать `--ignore=tests/test_db_nhl.py` в отдельном шаге «Tests with PostgreSQL». Локально это уже умеет `make ci-local` — синхронизировать.

#### A2 · Апгрейд `python-telegram-bot` 13.15 → 21.x — **P0**
- **Зачем.** Версия 2021 года: накопленные уязвимости и тупик для будущих фич (async-API, новые типы апдейтов). Ревью верно подняло это выше «атомарности».
- **Как.** Это мажорный разрыв (13.x sync → 20+/21.x asyncio). Создать ветку, перевести хендлеры на `async def`, заменить `Updater`/`Dispatcher` на `Application`, обновить сигнатуры `context`/`job_queue`, прогнать `test_skater_reports_bot.py`/`test_nhl_scoreboard.py` и ручной smoke меню `/stats`. Зафиксировать новую версию в `requirements.txt`.

#### A3 · Поднять покрытие тестами бота и пайплайна — **P1**
- **Зачем.** Самая используемая часть (`bot.py`, `database.py`, подписки, push, загрузчик 1543 стр.) покрыта <30%/<20% — регрессии здесь не ловятся, тогда как модель покрыта ~80%.
- **Как.** Приоритет по риску: (1) `database.py` — тесты whitelisting/`validate_table/column`, пагинация, read-only запросы (на postgres-job из A1); (2) хендлеры `bot.py` — рендеринг карточек, пагинация, ветки ошибок; (3) пайплайн — transform-хелперы и сборка строк на фикстурах NHL API без сети. Цель: бот/пайплайн ≥50%.

#### A4 · Явные предупреждения при усечении в UX — **P1**
- **Зачем.** Обрезка до 4096 символов (`bot_messages.py:13`) и кэп 100 кнопок (`bot.py:151`) происходят молча — пользователь не знает, что часть игр/данных скрыта.
- **Как.** При срабатывании усечения добавлять явный маркер («… показаны первые N из M») и/или пагинацию вместо обрезки. Для кнопок — страницы «вперёд/назад». Покрыть тестом граничный случай (M > 100).

#### A5 · Rate-limiting в боте — **P1**
- **Зачем.** Спам пагинацией = N+1 запросы к PostgreSQL без ограничений → деградация под нагрузкой/абьюзом.
- **Как.** Лёгкий per-user троттлинг (token-bucket в памяти или `ptb` `RateLimiter` после A2), debounce на callback-кнопки, опц. короткий TTL-кэш read-only ответов (совпадает с P1 «кэш read-only запросов» из `refactoring_plan_3.md`).

#### A6 · Валидация обязательных env на старте бота — **P1**
- **Зачем.** Сейчас отсутствие env всплывает при первом обращении к БД, а не на старте — бот «запускается», но падает в рантайме у пользователя.
- **Как.** Fail-fast проверка при инициализации (по образцу Pydantic-конфига модельного трека): собрать обязательные ключи (`BOT_TOKEN`, `PG_*`), при отсутствии — внятная ошибка и выход с ненулевым кодом.

#### A7 · Версионируемые миграции + индексы/FK в DDL — **P2**
- **Зачем.** `data_tables/migrations/` — не история с rollback; нет индексов и FK-ограничений → риск рассинхрона схемы и медленных запросов по мере роста данных (особенно после загрузки 3–5 сезонов, B1).
- **Как.** Ввести инструмент миграций (Alembic или нумерованные up/down SQL), добавить FK между `games`/`game_*_stats` и индексы по `game_id`/`season_id`/датам. Прогонять миграции в CI-job из A1.

#### A8 · Hardening Docker / compose — **P2**
- **Зачем.** Образ от root без healthcheck; в compose нет volume для БД — данные теряются на `down`.
- **Как.** Non-root `USER` в Dockerfile, `HEALTHCHECK`, в `docker-compose.yml` — именованный volume для PGDATA и `depends_on` с healthcheck Postgres.

#### A9 · Lock-файл зависимостей + ужесточить mypy — **P3**
- **Зачем.** Без lock-файла сборки невоспроизводимы; `ignore_missing_imports=True` маскирует ошибки типов.
- **Как.** `pip-tools`/`uv` → закоммитить `*.lock`; постепенно сузить mypy-исключения до конкретных модулей вместо глобального флага.

### Трек B — Модельный (данные — блокирующий трек)

> Этапы 1–11 (инфраструктура, сплиты, обучение, тесты) реализованы и валидны как код. Блокер — **данные**, не методология.

#### B1 · Загрузить 3–5 прошлых сезонов через тот же пайплайн — **P0 (предусловие ко всему треку B)**
- **Зачем.** На 1 сезоне (1211 игр) walk-forward на 5 окон неинформативен: ранним окнам не хватает train-истории, bootstrap-ДИ на тест-месяцах ~100–170 игр слишком широкие → acceptance-gate либо не пройдёт, либо пройдёт неинформативно.
- **Как.** Прогнать `season-sync` с историческими датами для сезонов 2020/21–2024/25 (~4–6k игр). Проверить идемпотентность upsert'ов (уже есть), затем пересобрать `dataset_train.csv`. Учесть олимпийскую паузу фев-2026 как разрыв (см. ниже).

#### B2 · Привязать параметры сплита к объёму данных — **P1 (после B1)**
- **Зачем.** Конфиг 300/300/5-окон рассчитан на мультисезонную историю; на одном сезоне он физически не помещается. Нужно либо адаптировать под smoke-прогоны, либо явно зафиксировать минимум данных.
- **Как.** В `configs/modeling_default.yaml` ввести профиль для smoke (меньшие `inner_val_games`/`calibration_games`/`n_test_windows`) и зафиксировать в доке/конфиге, что полная конфигурация требует N≥4000 игр. Добавить guard в `splits.py`/`config.py`, падающий с понятной ошибкой при нехватке истории под заданные параметры (часть уже есть — `SplitError`).

#### B3 · Обработать олимпийскую паузу как разрыв временного ряда — **P2 (после B1)**
- **Зачем.** Фев-2026 = 74 игры + 2-недельный перерыв: `shift(1)`-rolling-фичи смешивают форму «до» и «после» паузы (сдвиг распределения), а месячное окно неоднородно.
- **Как.** Пометить паузу в календаре фич, сбрасывать/флагать rolling-окна на разрыве, либо исключить переходные игры из обучения. Покрыть тестом в `test_modeling_splits.py`.

#### B4 · Реализовать инференс-контур: загрузка модели + сверка `features_hash` + заполнение predict-датасета — **P1 (после B1–B2)**
