**Связано:** задачи 101–106 — реестр `plan/open_tasks.md`, карточки `plan/tasks/task_10{1..6}_*.md`;
выросли из Задачи 37 (закрыта в минимальном объёме, `plan/archive/`). Строки кода — снимок `origin/develop` = `15483fb`, сверять.

## Запрос

Со слов человека: база команд по плей-офф с продуманными таблицами; отдельно — статистика
игроков в плей-офф; загрузить историю, чтобы ИИ (`telegram_bot/ai_stats.py`) отвечал на
вопросы о плей-офф.

## Решения человека (2026-10-31)

| Вопрос | Решение |
|---|---|
| Глубина истории | Те же 5 полных сезонов, что и регулярка (2021/22–2025/26), плюс текущий — с полной поматчевой детализацией. Старые сезоны не грузим |
| Объём работы | Данные в БД + ответы ИИ. Новые экраны бота (сетка, лидеры плей-офф, переключатель «регулярка / плей-офф») — отдельными задачами позже. В боте — только пометка раунда из 106 |
| Сезонные итоги плей-офф | **Вариант B:** `game_type` входит в ключ сезонных агрегатов, итоги плей-офф грузятся из stats API (`gameTypeId=3`) — официальные цифры NHL, включая продвинутые метрики |

Это отменяет решение из карточки 37 «сезонные агрегаты за плей-офф не загружаются» (теперь
в архиве): теперь загружаются — в те же таблицы, отличаясь `game_type`.

## Отвергнутые варианты

- **A — итоги плей-офф суммой поматчевых таблиц.** Поматчевые таблицы покрывают голы,
  передачи, броски, TOI, ±, большинство/меньшинство, хиты, вбрасывания, сейвы, но не
  продвинутые метрики (Corsi/Fenwick, старты в зонах) и не смены. Человек выбрал официальные
  цифры с продвинутыми метриками.
- **C — отдельные таблицы `playoff_*`.** Дубль DDL и загрузчика — Global Constraints 2 и 3.
- **Посев команд из `/v1/playoff-series/carousel`.** Не просили (YAGNI); серии строятся из
  `games` без нового источника.

## Схема

### `games` (101, своя миграция)

`game_type smallint NOT NULL CHECK (game_type IN (2, 3))` — 2 регулярка, 3 плей-офф. Ею
отличаются и все поматчевые данные плей-офф: `game_player_stats`, `game_goalie_stats`,
`game_team_stats`, `all_goals`, `shot_attempts`, `game_three_stars` ключуются по `game_id`
и не меняются.

### Сезонные агрегаты (103, своя миграция)

Таблицы: `teams_stats`, `players_season_stats`, `goalies_season_stats`,
`players_advanced_stats`, `players_shot_types`.

- Колонка `game_type smallint NOT NULL CHECK (game_type IN (2, 3))`, бэкфилл `2`.
- PK `(team_id | player_id, season_id)` → `(team_id | player_id, season_id, game_type)`.
- Индексы под лидерборды `(season_id)` → `(season_id, game_type)`.
- FK на `rosters` / `teams` остаются по `(id, season_id)`: игрок и клуб плей-офф — те же
  игрок и клуб сезона.
- Строка `game_type = 3` — итог игрока или команды за плей-офф этого сезона.

`teams` и `rosters` не меняются: справочник клубов по-прежнему строится из регулярки.

### Серии — представление `playoff_series` (105, своя миграция)

Без новой загрузки: строится из `games WHERE game_type = 3`. Раунд и номер серии — из
`game_id` (`2025030123`: сезон 2025, тип 03, раунд 01, серия 2, игра 3):
`round = (game_id / 100) % 100`, `series_number = (game_id / 10) % 10`.

Колонки: `season_id, round, series_number, team_a_id, team_b_id, wins_a, wins_b,
games_played, winner_id, first_day, last_day`.

- Порядок команд в паре фиксирован: `team_a_id = LEAST(home_team_id, away_team_id)`,
  `team_b_id = GREATEST(…)` — пара однозначна, тесты стабильны.
- `wins_a` / `wins_b` — число игр серии с `winner_id` соответствующей команды.
- `winner_id` — команда с 4 победами, `NULL`, пока серия идёт. Обладатель Кубка — `winner_id`
  серии `round = 4`.
- Текущий плей-офф обновляется сам вместе с `games` ежедневным sync.

**Где лежит DDL.** Новый файл `data_tables/t.playoff_series.sql` с
`CREATE OR REPLACE VIEW playoff_series AS …;` (идемпотентен):

- в `DDL_TABLES` Makefile — сразу после `t.games.sql` (порядок создания — `Makefile:26`):
  `scripts/db_drop_all_tables.sql` удаляет `games` с `CASCADE` и уносит представление, а
  применённая миграция после `db-reset` повторно не запускается (`schema_migrations`
  переживает drop, правило зеркалирования — `Makefile:119–122`) — пересоздаёт его только
  `db-tables`;
- миграция 105 подключает тот же файл (`\ir`, как миграция 0015 — `ai_reader_grants.sql`);
- `GRANT` — строкой `'playoff_series'` в массиве `data_tables/ai_reader_grants.sql`, который
  `db-tables` уже применяет после DDL; плюс `ai_stats.AI_TABLES` — их сверяет
  `tests/test_db_nhl.py` (`test_grants_are_exactly_select_on_ai_tables`);
- `ai_stats._schema()` (`telegram_bot/ai_stats.py:187–196`) ищет в `t.{name}.sql` только
  `CREATE TABLE.*?\n\);` и иначе бросает `RuntimeError` — регэксп расширяется на
  `CREATE OR REPLACE VIEW … ;`, иначе ИИ падает на первом вопросе. Тест
  `tests/test_bot_ai_stats.py:620` проверяет `CREATE TABLE {table}(` для каждой таблицы
  `AI_TABLES` — он учит и представление (`CREATE OR REPLACE VIEW playoff_series`).

### Нумерация миграций

Три миграции — по одной в 101, 103, 105. Номер — следующий свободный по `origin/develop`
на момент PR (на 2026-10-31 последняя — `0018`); сверять перед PR: параллельные задачи берут
одинаковые номера, и `db-migrate` молча пропускает вторую. Парные `data_tables/t.*.sql`
правятся синхронно (`DEVELOPMENT.md` §«Миграции схемы БД»).

## Загрузка (`pipeline/load_season_modern.py`)

`run()` каждый раз пересобирает сезонные агрегаты (`build_season_reference_rows`, `:1500`),
поэтому ежедневный sync (`pipeline/scheduled_sync.py`) в апреле–июне сам обновляет и итоги
плей-офф: до старта плей-офф отчёты `gameTypeId=3` пусты — строк типа 3 нет. Сам sync правок
не требует, но проверка готовности ночи для дайджеста — требует (ниже, «Готовность ночи»).

- **Игры.** `fetch_final_games` (`:837`, фильтр `:839`): `gameType in (2,3)`;
  `build_game_rows` пишет `game_type` из мета-записи (запись типа — 101, расширение
  фильтра — 104).
- **Расписание остаётся регуляркой.** `fetch_scheduled_games` (`:847`, фильтр `:859`)
  сохраняет `gameType=2`: из `scheduled_games` датасет берёт строки прогноза
  (`modeling/dataset_builder/base.py:146`), а колонки `game_type` у неё нет — фильтр 102 на неё
  не действует, и игры плей-офф молча попали бы в прогноз модели, обученной на регулярке.
  Следствие: ближайшие матчи плей-офф не попадают в `scheduled_games` и в превью подписки
  «Предстоящие матчи» — это часть будущих экранов плей-офф, не этой работы.
- **Готовность ночи.** `night_is_loaded` (`telegram_bot/push_digest_job.py:173–196`) собирает
  слейт ночи только с `gameType == 2` (`:135`, `:188`): в ночь, где играется только плей-офф,
  слейт пуст, и функция сразу отвечает «загружено» — дайджест уходит раньше, чем загрузчик
  запишет игры. В 104 вместе с `fetch_final_games` — `gameType in (2, 3)` и здесь, плюс тест
  на ночь только с плей-офф.
- **Агрегаты.** Методы `build_player_season_stats` (`:667`), `build_goalie_season_stats`
  (`:766`), `build_player_advanced_stats` (`:588`), `build_player_shot_types` (`:633`)
  принимают тип игры и подставляют его в `gameTypeId=` своих URL; строки несут `game_type`.
  `build_season_reference_rows` вызывает их для 2 и для 3.
- **`build_teams_and_stats` (`:295`) разделяется:** сейчас `teams` и `teams_stats` строятся
  из одного ответа `team/summary`. В ответе `gameTypeId=3` только 16 клубов — `teams` из него
  строить нельзя. `teams` — из регулярки, как сейчас; `teams_stats` — по каждому типу.
- **Ключи upsert.** Пять вызовов `execute_upsert` агрегатов (`:1627` `teams_stats`, `:1674`,
  `:1718`, `:1742`, `:1766`; `:1608` — `teams`, `:1653` — `rosters`) переходят на
  `conflict_columns` `[…, "season_id", "game_type"]` — иначе `ON CONFLICT` не совпадёт с
  новым PK. У `teams` и `rosters` ключ остаётся `(id, season_id)`. В 103 загрузчик пишет
  `game_type = 2` с новым ключом; тип 3 — в 104.
- **Ростеры.** `supplement_rosters_from_reports` (`:456`) уже дописывает в `rosters` всех из
  summary-отчётов, кого нет в ростерах, и падает громко. Ему передаются summary-отчёты обоих
  типов, а `extra_player_ids` — объединение advanced- и shot-type-строк обоих типов: игрок,
  вызванный только на плей-офф, иначе уронит FK.
- **Страна.** `fill_nationality` (`:561`, URL `:578`) берёт bios только с `gameTypeId=2` —
  у игрока, сыгравшего только в плей-офф, `nationality` будет `NULL` (в лог уходит лишь
  `info` со счётом). Bios берутся по обоим типам, тип 2 приоритетнее.
- **Фикстуры.** Плей-офф-игра (по возможности многоовертаймовая) и отчёты `gameTypeId=3` —
  через `scripts/capture_nhl_fixtures.py` (параметризовать тип, сейчас зашит `gameTypeId=2`).
  Проверить на пейлоаде: `is_overtime` (OT2+), `is_shootouts` (в плей-офф всегда false),
  nullable-колонки агрегатов (`points`, `ot`, буллиты в плей-офф пусты).
- **Дозагрузка.** Плей-офф за 5 сезонов в живую БД (`season-load-full` по сезонам,
  `PG_USER=postgres`), перед этим — дамп БД. Сначала `nhl_dev`, на прод — мержем в `master`.

## Потребители: только регулярка (103)

Каждое чтение сезонных агрегатов получает фильтр `<alias>.game_type = 2` — в той же
подзадаче, что смена PK (до загрузки типа 3 фильтр ничего не меняет):

- `telegram_bot/bot_messages.py` — 12 мест: `_pss_join_sql` (`:105`, `:107`, `:112`),
  лидерборд (`:1162`), `teams_stats` (`:1035`, `:1426`, `:1677`, `:2157`), профиль игрока и
  вратаря (`:1579`, `:1600`), `:1787`, `:1900`.
- `telegram_bot/ai_stats.py` — предпроверки `player_overview`: `_OVERVIEW_SKATER_SEASONS_SQL`
  (`:85`) и `_OVERVIEW_GOALIE_SEASONS_SQL` (`:95`) читают по `season_id IN (…)` и после
  загрузки получат по две строки на игрока.
- `telegram_bot/database.py:35–83` и `leaderboard_specs.py` — белые списки таблиц и колонок,
  запросов не держат; `game_type` в списки колонок для сортировки не добавляется.
- `scripts/verify_skater_reports_schema.sql` — сверить проверки PK под новый ключ.
- `modeling/` агрегаты не читает (только `games` — это 102).

Тесты: фикстуры со строкой `game_type = 3` в каждой агрегатной таблице; каждый экран и
`player_overview` показывают регулярку и не дублируют строки.

## ИИ

- **Аннотация схемы — вместе с загрузкой (104).** `telegram_bot/prompts/stats_schema_notes.md:9`
  утверждает «Плей-офф в базе нет совсем»; после загрузки это ложь. В той же подзадаче строка
  заменяется правилом: `games.game_type` 2 — регулярка, 3 — плей-офф; сезонные таблицы
  несут `game_type`; по умолчанию — только регулярка (`game_type = 2` и в поматчевых суммах
  через `games`: «последние N игр», «против команды», «дома/в гостях» иначе молча включат
  плей-офф), плей-офф — по явному вопросу. Маршрутизатор при этом ещё отказывает на
  плей-офф — честный отказ, не ложь.
- **Вопросы про плей-офф (105).** Аннотация `playoff_series` и обладателя Кубка; из
  промптов маршрутизатора (`ai_router.py:57`, `:71`, `:82`), ответа (`stats_answer.md:19`) и
  ревьюера (`stats_reviewer.md:8`) уходит «плей-офф нет / отказ»; кейсы плей-офф в
  `scripts/ai_stats_eval.jsonl` (обладатель Кубка, счёт серии, бомбардир плей-офф сезона,
  регулярка по умолчанию не включает плей-офф).
