# Задача 68. Модель вероятности победы — дизайн

**Дата:** 2026-10-11 · **Ветка:** `task-68-win-model` · **Карточка:**
[`plan/archive/tasks/task_model/task_68_win_model.md`](../../../plan/archive/tasks/task_model/task_68_win_model.md)

## Цель

`home_win` (победа хозяев в любом исходе) — откалиброванная вероятность p, которая на сумме
трёх проверочных сезонов Задачи 66 бьёт Elo с подобранной кривой (log-loss 0.6754). Нынешние
классификаторы `home_win` (logreg и lgbm на 215 колонках) Elo не бьют и заменяются.

## Решения человека (2026-10-11)

1. **Вариант B** — модель встраивается в существующий конвейер (`dataset_builder` →
   `train_runner` → `predict` → `publish` → `retrain`), а не отдельным модулем, как `goal_model.py`.
2. **Критерий калибровки карточки «≤ 2 п.п. в корзинах от 100 игр» заменён.** Он недостижим:
   шум доли побед в корзине на 100–600 игр — ±4–8 п.п. (2 SE), и сам Elo-эталон его не проходит
   (8.6 п.п.). Новый гейт `home_win`: pooled log-loss **ниже** Elo **и** pooled ECE **не выше**,
   чем у Elo. Таблица корзин с полосой шума ±2 SE пишется в отчёт без порога.

## Разведка (2026-10-11, одноразовый скрипт вне репозитория)

Реальные данные: 6049 строк датасета (`--min-prior-games 5`), `games_train.csv` 6568 игр,
броски из `game_team_stats` (выгружены из демо-базы `nhl_bot_predict_demo`; за пять полных
сезонов совпадают с рабочей `postgres` до строки, в демо-базе нет только 2026/27). Схема 66: модель сезона s учится на сезонах < s, проверка — все
строки датасета сезона s, ДИ — парный bootstrap по игровым дням. Логрег на одной разнице Elo
воспроизводит эталон до 4-го знака (0.6754 = 0.6754), протокол честный.

| признаки | log-loss | − Elo [95% ДИ] |
|---|---|---|
| Elo (подобранный по сезону) | 0.6754 | 0 |
| + b2b хозяев и гостей | 0.6734 | −0.0020 [−0.0044; +0.0005] |
| + доля бросков EWMA | 0.6714 | −0.0040 [−0.0065; −0.0015] |
| + b2b + доля бросков | 0.6692 | −0.0061 [−0.0098; −0.0022] |
| + b2b + доля бросков + отдых в днях | 0.6691 | −0.0062 (отдых ничего не добавляет) |
| + b2b + разница голов EWMA | 0.6739 | −0.0015, ДИ через 0 |
| **`diff_elo` датасета (константы Задачи 40) + b2b + доля бросков, протокол `train_runner` без Platt** | **0.6695** | **−0.0059 [−0.0100; −0.0016]**, ECE 0.017, все корзины в шуме |
| то же, но Platt на 300 играх | 0.6719 | −0.0035 [−0.0085; +0.0017], ECE 0.036 |
| то же, но с прогревочным сезоном 2021/22 в обучении | 0.6699 | −0.0054, ECE 0.027, 4 корзины за шумом |

Выводы, из которых следует дизайн:
- Модель лучше Elo в каждом из трёх сезонов; выигрыш устойчив к полураспаду EWMA (10–40 игр)
  и сжатию на смене сезона (0.33–0.66): от −0.005 до −0.007, ДИ без 0.
- Подобранный по сезону Elo как признак не нужен: фиксированная `diff_elo` даёт то же.
- Platt на 300 играх вредит (как и у lgbm в 66). Регуляризованный логрег (C на `inner_val`)
  сам прижимает прогноз к 0.5 и закрывает недооценку хозяев-андердогов, которую видно и у Elo.
- Прогревочный сезон (все стартуют с 1500) портит калибровку — из обучения исключается.

## Дизайн

### 1. Признак `diff_shot_share_ewm` (`modeling/dataset_builder/`)

Доля бросков команды в игре `shots_for / (shots_for + shots_against)` сглаживается
экспоненциально по играм команды: `s ← s + α·(x − s)`, `α = 1 − 0.5^(1/20)` (полураспад 20 игр),
старт 0.5. На смене сезона — сжатие к 0.5: `s ← 0.5 + 0.5·(s − 0.5)`. Значения константы,
как у Elo: модульные константы, не конфиг (GC1).

- **Межсезонный проход по всей истории сыгранных игр**, как у Elo (rolling-окна датасета
  сбрасываются на смене сезона, этот признак — нет). Источник — тот же `elo_history`
  (`load_target_games(..., with_outcome=True)`), к нему добавляются броски хозяев и гостей из
  уже присоединённых `game_team_stats` (`hs.shots`, `aws.shots`).
- **Без утечки:** значение на игру — по играм строго до её дня; обновления дня применяются
  после всех игр этого дня (та же заморозка, что в `EloHistory.run`).
- **Predict:** будущая игра (нет в истории) получает финальное состояние команды, как
  `attach_pregame_elo` берёт `final_ratings`. Команда без истории — 0.5.
- **Пропуск бросков в сыгранной игре — `ValueError`** (GC4). В рабочей БД (`postgres`) таких
  игр нет: броски есть у всех 6568 сыгранных, включая 8 игр 2026/27 (проверено 2026-10-11).
- В датасет идут `home_shot_share_ewm`, `away_shot_share_ewm`, `diff_shot_share_ewm` (по
  образцу `elo`: `sum_` не строится — сумма двух долей несёт не больше сигнала, чем разность).
  Колонки входят в манифест и `features_hash` — датасет и predict-манифест пересобираются.
- Расчёт прохода — функция рядом с Elo-аттачем в `features.py`; общий «аттач по `game_id`
  с откатом на финальное состояние» выносить, только если он дословно повторяет Elo (2-е
  повторение — не выносить, GC1).

### 2. Модель `home_win` (`configs/`, `modeling/config.py`, `modeling/train_runner.py`)

- **Признаки:** `tasks.home_win.features: [diff_elo, home_is_b2b, away_is_b2b,
  diff_shot_share_ewm]` в обоих конфигах. Поле `features` в `TaskToggle` — необязательное;
  не задано — все колонки датасета (так у `over_5_5`). Неизвестное имя — `ConfigError`.
- **Только `logreg`.** Семейства задачи — константа в `train_runner`
  (`home_win: (logreg,)`, `over_5_5: (logreg, lgbm)`); `--model lgbm --task home_win` —
  `ConfigError`, `--model both` для `home_win` даёт только `logreg`.
- **Обучение сезона s:** строки сезонов < s **без первого сезона датасета** (прогрев Elo);
  C из `models.logreg.grids.C` выбирается на `inner_val`, как сейчас.
- **Без Platt:** для `home_win` калибратор — тождество (`calibration_skipped`, уже
  поддержан в `calibrate.py`); строки блока `calibration` идут в обучение модели (C выбран,
  после выбора модель дообучается на всех строках до сезона). То же для финальной модели:
  все строки датасета без прогревочного сезона. Обоснование — разведка: логрег, обученный
  на сезонах обучения, сам и есть подобранная на них кривая (как Platt у эталона Elo в 66),
  а Platt на 300 играх вредит. Это осознанное отступление от строки карточки про Platt.
- `over_5_5` не меняется ни в чём.

### 3. Гейт и отчёт (`modeling/acceptance.py`, `modeling/train_runner.py`, `modeling/metrics.py`)

- **Гейт `home_win`:** pooled `model.log_loss < elo.log_loss` **и** pooled
  `model.ece <= elo.ece`. Причина отказа в `summary.md` называет, какое условие не выполнено.
  Гейт `over_5_5` (против константы) не меняется.
- **Таблица калибровки** (`calibration_table`): к каждой корзине — `noise_2se`
  (`1.96·√(p̄(1−p̄)/n)`) и `outside_noise` (`|факт − прогноз| > noise_2se`). Только отчёт.
- Срезы (`season_start`, `post_olympic_break`, `prior_games_*`) остаются как есть.

### 4. Predict, publish, promote

- `metadata.json` модели несёт список её признаков (`model_features`); `predict` подаёт в
  модель только их, проверка `features_hash` всего predict-датасета остаётся.

### 8. Фикс: признаки команды отставали на одну игру (решение человека 2026-10-11)

Найдено при реальном прогоне. Строка команды в `compute_team_rolling_features` описывала
состояние **до** своей игры (rolling по `shift(1)`, `prior_games_count = cumcount()`, отдых
перед этой игрой), а as-of снапшот берёт строку **предыдущей** игры. Итог на реальном датасете
(сверка с расписанием из `games_train.csv`): `*_roll_mean_*` совпадают с «без последней игры» в
100% строк (с правильным значением — 16.6%); `prior_games_count` = верное − 1 в 100%;
`rest_days` = отдых перед прошлой игрой в 100% (верный — 37.6%); то же у `is_b2b` и
`games_last_7d`. Сырые колонки последней игры (`home_goals_for` и т.п.) верны. Затронуты и
признаки `over_5_5`, и отсечение `--min-prior-games`. Человек решил чинить в 68.

Фикс в `modeling/dataset_builder/features.py`:
- строка команды — состояние **после** своей игры: rolling-средние включают эту игру (без
  `shift(1)` и маски сдвоенного дня), `prior_games_count = cumcount() + 1`; снапшот предыдущей
  игры тогда даёт верное состояние на день цели;
- `rest_days`, `is_b2b`, `games_last_7d` считаются от дня **цели** после снапшота:
  `rest_days = день цели − hist_day` (99 без снапшота в сезоне, как сейчас), `is_b2b = rest_days ≤ 1`,
  `games_last_7d` — игры команды в `[день цели − 7, день цели)`; для predict — так же, по истории;
- тест-инвариант на синтетической истории: для каждой цели rolling-среднее = среднее последних
  ≤ N игр команды строго до дня цели в сезоне, `prior_games_count` = число таких игр, `rest_days`
  = разница с последней игрой.

Следствия: число строк датасета вырастет (отсечение 5 игр теперь честное); `features_hash`
меняется; прогон из «Приёмки» делается после фикса; таблица разведки выше и итог 66 —
исторические числа на датасете с багом. Признаки `home_win` не меняются.

1. Реальный прогон: `build-dataset --mode train --min-prior-games 5` на живой БД →
   `train --config configs/modeling_default.yaml --task home_win` — `status: ok`: pooled
   log-loss ниже Elo, ECE не выше Elo; ДИ разности «модель − Elo» записан. Числа — в docs.
2. `predict` + `publish-predictions` проходят на реальном predict-датасете с новой моделью.
3. Тесты: признак (as-of — без игр того же дня, сжатие на смене сезона, финальное состояние для
   predict, падение на пропуске бросков); конфиг (`features`, неизвестное имя, семейства задачи);
   гейт (отказ по ECE, отказ по log-loss, проход); `noise_2se` в таблице корзин; predict
   подаёт только `model_features`; исключение прогревочного сезона.
4. `make ci-local` зелёный; `make all-tests` (изменён загрузочный SQL сборщика).
5. Ревью Opus.
