# CLAUDE.md — правила работы агентов в NHL_bot

Telegram-бот со статистикой NHL: `pipeline/` грузит NHL API → PostgreSQL,
`telegram_bot/` читает БД и рисует меню, `modeling/` строит датасеты и обучает модели.

**Читать перед работой:** [`docs/architecture.md`](docs/architecture.md) — карта проекта,
[`DEVELOPMENT.md`](DEVELOPMENT.md) — окружение, CI, зависимости. Не дублировать их здесь.

**Этот файл устаревает — чинить на месте.** Увидел, что факт отсюда разошёлся с репозиторием,
БД или планом — поправь в том же коммите и скажи об этом в отчёте; разрешение выдано заранее,
спрашивать не нужно. Исключение — Global Constraints 1–7 и «Мандат ревьюера»: это решения
человека, а не факты. Считаешь их устаревшими — сообщи и предложи, но не переписывай сам.

## Обязательные команды

| Команда | Когда |
|---|---|
| `make ci-local` | **Перед каждым коммитом.** ruff + mypy + compileall + pytest. Совпадает с GitHub Actions |
| `make test-fast` | Быстрый прогон тестов без линтера |
| `make all-tests` | При изменениях в `data_tables/*.sql`, `telegram_bot/queries/*.sql` или загрузчике (нужна поднятая БД) |

Красный `make ci-local` = задача не выполнена. Не сообщать об успехе без вывода команды.

## Регламент сессий

**Одна задача плана = одна сессия.** Контекст не переносится между задачами: оркестратору
при выполнении Задачи N история Задачи N−1 не нужна, а тянется она в каждом запросе.
Замер на задачах 1–3 (`work_plan_2026-08-08.md`): за 4 дня в одной сессии контекст вырос
33K → 336K, и 82% её стоимости пришлось не на результат, а на перечитывание и перезапись
истории. Отдельная сессия на задачу снижает эту часть примерно втрое.

**Что делает агент.** Закончив задачу (ревью пройдено, `make ci-local` зелёный, отчёт отдан) —
не начинать следующую молча. Сообщить, что задача закрыта и дальше правильнее начать новую
сессию, и спросить, продолжать ли здесь. Решает человек: попросил продолжить — продолжаем
в текущей сессии без повторных напоминаний до конца следующей задачи.

**Отметка о закрытии — часть задачи.** Перед финальным коммитом пометить задачу закрытой
в файле плана (`plan/engineering/work_plan_*.md`), в трёх местах сразу:

1. заголовок задачи — сменить `⬜`/`🟨` на `✅`;
2. строка `**Статус: не начата**` под заголовком → `**Статус: выполнена** (дата, ветка, PR)`;
3. строка задачи в «Сводке статусов» вверху файла — статус `✅ выполнена` и основание
   (ветка и PR); обновить снимок `origin/master` и «следующую задачу по порядку».

Правка идёт тем же коммитом, что и код задачи. Основанием служат ветка и PR, а не SHA
коммитов: коммит с отметкой не может сослаться на собственный хэш, а ветка и номер PR
известны заранее — конкретные коммиты можно указать сверху как необязательное дополнение.
Задача без отметки в плане не считается закрытой, даже если ветка смерджена. Разрешение
выдано заранее, спрашивать не нужно.

**Перерыв в работе.** Пауза дольше часа обнуляет кэш промпта, и возврат в старую сессию
стоит полной перезаписи контекста. После долгого перерыва начинать новую сессию, а не
дописывать вчерашнюю.

## Модели

| Роль | Модель |
|---|---|
| Реализация | Sonnet по умолчанию. Поднять до Opus — решение скилла, ведущего задачу; перечень таких задач здесь не фиксируется |
| **Любое ревью — задачи, ветки, повторное после правок** | **Opus** |

Ревью не переводится на Sonnet ни при каком размере задачи: находки ревьюера — последний
барьер перед мастером, и экономия здесь оплачивается пропущенным дефектом.

## Global Constraints

Обязательны для любого агента, который пишет или ревьюит код в этом репозитории.

1. **YAGNI.** Абстракция вводится с третьего повторения, не раньше. Никаких конфиг-флагов,
   слоёв, плагинных точек и хуков «на будущее». Если требования нет в ТЗ — кода быть не должно.
2. **Расширять, а не плодить.** Новый файл или модуль — только если задача его явно требует.
   По умолчанию правим существующий и следуем стилю соседнего кода.
3. **Никакой обратной совместимости.** Проект пре-релизный, пользователь один.
   Заменил реализацию — удали старую. Две живущие рядом ветки одного и того же запрещены.
4. **Падать громко.** Никаких `try/except`, глушащих ошибку, и никаких «fallback на всякий случай».
   Ловим исключение только там, где есть осмысленная реакция.
5. **Зависимости.** Новый пакет — только с явного разрешения человека.
   Приложение → `requirements.txt`, инструменты → `requirements-dev.txt`, ML → `requirements-modeling.txt`.
6. **Бюджет задачи.** Чистый прирост более 300 строк — ревьюер помечает как Important
   и требует обоснования. Крупная задача должна быть разбита, а не написана одним куском.
7. **Документация — часть задачи.** Публичная функция: docstring «что делает / зачем / аргументы».
   Модуль: шапка в 3–5 строк о его роли в пайплайне.
   Появился/исчез/переехал модуль — обновить `docs/architecture.md` в том же коммите.
8. **Объём данных.** Инфраструктура моделирования масштабируется под фактический объём
   данных, а не под гипотетический. Числа ниже — снимок, а не источник истины: проверять
   перед работой. В БД 5 сезонов, ~6.5k игр (2026-08-10). Датасет при этом отстаёт —
   `artifacts/datasets/season_20252026/dataset_train.csv`: 1211 игр, один сезон (2026-08-12).
   Загрузка в БД ≠ пересобранный датасет, это два разных факта.

## Мандат ревьюера

Ревью проверяет не только «работает ли», но и **что можно удалить**:

- Что в диффе **не требуется** по ТЗ? Лишнее — находка уровня **Important**, подлежит удалению.
- Нарушение любого из Global Constraints выше — находка уровня **Important**.
- Тест, который ничего не утверждает, или мок вместо реальной проверки — **Critical**.
- Дословное дублирование блока логики — **Important**.

Формулировать находки с указанием `файл:строка` и конкретным нарушенным пунктом.

## Секреты

Секреты только в `.env`, в репозиторий — `.env.example`. Токены и доступы к БД не коммитить,
не печатать в логи и не вставлять в отчёты.
